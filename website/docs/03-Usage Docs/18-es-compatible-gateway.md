# Elasticsearch-Compatible API Gateway

LakeSoul ships `lakesoul-es-gateway`, a small HTTP service that exposes the Elasticsearch REST surface retrieval clients speak, backed by LakeSoul tables with Tantivy full-text and IVF+RaBitQ vector indexes. Clients keep their Elasticsearch driver and point it at the gateway:

- keyword retrieval runs against the text index with BM25 scores;
- vector retrieval runs against the vector index with cosine similarity;
- document writes, delete-by-query and partial updates map onto LakeSoul upserts (merge-on-read plus CDC tombstones), and the indexes are maintained synchronously — a document is searchable when the write request returns.

Indexes are **pre-declared** in a TOML configuration; the gateway provisions the tables at startup and rejects undeclared indexes.

## Quick start

```bash
cargo build --release -p lakesoul-es-gateway
```

`lakesoul-es-gateway.toml`:

```toml
[server]
listen = "0.0.0.0:9200"
version = "8.19.6"        # reported by GET /; 7.x binds clients to keyword-only

[lakesoul]
namespace = "default"
warehouse_prefix = "s3://bucket/lakesoul"
# S3 credentials can be set here or via the environment
# endpoint = "http://minio:9000"
# s3_bucket = "bucket"
# s3_access_key = "..."
# s3_secret_key = "..."

[defaults]
hash_bucket_num = 4
tokenizer = "jieba"
nprobe = 64

[[indexes]]
name = "my_index"          # Elasticsearch index name
table = "my_docs"          # LakeSoul table (defaults to the index name)
dim = 1536                 # embedding dimension; omit for keyword-only
```

```bash
export LAKESOUL_PG_URL='jdbc:postgresql://127.0.0.1:5432/lakesoul_test?stringtype=unspecified'
export LAKESOUL_PG_USERNAME=lakesoul_test
export LAKESOUL_PG_PASSWORD=lakesoul_test
./target/release/lakesoul-es-gateway --config lakesoul-es-gateway.toml
```

## Document model

Every document is stored with a fixed schema: `content` (the full-text
column), `source_id`, `source_type`, `chunk_id`, `knowledge_id`,
`knowledge_base_id`, `tag_id`, `embedding`, `is_enabled`, `is_recommended`.
The internal primary key is generated by the gateway and returned as the
string `_id`. Embeddings are L2-normalized on write and indexed with the
inner-product metric, so the indexed similarity is cosine.

## Supported endpoints

| Endpoint | Behaviour |
|----------|-----------|
| `GET /` | Version and cluster info; the reported `version.number` selects the client dialect (7.x keyword-only, otherwise v8). |
| `HEAD /{index}`, `PUT /{index}` | Declared indexes exist; `PUT` validates the declaration and ignores `number_of_shards`/`number_of_replicas`. |
| `GET /{index}/_mapping` | Fixed mapping, with all filter fields as `keyword`. |
| `POST /{index}/_doc`, `PUT /{index}/_doc/{id}/_create`, `PUT/POST /{index}/_doc/{id}` | Single-document upsert. |
| `POST /{index}/_bulk` | NDJSON `index`/`create` actions (v7 `_id` and v8 server-generated forms). |
| `POST /{index}/_delete_by_query` | `terms`/`term`/`bool` filters; matching rows are rewritten as CDC tombstones. |
| `POST /{index}/_update_by_query` | The fixed scripts for enable/disable, tag updates and moving a knowledge base. |
| `POST/GET /{index}/_search` | Keyword, vector and filter-only queries. |
| `POST /{index}/_refresh` | No-op: writes are visible immediately. |

All responses carry `X-Elastic-Product: Elasticsearch`, and errors use the
`{"error":{"type","reason"},"status"}` shape.

## Search semantics

Keyword search (`match` on the content column) returns hits ordered by BM25
with a numeric `_score`. Candidates are verified against the current rows, so
updated or deleted documents never leak into the response. Ordering across
hash buckets uses each bucket's own index statistics — the same trade-off as
a default Elasticsearch search across shards; rank fusion (RRF) stays on the
client side.

Vector search uses the `script_score` form the clients send:

```json
{"query":{"script_score":{
   "query":{"bool":{"filter":[{"term":{"knowledge_base_id":"kb1"}}]}},
   "script":{"source":"Math.max(cosineSimilarity(params.query_vector, 'embedding'), 0.0)",
             "params":{"query_vector":[0.1, 0.2]}},
   "min_score":0.5}},
 "size":10,"_source":{"excludes":["embedding"]}}
```

Candidates come from the vector index; exact cosine is recomputed over the
current rows and clamped to `[0, 1]` (mirroring the script's `Math.max`),
and `min_score` filters the clamped score. A filter-only query (no scoring
clause) runs as a plain scan and returns the full `_source`, which is what
the index-copy path needs.

## Limitations

- Delete/update resolve their filters with a table scan; only primary keys
  have a fast path.
- `number_of_shards`/`number_of_replicas` are ignored at index creation; the
  bucket count and `nprobe` come from the gateway configuration.
- Authentication, RBAC, highlighting, aggregations and `sort` are not
  implemented.
- The `_search` query subset is `match`, `terms`, `term`,
  `bool.filter/must/must_not` and `script_score` with `cosineSimilarity`.
