# PostgreSQL SQL compatibility tests

`postgres-lakesoul` is a LakeSoul service that speaks the PostgreSQL protocol: it supports queries, `CREATE TABLE`/`DROP TABLE`, `INSERT`, `UPDATE` on non-CDC primary-key tables, and the general `INSERT ... ON CONFLICT DO UPDATE` within the boundaries below, but is not a complete PostgreSQL. The matrix below records the concrete evidence for each integration target; it does not treat every DataFusion SQL capability as verified compatibility.

> Experimental feature: the same binary can run the P0 PostgreSQL logical-replication subscriber with `--subscribe`; the server also supports `CREATE/DROP/ALTER SUBSCRIPTION` and performs synchronization through a local child process, see [SUBSCRIBE_P0.md](SUBSCRIBE_P0.md). It is not part of the SQL compatibility matrix below.

## Running

Run from the repository root in a development environment with the native build dependencies configured (`nix develop` recommended):

```sh
export LAKESOUL_PG_URL='jdbc:postgresql://127.0.0.1:5432/lakesoul_test?stringtype=unspecified'
export LAKESOUL_PG_USERNAME=lakesoul_test
export LAKESOUL_PG_PASSWORD=lakesoul_test
export TZ=UTC

# Prepare the dedicated test database on first use; this script wipes the test database, do not use it on production databases.
./script/meta_init_for_local_test.sh -j 1

LAKESOUL_IO_USE_V2_MERGE=false cargo -q test -p postgres-lakesoul --test sql_compat --test session_contract --test storage_contract --test catalog_contract --test vector_contract --test tpch_contract --test ddl_contract --test insert_contract --test update_contract -- --nocapture
LAKESOUL_IO_USE_V2_MERGE=true cargo -q test -p postgres-lakesoul --test sql_compat --test session_contract --test storage_contract --test catalog_contract --test vector_contract --test tpch_contract --test ddl_contract --test insert_contract --test update_contract -- --nocapture
```

This requires a reachable, initialized, and migrated PostgreSQL, plus the repository's native build dependencies such as `protoc`, the Vortex `flatc`, and Clang/libclang; the TPC-H targets additionally require Python 3.11+ and use only the standard library. No separate PG wire service or hand-made fixtures are needed; these targets use a local warehouse, do not depend on S3/RustFS, and do not require pgvector in a reference PostgreSQL.

The physical executor uses the `datafusion-physical-plan` patch pinned by Git `rev` in the root `Cargo.toml` (`mag1c1an1/datafusion`, branch `feature/lakesoul-physical-plan-55.2`), and no longer keeps a local crate copy. That branch is based on upstream `55.2.0` and retains the repartition spill-pool deadlock fix and the `ScalarSubqueryCardinalityError` used for SQLSTATE `21000` mapping. The patch manifest's other DataFusion dependencies still come from crates.io, avoiding two incompatible type sets; when updating `rev`, keep the existing dependency versions and rerun the scalar-subquery, spill, and real PG protocol regressions.

In addition to the existing legacy/v2 default member tests, CI explicitly runs:

```sh
cargo -q test --profile test-fast -p postgres-lakesoul --test sql_compat --test session_contract --test storage_contract --test catalog_contract --test vector_contract --test tpch_contract --test ddl_contract --test insert_contract --test update_contract --jobs 4 -- --nocapture
```

The workspace `default-members` is unchanged. The default result includes two **named, explicitly marked strict reproductions of known defects** (see below); they are not part of the passing compatibility claim, and the remaining tests must not be skipped for lack of a service. Projection scalar subquery multi-row and `SET TIME ZONE`/connection reset have been fixed and promoted to normal gates; they are no longer counted as defects.

## IVM incremental entry point

The service always installs the IVM runtime; both ordinary `INSERT` and IVM incremental maintenance can coexist for the same user table:

```sql
-- Airflow IVM task
SET lakesoul.ivm.enabled = on;
INSERT INTO target SELECT ... FROM source;

-- Ordinary batch/streaming write
SET lakesoul.ivm.enabled = off;   -- default
INSERT INTO target ...;
```

- Only `INSERT ... SELECT` enters IVM; `INSERT ... VALUES` is always an ordinary INSERT.
- IVM statements require autocommit; explicit transactions and multi-statement simple-query batches are rejected.
- The target table must already have `rowKinds` (the LakeSoul CDC change column); PG DDL allows declaring this exact column name as the quoted `"rowKinds"`. If `__ivm_epoch` is missing, the service adds it to the table schema and automatically rebuilds the data.
- A rebuild happens automatically when the definition changes or the state is empty or dirty. A rebuild uses a single atomic `UpdateCommit` against the user-visible target and does not truncate first, so readers never see an empty table.
- The target table can use `PARTITIONED BY`. IVM records the partitions it has published; a rebuild replaces only those partitions and leaves all others untouched.
- If an external engine produces a data commit in a partition IVM owns or is writing in this run, IVM detects it at refresh start and before commit and reports an error; compaction commits are allowed. Ordinary batch/streaming writes on different partitions can coexist with IVM.
- IVM works together with distributed mode (experimental). The coordinator owns refresh orchestration, epochs, and commits; workers execute serializable scan/lookup/write stages, writing only staged files and never `ivm.epochs`. Example:

  ```sh
  postgres-lakesoul \
    --discovery static \
    --distributed-workers http://worker-0:50051,http://worker-1:50051 \
    --distributed-target-partitions 8 \
    --ivm-view-parallelism 2 \
    --ivm-max-active-tasks 4

  lakesoul-worker --bind 0.0.0.0 --port 50051 \
    --ivm-view-parallelism 2 \
    --ivm-max-active-tasks 4
  ```

  Workers must use the same protocol generation (`lakesoul-distributed/7-ivm`) with IVM enabled; mixed versions fail during discovery/decode. The coordinator and every worker must install the same `--ivm-*` options (`view_parallelism`, `max_active_tasks`, `max_derived_steps`, `state_index`, `internal_file_format`, and the writer/vortex options); these are process-local and workers do not inherit them from the coordinator's plan. With no worker available, or with `--distributed-fallback-local`, refresh runs on the coordinator.
- Distributed IVM's keyed lookup uses datafusion-distributed's Range bucket shuffle. This repository pins the `lakesoul-ivm-range-shuffle` branch, so the range repartition can run on workers; external deployments on a datafusion-distributed version without Range shuffle keep that stage on the coordinator, with unchanged single-node semantics.

## Data path, isolation, and adjudication

- `tests/support/mod.rs` creates tables through the admin-side `LakeSoulSessionFactory` / `SessionContext`; the base fixture writes through SQL, while the storage fixture uses the native writer to preserve real missing-column schemas. The real `postgres-lakesoul` child process built by Cargo starts only after all fixtures are complete.
- Each suite owns an independent LakeSoul namespace (the catalog suite owns a second namespace as well), a temporary warehouse, a PostgreSQL reference schema, and distinct dynamic PG/metrics ports. The service's external contract is LakeSoul namespace → same-named PG database, with user tables inside a database uniformly `public.table`; namespaces are not mapped to PG schemas. The reference PG's dedicated schema/`search_path` is used only for test resource isolation and does not imply that the service exposes a same-named schema; PG-equivalent queries use identical SQL with no implicit rewriting, while catalog mapping is asserted against a separately known LakeSoul contract.
- The base fixture's two-sided INSERT consumes the same explicit VALUES constants; the storage fixture's PG tables explicitly write the final relation independently derived from the commit input. UTC and ISO/YMD date formats are fixed, and reference text columns use `COLLATE "C"`.
- Base tables include NULLs, empty strings, UTF-8 text with whitespace, and duplicate keys. `pk_items` uses a single bucket and two independent commits, with key 1 updated from `(10,'old')` to `(99,'new')`; metadata must contain at least two commits and two files that actually exist, and the query must return the final three rows.
- Readiness requires completing a protocol query, three fixture queries, and a metrics-port connection. Missing dependencies, early child exit, timeouts, or fixture errors all fail.
- `tokio-postgres::simple_query` validates text; `prepare` / `query` validate extended binary, column names, common type OIDs, and real client decoding. The driver hides simple-query OIDs, so that field is not claimed to be checked.
- Unordered results are compared as multisets, preserving duplicates; ordered results are compared row by row. NULL is not equal to the empty string, text is not trimmed, and integers/DECIMALs do not go through floating-point approximation or benchmark tolerances.
- Controlled startup failures, suite errors, panics, and timeouts all run cleanup: shut down connection tasks, kill + wait for the child process, verify both ports are released, and remove self-created metadata/reference schemas/temporary directories. Metadata cleanup first drops tables recorded by the fixture, then enumerates the namespace's remaining tables from the primary PG's `table_info` (tables created by the service under test are not in that ledger, and phase seven DDL creates exactly such tables), so a failed or interrupted suite leaves no table rows behind either. Failures retain the original error, cleanup errors, and service logs; uncontrolled exits such as a forcibly killed test process rely on the CI outer lifecycle as a backstop.
- Within one integration target, the handoff from port reservation release to child-process readiness is serialized to prevent another suite from selecting a not-yet-bound port; queries from independent suites may still run concurrently. Do not build/overwrite a binary that is starting up in the same Cargo output directory; run the bootstrap test commands serially as described above.

### Phase three · 3.1: storage semantics

The 27 new SQL cases run the same SQL through simple text and extended binary, compare against independent expectations and the PG final relation, preserve duplicate counts, and check column names, binary OIDs, and real decoding. The classification here is **final-relation checking of LakeSoul-specific semantics**, not a claim that PostgreSQL implements LakeSoul's merge/CDC write semantics.

| Storage contract | Consumer-visible error to catch | Specific cases |
| --- | --- | --- |
| Append-only preserves exactly identical rows across files | Erroneous deduplication reducing the bag, group counts, or aggregate values; NULL confused with empty string | `append-duplicate-rows-preserved`, `append-grouped-multiplicity`, `append-aggregate-multiplicity`, `append-empty-label-is-not-null`, `append-null-label-filter` |
| Merge across commits first, then evaluate non-key predicates | Old versions resurrect when the old value satisfies the predicate but the new one does not; key filters return old values or duplicate versions | `merge-superseded-value-filter`, `merge-updated-value-filter`, `merge-key-filter-projection`, `merge-one-latest-row-per-key` |
| Missing columns contribute nothing, explicit NULL overrides; a new key with no contributed value reads as NULL | Treating a missing column as NULL overriding the old value, filling NULL with zero, reading only the newest file; trusting storage NOT NULL causing wrong IS NULL/COUNT(col) | `partial-full-projection`, `partial-null-value-filter`, `partial-not-null-value-filter`, `partial-filter-after-merge-updated-value`, `partial-filter-on-omitted-column`, `partial-aggregate-counts` |
| Primary-key merge within a partition, same key independent across partitions | Erroneous global deduplication, partition value/filter mismatches, historical versions entering cross-partition aggregates or JOINs | `partition-same-key-independent`, `partition-pruned-latest`, `partition-nonkey-filter-after-merge`, `partition-cross-aggregate`, `partition-cross-join` |
| CDC tombstones removed after merge, and a later insert can reinsert the key | Leaking tombstones when the projection omits op; non-key filters resurrecting deleted/updated old rows; wrong delete/reinsert order; wrong aggregate/JOIN counts | `cdc-live-projection-drops-tombstones`, `cdc-deleted-key-key-lookup`, `cdc-non-key-filter-no-resurrection`, `cdc-reinserted-key-exposes-new-value`, `cdc-visible-version-accounting`, `cdc-change-column-groups`, `cdc-join-no-tombstone-leak` |

`tests/support/storage.rs` uses the existing `create_io_config_builder`, the native writer, and `LakeSoulTable::commit_flush_result`, with each write committed independently and awaited. It reads each newly published actual Parquet file, checks the physical column set and the multiset of original input rows, then checks that each partition's latest metadata snapshot spans multiple commits and that all active files really exist. Thus the full columns `(id,v,w)` from a partial update, the missing columns `(id,v)`, and the primary-key-only `(id)` really come from different physical schemas, and SQL INSERT's implicit NULL is not passed off as a missing column. Partition columns are omitted from physical files; their correct values are verified by real queries.

New fixtures are created before startup, and all tables are registered with the existing cleanup immediately; startup failures and suite failures must also clean up the new tables. Both success and failure emit physical proof and cleanup proof. It never waits for the catalog or data to be "eventually correct" by polling the SELECT under test, and it does not substitute full-plan text snapshots for result assertions.

### Phase three · 3.2: namespace → database, user tables fixed to public

The same real service process connects to two independent namespaces: both have `mapping_items`, but with alpha/beta data respectively, and each has a table that exists only in its own database. All namespaces and files are prepared before startup; no new reference PG database is created, the reference side's fixture schema is not treated as the external schema, and cross-database access is not simulated by renaming within a single connection. The following is **LakeSoul-specific catalog semantics**: it asserts results independently determined by fixtures/mapping contracts directly, and does not compare the reference connection's irrelevant `current_database()` or schema identity.

| Contract | Consumer-visible error to catch | Specific cases |
| --- | --- | --- |
| The connected database is the namespace, and the default user schema is public | Wrong identity returned, namespace treated as a schema; existing/new primary connections reading peer data after using a peer | `catalog_mapping_identity_*`, `catalog_mapping_unqualified_*`, `catalog_mapping_qualified_*` |
| Databases are discoverable, schemas do not leak namespaces | `pg_database` missing/duplicating controlled namespaces; `pg_namespace` exposing other user schemas or missing public/pg_catalog | `catalog_mapping_pg_database_primary/peer`, `catalog_mapping_pg_namespace_primary/peer`; the database list filters to its own names to avoid interference from concurrent suites, while the schema list is asserted completely |
| User table/column catalog ownership in the current database is correct | `pg_class` leaking another database's private tables, or a relation OID resolving to the wrong columns in `pg_attribute` | `catalog_mapping_pg_class_public_primary/peer`, `catalog_mapping_pg_attribute_primary/peer`; OIDs are used only in real JOINs, never hard-coded |
| Three-part qualified names work for the current database, and cross-database/namespace-as-schema is unreadable | Impersonating isolation with "all qualified names fail"; reading the other side's same-named or private tables; connection identity corrupted after rejection | `iso-own-catalog-*`, `iso-cross-schema-*`, `iso-cross-catalog-*`, `iso-foreign-unqualified/public-*` |
| search_path cannot bypass database isolation | Reading peer data after putting the peer namespace before public, or a setting leaking to another connection | `iso-search-path-*`; SHOW confirms the setting is recorded, then queries still return own data, the other side's private tables are still rejected, and existing peer/primary settings are unchanged |
| A nonexistent database is rejected at connection startup | Silently connecting to the default namespace, mistaking a transport error for a server rejection, or corrupting existing connections | `iso-unknown-database-startup`, checking the real ErrorResponse `FATAL XX000`, after which primary/peer still read their own data |

Query/catalog results run simple text and extended binary, checking column names, binary OIDs, and actual decoding. Cross-database/missing-table rejections cover simple execution and extended Parse respectively, both checking the current service's SQLSTATE `XX000`; after each rejection, the **first query** directly reads this connection's `public.mapping_items`, without reconnecting or sending a probe query first. This error code and the unknown-database `FATAL XX000` are recorded mapping boundaries, not claims of equivalence with PostgreSQL SQLSTATE.

`tests/support/catalog.rs` verifies that new tables' namespaces and published files really reside in the owned warehouse; the harness tracks the second namespace, every table in it, and all extra connection tasks, using the same normal/failure teardown. The connection helper retains the real `tokio-postgres::Error` source, and the startup SQLSTATE is not guessed from an error string. This only proves default public lookup, catalog ownership, and no-bypass; it does not promise arbitrary user schemas or full search_path resolution compatibility.

### Phase three · 3.3: vector codec, exact fallback, and ANN

`tests/support/vector.rs` creates three tables in its own namespace/warehouse: `vector_values` stores two fixed vectors and one NULL; `vector_plain` and `vector_ann` store the same 64 8-dimensional float32 inputs, and the latter automatically builds a single-bucket, nlist=4, 7-bit, L2, seed=42 index. Before the service starts, it decodes the real Parquet values one by one, resolves the committed header/segment list from the metadata index catalog, reads each segment payload, and checks file size, data-file coverage, 64 vectors, and at least two non-empty IVF clusters. The no-index table requires no shards in the control plane and no index directory on disk; SQL success or a non-empty directory alone is not index proof.

| Contract | Consumer-visible error to catch | Specific cases |
| --- | --- | --- |
| Dynamic vector type and real client codec | Hard-coded OIDs, Describe/catalog mismatch, wrong parameter or result byte format, NULL filled as an empty vector | `vector-type-discovery`, `vector-stored-binary/text`, `vector-indexed-stored-binary/text`; official `pgvector::Vector`; reference PG need not have the extension installed |
| Distance and NULL | Wrong L2, wrong `<#>` sign, cosine missing normalization, any NULL operand becoming a value/raising an error | `vector-distance-binary/text`, `vector-null-literal-binary/text`, `vector-null-stored-binary/text`; independent f64 algorithm over known f32 inputs, absolute tolerance `1e-9` for L2/negative inner product and `1e-12` for cosine, without modifying the common strict comparator |
| Rebinding the same Statement | Explicit `$1::vector(8)` or bare `$1` type inference failure, stale parameters, wrong NULL shape | `vector-parameter-explicit/bare`; two different vectors, NULL, the first vector, distances of actually stored rows, and result decoding |
| Explicit rejection and connection recovery | Mismatched dimensions computed over a common prefix, invalid text accepted, client-side local errors impersonating server rejection | `vector-reject-declared-dim-literal`, `vector-reject-bare-literal-dim`, `vector-reject-malformed-*`, `vector-reject-parameter-dim`, `vector-reject-bare-parameter-length`; the first read after each error directly reads this connection's fixture |

These are independent assertions of **LakeSoul vector protocol and index behavior**, not a diff against a reference PG with pgvector installed. The indexed table's `vec` returns the dynamic vector type directly; a `FLOAT[]` column without index configuration is still float4[], the codec cases explicitly project `vec::vector(8)`, and arbitrary float arrays are not claimed to become vectors automatically. Variable-length columns themselves declare no dimension; tests distinguish Parse/parameter-decoding rejection of explicit `vector(8)` from execution-time length checks for bare parameters. Current planning/execution errors are `XX000`, declared-dimension parameter decoding and invalid probes are `22023`, and not all error codes are claimed to equal pgvector's.

`EXPLAIN VERBOSE` selects only the final `physical_plan` row to inspect local nodes, does not snapshot the full plan, and does not treat logical markers as proof the index executed. Actual query results and changes in probes' candidate coverage together provide execution evidence; SET/SHOW echo is not proof probes took effect. SHOW values are verified in text/extended, and extended Describe also asserts `ivfflat.probes`/`text` consistency with the `Execute` response (`vector-probes-show-describe`); broader `SHOW` metadata is not claimed as verified.

**Scope remains limited:** the above are representative cases, not a compatibility promise for every SQL/type/storage-layout combination. The TPC-H workload below uses separate adjudication rules, and passing it does not imply PostgreSQL equivalence for arbitrary SQL.

### Phase seven: DDL (`CREATE TABLE`/`DROP TABLE`)

DDL is handled by the statement hook in `src/ddl.rs`, bypassing both DataFusion's own DDL planning and admin-side SQL. `CREATE TABLE` constructs a provider with the same `LakeSoulTableProvider::new_from_create_external_table` used internally by the service, then publishes metadata through `SchemaProvider::register_table`; `DROP TABLE` goes through the cascading delete of `SchemaProvider::deregister_table`. The table path is fixed to `{warehouse}/{namespace}/{table}`, and clients do not provide `LOCATION`, so tables in different PG databases cannot land in the same directory. Table and column names are folded to lowercase per PG rules (unquoted); quoted names whose folding would change them are rejected outright: the provider itself folds schema, column names, and `table_info.table_name`, so accepting such names would mean a silent rename, while `table_info`'s `partitions`, `table_path`, and subsequent reads/writes all depend on that single identity.

`PARTITIONED BY` is this service's LakeSoul SQL extension: it partitions by the values of existing columns, not PostgreSQL declarative partitioning:

```sql
CREATE TABLE partition_items (
    part INTEGER NOT NULL,
    id BIGINT PRIMARY KEY,
    val TEXT
)
PARTITIONED BY (part)
WITH (hash_bucket_num = 4);
```

Multiple partition columns are supported, with declaration order preserved; partition columns and primary keys are declared separately, `hash_bucket_num` controls hash bucketing within each partition, and global primary-key uniqueness across partitions is not promised. Omitting `file_format` still uses `vortex-compact`. No PG child tables or partition bounds are created, and client `LOCATION`/`STORED AS` is not exposed.

Semantic boundaries (LakeSoul-specific; PG equivalence is not claimed):

- Primary-key tables are merge-on-read. A plain `INSERT` is insert-only, and a duplicate key raises an error rather than PG's "delete then insert"; `ON CONFLICT DO NOTHING` filters conflicting rows on the sink side. The existing "all columns + each column `= EXCLUDED.col`" form of `ON CONFLICT DO UPDATE` still maps to a whole-row replace; the general partial-column, old-value/`EXCLUDED` expression, and conflict-`WHERE` forms use the new read-modify-write planner in §10, with the boundaries in "General UPSERT (pending acceptance)".
- A range-partitioned table's primary key is unique only within a partition; PG's plain `INSERT` allows the same key in different partitions, but a duplicate key within the same partition is still `23505`. PG `ON CONFLICT` on partitioned tables is currently still `0A000`; the cross-commit merge above is verified via backend `INSERT OR REPLACE` and cannot be taken as evidence that PG partitioned-table upsert is supported.
- One statement on a non-PK range-partitioned table may write multiple partitions. The commit puts all `DataCommitInfo` into one PostgreSQL transaction and publishes all partition versions at once; readers see only the whole statement. Parquet files are written to object storage before metadata; a failed or cancelled statement (including a metadata publication failure) deletes this run's attempted files, and orphan files left by a process crash are handled by GC—the file layer is not atomic.
- Cancellation: if the result stream is dropped before the commit starts, nothing is published and files are cleaned up; once metadata commit has begun it cannot be interrupted (single transaction, millisecond scale).
- Concurrent write conflicts: when snapshot validation finds a partition version advanced by another writer, `40001` is returned (retryable) rather than `23505`—at this step LakeSoul cannot distinguish "same-key conflict" from "any concurrent commit", and the client only gets `23505` after retrying. An indeterminate commit result (`InsertCommitOutcomeUnknown`) remains server-side `XX000`, and files are retained.
- Post-commit maintenance failure: if automatic vector/text index construction fails after a successful metadata commit, the statement still returns an error, but the rows are already committed and visible. Clients must not treat such a failed INSERT as not having taken effect.
- `ON CONFLICT DO UPDATE` with the source repeating the same primary key is judged row by row by "does the later input hit a row this command already inserted or updated": a hit gives `21000` (`ON CONFLICT DO UPDATE command cannot affect row a second time`) and publishes nothing for the whole statement; the check precedes the later row's own conflict `WHERE`, but a row skipped by an earlier `WHERE` and therefore unmodified can be updated by later input. `DO NOTHING` still discards duplicate rows without error, like PG. Acceptance status and boundaries for the first delivery are in "General UPSERT (pending acceptance)".
- Transactions: DataFusion has no transactions, so `INSERT` inside a `BEGIN` block or inside a simple-query multi-statement batch is always `0A000`, preventing clients from assuming `ROLLBACK` can undo it.
- `RETURNING` is not supported yet: the sink commits at the end of the statement and there is no row stream to feed back.
- Source analysis: before planning, the source is checked per PostgreSQL semantics. When the number of expressions in an explicit column list differs from the list, or a column-list-less `VALUES`/`SELECT` is wider than the table, the result is `42601` (`more expressions than target columns`); when an explicit column list is wider than the source, `42601` (`more target columns than expressions`); when a column-list-less `VALUES` or `SELECT` is narrower than the table, NULLs are appended per PG default-value semantics (there is currently no `DEFAULT`, so NULL is appended). Untyped literals and typed expressions are handled separately: bare literals in `VALUES` rows and in `INSERT ... SELECT` projections are resolved against the target column, with string literals converted and failure as `22P02` (`invalid input syntax for type ...`); typed expressions such as numeric/boolean literals, function and `CAST` expressions, and column references in `SELECT` projections are checked against the PG assignment cast matrix, with violations as `42804` (`column "c" is of type X but expression is of type Y`). The matrix covers within numeric families and numeric→string, boolean→boolean/string, text→text, within date/timestamp families and →string, and bytea→bytea/string; unlisted source types are always `42804`. String length overflow (`22001`) and varchar(n)/char(n) length validation are out of scope; when a `SELECT` projection contains a `*` wildcard, column positions cannot be mapped from the AST, so that case falls back to planning-time type checking and does not claim full equivalence with PG's untyped-literal rules. This analysis does not change `SELECT` expression conversion: `SELECT 'abc'::int` remains the recorded `XX000` mapping boundary (see the "Error mapping" row in phase two). Duplicate primary keys within an upsert statement produce `21000` when a later input hits a row this command already inserted or updated; see "General UPSERT (pending acceptance)".

#### General UPSERT

The general form of `ON CONFLICT ... DO UPDATE` is planned by `lakesoul-datafusion::planner::upsert` and shares the fixed primary-database snapshot and exact-version publication with UPDATE; `insert.rs` only analyzes and infers parameter types at Parse, then re-checks the target identity, binds this execution's parameters, and captures the snapshot at Execute. `tests/upsert_contract.rs` and the native `tests::sql_upsert_tests` are this section's regressions; legacy/v2, simple/extended, local and real dual-Flight-worker (fallback disabled), and vector/text index scenarios have all been exercised, with evidence and the matrix in `.plans/update-upsert.md` §10.9. Unlisted shapes are still rejected with `0A000` or an existing SQLSTATE.

First-delivery boundaries (code facts; the regressions are this section's matrix and the native `tests::sql_upsert_tests`):

- The target must be a LakeSoul table that is non-CDC, has a primary key, is not range-partitioned, uses overwrite-style merge, and is not `appendOnly`; `SET` cannot modify primary-key or partition columns (`0A000`).
- Partial `INSERT` column lists and partial `SET` are supported: unassigned columns keep the old row, and an explicit `NULL` overrides. `EXCLUDED` is the complete would-be inserted row after the existing INSERT padding rules, not just the explicitly listed columns.
- `SET` and conflict `WHERE` support constants, old values, `EXCLUDED` expressions, and multi-column assignments against the same old row; same-value updates still count, a conflict `WHERE` that is false/NULL skips the row without counting, and new keys are not filtered by that `WHERE`. A bare string literal written directly (optionally parenthesized) in a conflict `WHERE` is treated as PG `unknown` and evaluated in boolean context (`'true'`/`'false'` take effect, invalid spellings are `22P02`); an explicit `::text` is still `42804`. Compound expressions containing a bare literal (e.g. `NOT 'true'`) are still reported as typed expressions with `42804`.
- Name binding follows PG: a target alias replaces the original name (the original name is `42P01`), bare-column ambiguity is `42702`, a qualified `SET` target is `42703`, omitting the `DO UPDATE` conflict target is `42601`, and a table without a primary key is `42P10`.
- The source executes once; an explicit source `ORDER BY` decides duplicate-key order. If a later input hits a row this command already inserted or updated, `21000` is raised first (even if that later row's `WHERE` is false); a row that was skipped and left unmodified can still be updated by later input. A failure publishes nothing for the whole statement. Whenever the source can observe expression types (`DISTINCT`, `UNION`/`EXCEPT`/`INTERSECT`, `ORDER BY`, `LIMIT`), assignment conversion runs only on the rows read out, and inside the source only PG `unknown` values (string literals, `NULL`, `$n`) are typed against the target column; for example, a numeric source sorts numerically before writing to a `TEXT` column, and duplicate keys are detected only after deduplication. A plain `VALUES` list without those semantics keeps per-value typing against the target column (PG likewise coerces each row expression; the list itself does not deduplicate or sort).
- Incoming-row type/NOT NULL validation precedes the conflict action (even when the row is ultimately skipped by `WHERE`); output-row constraints are checked only when that row is actually produced, and a late failure rolls back the whole statement.
- Prepared statements do not reuse the data snapshot from Parse; Execute resolves the catalog once and compares the captured `table_id` with the Parse-time target, returning `42P01` after another connection's DROP/same-name recreation and never publishing to the new `table_id`.
- Known limitation: `$n` in `VALUES`/`SELECT` gets its parameter type from the target column's PostgreSQL type spelling; vector, time (`Time32`/`Time64`), interval, and other columns without that spelling still report an `unknown` parameter type at Parse. Plain INSERT infers these types through DataFusion's INSERT planning; general UPSERT does not reuse that path (it rejects the existing shape where a derived `VALUES` has more columns than the target).
- Deliberate differences: modifying the conflict key is `0A000` (PG allows it); a non-primary-key conflict target is `0A000` (PG `42P10`); range-partitioned tables with `ON CONFLICT` are `0A000`; CDC tables keep only the existing "all columns `EXCLUDED`" form, and the general old-value form is `0A000`; `RETURNING`, `appendOnly`, explicit transactions, and multi-statement write batches remain rejected.
- Concurrency granularity is the range-partition version (the table's single partition when there is no range): a concurrent writer advancing the version returns `40001`, and the client must retry the whole statement; PG row locks are not promised. An empty source, or one where every conflict `WHERE` skips, is `INSERT 0 0` and produces no files or metadata publication.
- Index maintenance follows INSERT's post-commit policy; `indexed_upsert_contract` in `tests/upsert_contract.rs` covers the vector/text scenarios, and the native `tests::sql_upsert_tests` cover concurrency and memory scenarios.

#### Distributed INSERT

With worker discovery configured, `INSERT ... SELECT` uses the same automatic stage partitioning as queries; without workers or when explicitly entering local planning fallback, the single-node path is used. Distribution does not change the PG conflict semantics above, nor does it mean every statement is parallel: `VALUES`, global aggregates/LIMIT, and similar remain constrained by existing task placement.

```text
source query → worker LakeSoulWriteExec → Arrow file reports
                                     ↓
          coordinator LakeSoulCommitExec → one metadata publication → index maintenance → INSERT 0 n
```

- Workers only write files and do not connect to the LakeSoul metadata service. The primary key's existing-key scan captures one complete snapshot during coordinator planning and ships it as a nested physical plan with the write node, with each worker validating it independently in a streaming fashion; snapshot version comparison and publication happen only on the coordinator.
- Network hash ensures the same key goes to the same worker; workers then sort and generate persistent buckets with LakeSoul's original hash. DataFusion network partition numbers must not be treated as LakeSoul buckets. The number of write tasks need not equal `hashBucketNum`: each task can write multiple persistent buckets; multi-task file names include a task suffix to avoid overwrites.
- Workers preserve typed unique-key/NOT NULL errors in reports, and the coordinator restores `23505`/`23502`; losing the snapshot race during primary-key publication is still `40001`. `n` is the sum of rows across all successful file reports, with Skip counting only actually inserted rows.
- If any report stream fails, nothing is published; the coordinator drains the remaining reports, cleans up this statement's files, and looks up not-yet-reported files by statement id. Pre-commit cancellation of a healthy worker is also cleaned up; when the report channel disconnects, the write task stops all writers and cleans up itself. Worker/coordinator process crashes can still leave orphan files, handled by GC. When the commit result is indeterminate (connection interruption), whether it was published is determined only on the primary database by commit id; on query failure, files are retained as "possibly published".
- The current unpublished protocol is codec `2` (`lakesoul-distributed/2`; `lakesoul-distributed/2-ivm` with the `ivm` feature): general UPSERT adds the `UpsertExec` wire encoding after the IVM/external-file codecs and explicitly encodes the source-order column as a physical ordering requirement. The protocol is still in development, so the same number covers every unpublished build: the coordinator and workers must use the same build and be updated/restarted together. **Do not bump the codec version during development**: append new codecs to the end of the list and keep `2`; bump only once the protocol is released and cross-deployment compatibility is required. Discovery cannot distinguish different development builds that share this number, and a static worker list only probes versions when the resolver is built or updated.

### Phase nine: UPDATE

`src/update.rs` takes over PG simple and extended Parse/Execute; the shared implementation lives in `lakesoul-datafusion::planner::update`. It supports only LakeSoul tables that are **non-CDC, have a primary key, are not appendOnly, and use overwrite-style merge**; an explicit `UseLast` is equivalent to the default overwrite-style merge. Range-partitioned tables can be updated, but primary-key and partition columns cannot appear in SET. An ordinary data column that happens to be named `op`/`rowKinds` does not turn a table into CDC.

```sql
UPDATE counters
SET n = n + 1, label = NULL
WHERE id = 1;
```

- All SET expressions read the same old row; unassigned columns keep their old values, and explicit NULL overrides. WHERE is evaluated on the current relation after primary-key merge and cannot update historical versions; WHERE is not required to mention keys or partition conditions. Without WHERE, all current rows are updated.
- Expressions reuse existing SELECT capabilities: equality-correlated and uncorrelated scalar subqueries can be used in assignments, and a multi-row scalar result is `21000` and publishes nothing. Non-equality correlated scalar subqueries that SELECT itself does not support (e.g. correlation `src.id > dst.id`) are out of scope for this extension and are not faked as supported via LIMIT 1/NULL rewriting. Write plans that still contain runtime subqueries execute as a single coordinator plan, so their shared result/cardinality state and errors are not split across different worker write tasks; ordinary UPDATEs already decorrelated into joins still use the distributed write stage, and the configuration semantics of `fallback_to_local=false` are unchanged.
- The success tag is `UPDATE N`; same-value assignments still count as matched rows, and zero matches returns `UPDATE 0` without producing files or a publication.
- Old files are not modified in place. A new version of the complete new row is written while old active files are retained, and the current relation is obtained through the existing merge-on-read; the commit uses AppendCommit and does not automatically generate CDC events.
- Each Execute re-checks the target identity, schema, and table properties on the primary database and captures a fixed partition snapshot. A prepared statement does not reuse the data snapshot from Parse; an old UPDATE binding after another connection's DROP/same-name recreation returns `42P01` and cannot write to the new table_id.
- The commit compares exact versions of affected partitions and publishes multiple partitions atomically in one step. A conflict returns `40001` without silently rebasing after refreshing head and without automatic retry; the client must retry the whole statement. The validation granularity is the whole range partition, or the table's single partition when there is no range; PG row-lock concurrency capabilities are not promised.
- CDC (including empty tables, WHERE false, and explicit SET of the change column), no primary key, appendOnly, non-overwrite merge-op, modifying primary-key/partition columns, RETURNING, UPDATE FROM, explicit transactions, and multi-statement write batches are unsupported. Data-modifying CTEs are explicitly rejected by the statement guard as `0A000`, so DataFusion planning gaps are not exposed as internal errors and unsupported transactional behavior is not disguised.
- CAS publication and single-table DROP share/exclusive-lock the same `table_info` row; single-table cascading metadata deletion completes in one transaction. This guarantee does not extend to global serialization of generic commit_data writes, multi-table DROP, or GC/read leases.
- File generation precedes publication, and only files explicitly known to be unpublished may be cleaned up. Index maintenance follows INSERT's post-commit policy: a maintenance error does not mean data rollback, and data files must not be deleted when publication succeeded or the commit result is unknown.

`tests/update_contract.rs` contains a protocol behavior matrix shared between local and dual-Flight-worker runs, plus retrieval contracts for UPDATE after real vector/text indexes are pre-built. Default exact reranking must not return old versions; index-only mode still follows the existing approximate-retrieval semantics and does not promise immediate deletion of historical index entries. There is also a real index-write failure case: the client receives a maintenance error, but the new value is committed and other rows and committed data files are retained. `tests/session_contract/readonly.rs` keeps the no-primary-key rejection and verifies that supported UPDATE is no longer blocked by the blanket guard.


Concurrency cases use real object-store gates/metadata locks to create interleavings, not sleep-based collisions; they check versions, all commit records, actual files, and the final relation.
