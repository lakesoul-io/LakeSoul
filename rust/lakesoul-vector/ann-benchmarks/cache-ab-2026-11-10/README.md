# 四数据集 ANN 缓存/参数基准（2026-11-10）

## 1. 实验目的

重新测试 SIFT-128、GloVe-200、GIST-960、Deep-Image-96（9.99M）四个数据集：

- 索引构建时间、构建 RSS；
- recall@100；
- 搜索 QPS / 平均延迟 / first latency / RSS；
- `nlist`、`nprobe`、`nbits` 不同组；
- index-only 与 exact；
- 缓存开启/关闭；
- 单查询与 native batch。

所有表在 MinIO 上端到端测试；每个数据集测试完成后立即 drop 表、删除 S3 前缀和本地 cache，避免磁盘累积。

## 2. 数据与距离

| 数据集 | 行数 | dim | 距离 | 处理 |
|---|---:|---:|---|---|
| sift | 1,000,000 | 128 | Euclidean | L2 |
| glove | 1,183,514 | 200 | angular/cosine | train/test 逐行 L2 归一化 + IP |
| gist | 1,000,000 | 960 | Euclidean | L2 |
| deep | 9,990,000 | 96 | angular/cosine | train/test 逐行 L2 归一化 + IP |

查询：SIFT/GloVe/GIST NQ=100（缓存开启）/NQ=20（缓存关闭）；Deep NQ=50/20。
top_k=100，exact_overfetch=1，4 个 hash bucket。


> **RSS 测量说明（重要）**：本报告 `raw/` 中的搜索 RSS 来自旧版
> `search2.py`，脚本在搜索进程里同时保留了完整 `train` 数组（GIST/Deep 各
> 3.84 GB）。因此 raw 中的 GIST/Deep RSS 包含 **3.8 GB 的 base 数据**，不是纯粹
> 的查询 cache RSS；SIFT/GloVe 也分别包含 0.52/0.95 GB。新版脚本已 `del train`，
> 后续重测应使用 `VmRSS_after - baseline` 或 `VmHWM` 减去 base 数据占用。

## 3. 缓存配置

缓存开启：

```bash
LAKESOUL_VECTOR_CACHE=1
LAKESOUL_VECTOR_MEMORY_BYTES=8GiB
LAKESOUL_CACHE_PATH=<fresh per run>
LAKESOUL_CACHE_SIZE=16GiB
LAKESOUL_VECTOR_LAZY_INDEX=auto
```

缓存关闭：`LAKESOUL_VECTOR_CACHE=0`。exact 在无 L2 时回退 reader；batch exact
在缓存关闭时通过 table fallback 逐 query SQL 执行（结果正确但慢）。

每次搜索使用独立进程和独立 cache 目录；构建索引时缓存关闭，构建 RSS 为
`VmHWM`，搜索 RSS 为当前进程 `VmRSS`。

## 6. 主要观察

1. **构建**：Deep-Image 的 nlist=4096 构建约 220–230 s、RSS 3.6–3.8 GB；nlist=1024 约 66–74 s。GIST-960 的构建 RSS 约 3.0–3.3 GB，主要受宽向量影响。
2. **recall**：nbits=7 明显高于 nbits=1（例如 SIFT nprobe16 从 ~0.61 到 ~0.89；GIST 从 ~0.69 到 ~0.80–0.93）；exact 在相同候选集上进一步提高 recall。
3. **QPS**：单查询 index 在 SIFT/GloVe 约 180–260 QPS，GIST 约 60–160 QPS，Deep 约 36–131 QPS；batch 显著更高（SIFT 可达 ~7k，Deep 可达 ~1.6k）。
4. **exact**：SIFT/GloVe exact batch 可达 1–3k QPS；GIST-960 exact 约 12–14 QPS 单查 / 400–600 QPS batch；Deep exact 约 6–9 QPS 单查 / 130–600 QPS batch。
5. **缓存关闭**：index 单查约 38–60 QPS（每次加载），exact 单查约 0.4–2 QPS，exact batch fallback 约 0.4–2 QPS；说明缓存对 exact 是数量级影响。
6. **RSS**：缓存开启时 L1/L2 预算 8 GiB + 16 GiB 使 GIST/Deep 的 exact RSS 达 7–9 GB；关闭缓存后 RSS 显著低，但 QPS 大幅下降。
7. **first latency**：lazy cluster 首次加载要读取 cluster centroid；Deep nlist=4096 首次 index 查询可达 ~30 s，后续 warm QPS 才回升；这是 directory 未持久化的代价。

## 7. 与之前结果的关系

- 上一轮 Deep-Image 单查 index 2.5 QPS（整 shard 加载）→ 本轮 cache-on/lazy 约 40–130 QPS（nlist/nprobe 不同）；说明 cluster-lazy 已实际生效。
- GIST-960 的 exact 仍受 960 维 block 读放大限制；index batch 高，exact batch 低。
- 本轮统一使用 5 个公共缓存变量，旧变量没有进入 benchmark 配置。

## 8. 限制

- cache-on 每次使用 fresh 目录；first latency 包含冷 cache/centroid 初始化，warm QPS 是主要比较项；
- cache-off 的 NQ=20，batch exact 是 SQL fallback，不代表 native exact；
- 每个数据集完成后已释放 table/S3/cache，原始结果见 `raw/`；
- 同一进程只测一个 cache 模式；切换模式使用新进程；
- GIST/Deep 的精确结果受 candidate recall 与 block 读共同影响，不能只看 QPS。

## 9. 复现

脚本见 `scripts/`，运行：

```bash
./scripts/run_one.sh sift
./scripts/run_one.sh glove
./scripts/run_one.sh gist
./scripts/run_one.sh deep
```

每个脚本完成 setup → 4 个 build 配置 → 8 个 search 配置 → drop/S3/cache 清理。
