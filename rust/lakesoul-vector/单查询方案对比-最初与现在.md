# 单查询（SQL 向量检索）方案对比：最初 vs 现在

> 适用场景：`select id from tbl order by array_distance(vec, ARRAY[...]) limit 100`，
> session 设置 `lakesoul_vector_search.rerank = 'index'`（index-only 排序）。
> 基准：GloVe-200，1,183,514 条 base / 200 条真实 query / 200 维 / nlist 1024 / **nbits=1** /
> nprobe 16 / top_k 100 / 4 个 hash bucket / KVM 虚拟机（8 物理核 16 逻辑核，AVX-512）/ 构建与搜索分进程。
>
> 所有数字均为本仓库实测（记录见 `向量查询优化日志.md` R1–R38），未做任何"改 SQL/改数据"的取巧。

---

## 0. 一句话结论

最初的单查询是 **"通用 DataFusion 规划 + reader 读数据文件做精确重排"**；
现在是 **"analyzer 里把查询折成句柄 → 索引直达扫描（limit）"**，
中间所有"为这次查询搭建读路径 / 读 payload / 排序"的工作都被移除了。

| 指标 | 最初 | 现在（HEAD） | 提升 |
|---|---:|---:|---:|
| 单查询 QPS（顺序） | **61.3** | **~526**（500 / 521 / 531 / 545） | **8.6×** |
| p50 延迟 | **16.0 ms** | **1.78 ms**（1.71–1.88） | **9.0×** |
| CPU / query | **41.5 ms** | **2.4 ms** | **17×** |
| 查询期 RSS | **339 MB** | **232 MB** | −32% |
| Recall@100 | 0.42035 | 0.42035 | 不变 |
| 并发吞吐 c=4 / c=8 / c=16 | 未单独优化（c=8 约 831*） | 1,209 / 2,055 / 2,368 | 2.5× @c=8 |

\* c=8 的 831 QPS 是元数据客户端读并发化（R36）之前、其它改动全部生效时的实测值。
批量入口（快照批量 API）不在本对比范围内，改造前后为 11.4–12.1k QPS（200 query）/ 13.3–14.2k（10k query）。

## 1. 最初的方案（baseline）

### 1.1 每一条语句做的事情

```
SQL 文本（含 200 个浮点字面量）
  │
  ├─[parse] sqlparser：AST（ARRAY[200 个字面量]）                      ~0.21 ms
  │
  ├─[analyze] name resolution
  │    └─ catalog.table()：PG 查表信息 + **每次新建 LakeSoulTable / Provider**
  │         （解析 Arrow IPC schema、properties、partitions、建 IOConfig、初始化 format）
  │    └─ SqlToRel：ARRAY[...] → Expr::make_array(200 个 Expr)           ~1.17 ms
  │
  ├─[logical optimizer] 默认 25 条规则 × 多轮
  │    └─ plan：GlobalLimit → Sort(array_distance(vec, ARRAY[200])) → Projection → TableScan
  │                                                                      ~0.35–0.82 ms
  │
  ├─[physical planner] DataFusion 默认 planner
  │    └─ 逐节点转换 + 一整轮物理优化器（插 CooperativeExec 等）          ~1.15 ms
  │
  └─[exec] LakeSoulVectorSearchExec —— **reader 路径**                   ~13–15 ms
       ├─ 解析索引 commit（PG 往返）
       ├─ 装载各 bucket 分片索引（每次查询）
       ├─ 为每个 bucket 建 reader 配置：打开数据文件、读 schema、
       │    merge-on-read 的 mutation 链检查
       ├─ ANN probe 4 个 bucket（串行）
       ├─ **回读数据文件里的向量列做精确重排（exact re-rank）**
       ├─ 按精确距离排序
       └─ 再读 id payload 输出
```

### 1.2 根因（为什么慢）

1. **每语句重复做"搭建"**：provider、reader、索引分片、文件列表都没有跨语句复用；数据文件明明不可变，同一快照的重复查询仍从头来过。
2. **读路径太重**：为了返回 `id`，先读向量列做精确重排、再读 payload；而用 `rerank='index'` 时排序只依赖索引距离，根本不需要读向量列。
3. **排序在 DataFusion 里做**：`Sort` 算子要先把候选行物化再排，代价随候选数增长。
4. **plan 里带着 200 维向量**：analyzer/optimizer 每轮遍历、签名、不变量检查都要走 200 个表达式节点（或 2.6 KB 的 CSV 字符串）。
5. **通用 planner 对该语句是纯开销**：这条语句的最终形状是确定的（Limit + 向量扫描），逐节点转换和物理优化器不产生任何收益。
6. **进程级互斥**：元数据客户端用一把 `Mutex` 把所有元数据查询（含纯读）串行化，并发语句排队。

## 2. 现在的方案（HEAD）

### 2.1 每一条语句做的事情

```
SQL 文本
  │
  ├─[parse]                                                              ~0.21 ms（未变）
  │
  ├─[analyze]
  │    ├─ catalog.table()：**仍然每语句读 PG 最新表信息**（新鲜度语义不变）
  │    │    └─ provider 按「表信息 + catalog options 指纹」复用（变了才重建）
  │    └─ analyzer 规则 FoldVectorQueryLiterals（插在 TypeCoercion 之前）：
  │         array_distance(col, make_array(200 字面量))
  │           → __lakesoul_vector_distance(col, '@q<hex>', 'L2')   ← plan 里只留 8 字节句柄
  │         向量存进程内 registry（4096 FIFO）；该 UDF 求值委托内置 array_distance，语义等价
  │                                                                      ~0.60 ms
  │
  ├─[logical optimizer]
  │    └─ VectorSearchPushdownRule 认出整条形状：
  │         Limit → Sort(distance) → [Projection/Filter]* → TableScan
  │       改写成：Limit(fetch) → TableScan(projection=PK, filters=[marker], fetch)
  │       **Sort 节点消失**（index 排序下索引返回即有序）                 ~0.20 ms
  │
  ├─[physical planner] LakeSoulQueryPlanner 快路径
  │    └─ 形态完全匹配 → provider.scan() + GlobalLimitExec，跳过默认 planner
  │       （两道保险：计划树必须含 VectorSearchExec、输出 schema 必须一致，否则回退）
  │    └─ list_files_for_vector_scan：1 次分区信息 PG + 版本键的文件列表缓存
  │                                                                      ~0.19 ms
  │
  └─[exec] index-only 直返（~0.36–0.44 ms）
       ├─ 快照身份（store + 文件列表 + 检索列）命中 → resolve 0.0 / load 0.005 ms
       ├─ 4 个 bucket 并行 probe（ANN，各 1 线程；这是现在的下限 ~0.30 ms）
       ├─ 去重 → select_nth 取前 top_k（100/800）→ 只解码这 100 个 key（0.06 ms）
       └─ 直接输出 PK 组成的 Arrow batch —— 不读数据文件、不读 payload、不做 exact re-rank
```

### 2.2 为什么现在快（原理）

1. **索引序 = 结果序**：`rerank='index'` 下索引返回的行本就按索引距离有序，`Sort` 与"精确重排"都是多余工作，直接消掉。
2. **PK 即答案**：投影只有主键时，索引 key 解码就是答案，完全不需要读向量列/payload/merge-on-read。
3. **缓存粒度对齐不可变性**：数据文件不可变 → 用"快照身份"缓存分片、用版本缓存文件列表、用 commit_id 缓存 view。"最新快照"的读取点只有两次 PG 查询，其余全部命中缓存。
4. **plan 保持最小**：200 维向量 → 8 字节句柄。optimizer 的不变量检查、plan 签名、每轮规则遍历都与 plan 大小线性相关，实测这一项就值 ~0.15 ms/语句。
5. **跳过对目标形状无收益的通用流程**：fast physical plan 把该语句的物理规划从 1.15 ms 压到 0.19 ms，且用两道校验保证绝不误伤其它语句。
6. **读并发化**：元数据读之间无依赖，`RwLock` 让并发语句的读重叠；写仍独占（比原来更强）。
7. **内存有界**：批量分块（1024/块、最多 2 块在飞）+ 只解码 top_k，避免为最终被 LIMIT 丢掉的行做工作。

## 3. 逐项改进清单（改了什么 / 为什么 / 收益 / 提交）

### 3.1 规划层：每语句固定开销 ~2.4 ms → ~1.35 ms

| # | 改了什么 | 为什么改 | 实测收益 | 提交 |
|---|---|---|---|---|
| R26 | 物理规划快路径：形状匹配时 `provider.scan()` + `GlobalLimitExec`，跳过默认 planner 的逐节点转换与物理优化器；含计划树/schema 双重校验，不匹配即回退 | 该形状的物理计划是确定的，通用流程纯开销 | 345 → 362 QPS（+4.9%），planner 1.15 → 0.24 ms | `f5ade7a2` |
| R27 | 表 provider 按「表信息 + catalog options 指纹」缓存复用；**表信息仍每语句从 PG 读** | provider 构建（解析 schema/properties/IOConfig/format 初始化）0.183 ms/语句，且完全由表元数据决定 | 360 → 392 QPS（+8.9%） | `f5ade7a2` |
| R30 | analyzer 规则在 `TypeCoercion` 之前把 `make_array(全字面量)` 折叠成单个列表字面量 | 200 个元素表达式让 optimizer 的第一遍遍历/不变量检查变贵；对已改写小 plan 再优化只要 0.03 ms | **388 → 488 QPS（+26%）**，optimizer 0.82 → 0.31 ms | `32193fe9` |
| R32 | 进一步在 analyzer 把字面量换成**句柄**（内部距离 UDF `__lakesoul_vector_distance`），向量存进程 registry；UDF 求值委托内置函数 | plan 里留 2.6 KB 字面量仍让 optimizer 的规则前处理变贵（200 维 vs 2 维差 0.16 ms） | 506 → 522 QPS（+3.2%），physical planner 0.501 → 0.413 ms | `1645bc9d` |

### 3.2 执行层：~13–15 ms → ~0.36–0.44 ms

| # | 改了什么 | 为什么改 | 实测收益 | 提交 |
|---|---|---|---|---|
| R17 | **index-only 直返**：投影恰为主键 + index 排序时，直接用索引 key 解码输出，不开 bucket reader、不读数据文件、不做 exact re-rank | 用 `rerank='index'` 时精确重排与 payload 读取全是浪费 | 主要耗时来源被整体移除（61 → 300+ QPS 量级） | `f9fd6457` |

| 阶段 | 最初 | 现在 | 变化原因 |

## 5. 数据流对比（ASCII）

**最初**

```
SQL → parse → analyze(每次建 provider) → 200 字面量进 plan → 默认 optimizer
    → 默认 physical planner → VectorSearchExec(reader 路径)
        → PG 解析 commit → 装载 4 个分片索引 → 建 reader 配置(开文件/读 schema/mutation 链)
        → ANN probe(串行) → 读向量列 exact re-rank → Sort → 读 payload → 输出
```

**现在**

```
SQL → parse → analyze(provider 按指纹复用；向量折叠成 8 字节句柄)
    → optimizer(规则把整条语句改写成 Limit + 索引扫描，Sort 消失)
    → planner 快路径(provider.scan + GlobalLimitExec；1 次分区 PG + 版本缓存)
    → VectorSearchExec(index-only 直返)
        → 快照身份命中缓存(resolve 0 / load 0.005ms)
        → 4 bucket 并行 ANN probe(~0.30ms)
        → 去重 + 部分排序 top_k + 只解码 100 个 key(~0.06ms)
        → 输出 PK batch
```

## 6. 未改变的原始特性与正确性证据

- **快照语义不变**：每条语句仍从 PG 读**最新**表信息与分区版本；没有引入 TTL/记忆化、没有移动"读取点"。
- **数据层不变**：表数据不可变、merge-on-read、分区/哈希桶、时间旅行、索引结构（IVF + RaBitQ、nbits=1）全部未动；文本/ES 索引路径与普通 `list_files_for_scan` 语义未动。
- **结果不变**：单查询 Recall@100 全程 **0.42035**；10k 自查询集 0.43784；exact-rerank 模式下"句柄改写"与"内联字面量"两种实现 Recall **完全相同**（0.64015），单测验证求值误差 < 1e-12。
- **测试**：`lakesoul-io --lib` 192 项、`lakesoul-datafusion --lib` 192 项全绿；
  `lakesoul-metadata --lib` 23/24（唯一失败为既有的 `jwt::tests::test_verify_token_expired`，
  其硬编码 token 于 2026-11-06 04:56 UTC 过期，与本工作无关）。

## 7. 实测过但被证伪并回滚的实验（避免重复踩坑）

| 实验 | 预期 | 实测 |
|---|---|---|
| pushdown 规则前置（插到 optimizer 最前） | 后续规则不再遍历大表达式 | optimizer 0.313 → 0.326 ms，无变化（已核实规则顺序生效） |
| marker 只携带 query 句柄（改写时生成） | 缩小 plan 载荷 | 494 vs 500 QPS，无收益（成本在规则**前**处理，句柄生成太晚） |
| 缓存 Arrow IPC schema 解析 | 省 30–50 µs | 实测解析仅 0.009 ms，不值得 |
| 关闭池 metrics | 省 checkout 开销 | `pool.get()` 0.068 → 0.096 ms（无改善） |
| 自适应 probe 线程数（并发时降为 1–2） | 提高总吞吐 | c=4/8/16 全部略差（1,185/1,985/2,396） |
| PG 连接池 8/32/64 | 减少排队 | 与默认 16 持平或更差 |
| `search_parallelism` = 2/4/8 | 单查询用更多核 | QPS 520 → 498 → 490 → 489，变差 |
| 元数据"专用连接" | 省 2×0.067 ms | 未实施：共享语句缓存跨连接使用有失效风险，收益/风险不匹配 |
| 元数据 prefetch / TTL | 省 0.36 ms/语句（+20%） | 需改变新鲜度口径，未经批准未实施 |

## 8. 复现方式

```bash
# 基准 harness（构建与搜索分进程；单查询用 200 条真实 query，批量用 10k 自查询集）
cd /tmp/lakesoul-vector-query-opt-20261105
SPLIT_BENCH=vector_rebuild_bench_new SPLIT_BITS=1 SPLIT_CONFIGS="0,0,0,0" \
  SPLIT_TAG=single python3 run_glove_split.py          # 单查询
SPLIT_BENCH=vector_rebuild_bench_new SPLIT_BITS=1 SPLIT_CONFIGS="auto,auto" \
  SPLIT_TAG=batch200 python3 run_glove_split.py        # 批量 200
SPLIT_QUERIES=10000 SPLIT_QUERY_FILE=.../glove-query-10k.fvecs \
  SPLIT_GT_FILE=.../glove-gt-10k.ivecs \
  SPLIT_BENCH=vector_rebuild_bench_new SPLIT_BITS=1 SPLIT_CONFIGS="auto" \
  SPLIT_TAG=batch10k python3 run_glove_split.py        # 批量 10k
SPLIT_CONCURRENCY=8 SPLIT_BENCH=vector_rebuild_bench_new SPLIT_BITS=1 \
  SPLIT_CONFIGS="0" SPLIT_TAG=c8 python3 run_glove_split.py   # 并发
```

**A/B 开关**（默认全开，置 0 关闭以便对照）：

| 环境变量 | 作用 |
|---|---|
| `LAKESOUL_VECTOR_INDEX_ONLY=0` | 关闭 index-only 直返，回到 reader 路径 |
| `LAKESOUL_VECTOR_SNAPSHOT_CACHE=0` | 关闭快照分片缓存 |
| `LAKESOUL_VECTOR_FAST_PLAN=0` | 关闭物理规划快路径 |
| `LAKESOUL_TABLE_PROVIDER_CACHE=0` | 关闭 provider 复用 |
| `LAKESOUL_FOLD_VECTOR_LITERALS=0` | 关闭 analyzer 字面量折叠/句柄化 |
| `LAKESOUL_DISTANCE_HANDLE=0` | 只折叠成 list 字面量（退回 R30 行为） |
| `LAKESOUL_VECTOR_BATCH_CHUNK_QUERIES` / `..._CHUNKS_IN_FLIGHT` | 批量分块大小 / 在飞块数 |
| `LAKESOUL_VECTOR_SEARCH_PROFILE=1` | 输出各阶段耗时（plan / physical plan / exec / probe / metadata） |

**诊断场景**：`vector_rebuild_bench --scenario plan-probe`（planning 四阶段拆分 + optimizer 规则顺序打印）、
`--scenario rust-shard-batch`（纯 Rust 参考实现，作为上限对照）。
