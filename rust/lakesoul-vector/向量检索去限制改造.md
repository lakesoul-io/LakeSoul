# 向量检索"去特殊要求"改造（P1–P4）

> 目标：**不对表形态提特殊要求**——多文件桶、带 filter、任意投影、分区/CDC 都要能走同一套
> 候选检索 + 按需取行，而不是"只有 1 文件/桶、无 filter、投影固定时才快"。
> 原则：正确性由"逐候选可见版本解析"保证，性能靠"只读候选行"；**compaction 不再是前提**，
> 只是 F=1 时省掉解析的优化。所有改动都保留环境变量回退开关，并记录在本文件与
> `向量查询优化日志.md`。

## 四层方案

| 层 | 目标（去掉的要求） | 核心改动 | 状态 |
|---|---|---|---|
| **P1** | 去掉"每个 hash bucket 只能 1 个数据文件" | 候选解析器：对桶内每个文件建 key→rowid 映射 + payload，逐候选定位；多版本/多命中则回退 | **已完成（append 型）**，多版本待 P1b |
| **P2** | 去掉"投影=主键+向量列" | 按需列取（任意投影列只读候选行），向量列仅内部使用 | 未开始 |
| **P3** | 去掉"scan 与 Sort 之间无 filter"、"过滤选择性高时少行/0 行" | 过滤感知迭代扩探（谓词下推到候选阶段，不足 K 时扩大 nprobe/overfetch） | 未开始 |
| **P4** | 去掉"无 CDC/分区列" | 候选解析接入分区值与 CDC 变更语义（delete/update 逐候选解析） | 未开始 |

## P1（已完成部分）：多文件桶候选解析

**问题**：`exact_fast_path_eligible` 要求 `file_groups.iter().all(|group| group.len() == 1)`；
多文件桶直接回退 reader 路径（实测 exact 单查询 13–25 ms，约 40–75 QPS，而快路径 1.7 ms/533 QPS）。
大表单桶数据量 > `max_file_size` 时永远压不成 1 文件，等于永久降级。

**改动**（提交见下方记录）：
1. `rust/lakesoul-io/src/pk_locator.rs`
   - 新增 `rows_per_prefix_lenient()`：与 `one_row_per_prefix` 相同的单调 gallop 查找，但
     "0 行/多行"的 key 返回 `None` 而不是整批失败（多文件解析需要知道每个 key 归属哪个文件）；
   - `VectorPayloadSource` 新增 `lookup_rows()`（哪些 key 在本文件唯一命中）与 `take_rows()`
     （按行号读 payload）；
   - 新增 `take_multi_file(sources, keys)`：对候选 key 逐个在桶内所有文件中定位，
     **恰好命中一个文件**才读取；命中 0 个或多个（多版本）→ 返回 `None`，上层回退
     merge-on-read reader 路径；读取后按原候选顺序用 `arrow::compute::interleave` 重排。
2. `rust/lakesoul-datafusion/src/datasource/file_format/vector_search_exec.rs`
   - `exact_fast_path_eligible`：不再要求每组 1 个文件（保留 `LAKESOUL_VECTOR_MULTI_FILE_EXACT=0`
     可恢复旧行为用于 A/B）；
   - 直读路径按桶打开**每个文件**的 payload source，任务内改用 `take_multi_file`。
3. 测试（`src/tests/vector_search_tests.rs`）
   - `sql_vector_search_multi_file_bucket`：单桶两次提交 = 2 个数据文件，断言**仍走直读路径**
     （test-only 计数 `EXACT_DIRECT_RUNS`）且 recall ≥ 8/10；
   - `sql_vector_search_multi_file_upsert_falls_back`：同一批 key 写两次（多版本），断言结果
     与"合并后"的暴力 top-k 一致（解析器返回 None → reader 路径，结果仍正确）。

**语义边界（P1 当前版本）**
- 支持：追加型多文件桶（不同 key 分散在多个文件）、每桶 1 文件（原快路径，行为不变）；
- 回退：候选 key 在桶内出现于多个文件（update/upsert 多版本），或命中 0 个（索引与文件不一致）、
  或存在索引 mutation/CDC 变更链、分区列、filter 等原有条件不满足时；
- 结果一致性：直读只读"唯一可见行"，与 merge-on-read 的可见定义一致；回退路径由通用 reader 保证。

**后续 P1b（多版本解析）**：利用文件 commit 顺序 + 索引 `version`/`birth_version`，按"最新
commit 胜"挑选可见版本、按 tombstone 丢弃，从而支持 upsert 型多文件桶，而不只是追加型。
