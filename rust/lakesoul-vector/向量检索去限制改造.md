# 向量检索"去特殊要求"改造（P1–P4）

> 目标：**不对表形态提特殊要求**——多文件桶、带 filter、任意投影、分区/CDC 都要能走同一套
> 候选检索 + 按需取行，而不是"只有 1 文件/桶、无 filter、投影固定时才快"。
> 原则：正确性由"逐候选可见版本解析"保证，性能靠"只读候选行"；**compaction 不再是前提**，
> 只是 F=1 时省掉解析的优化。所有改动都保留环境变量回退开关，并记录在本文件与
> `向量查询优化日志.md`。

## 四层方案

| 层 | 目标（去掉的要求） | 核心改动 | 状态 |
|---|---|---|---|
| **P1** | 去掉"每个 hash bucket 只能 1 个数据文件" | 候选解析器：对桶内每个文件建 key→rowid 映射 + payload，逐候选定位；多版本按文件年龄取最新，年龄并列则回退 | **已完成（P1a 追加型 + P1b 多版本/upsert 型）** |
| **P2** | 去掉"投影=主键+向量列" | 精确排序仍走直读（只读主键+向量列）；其余投影列在 keep 行上用 pk 过滤二次读取，任意投影保持快路径 | **已完成** |
| **P3** | 去掉"scan 与 Sort 之间无 filter"、"过滤选择性高时少行/0 行" | 谓词随 marker 下推到 scan，候选行读回后在本进程求值，不足 keep 行时按 ×4 扩大候选集（有上限） | **已完成** |
| **P4** | 去掉"无 CDC/分区列" | CDC：候选行读回后按 `cdc != delete` 求值、覆盖性证明放宽为"索引覆盖全部文件"（mutation 由已加载分片屏蔽）；分区列候选解析待续 | **CDC 已完成；分区待续** |

## P4（部分完成）：CDC 变更语义接入候选路径；分区列待续

**问题**：直读/过滤快路径此前都要求 `cdc_column.is_empty() && partition_cols.is_empty()`，
CDC 表的查询只能回退 reader 路径；而 CDC 表的删除是"数据文件里 `op='delete'` 的墓碑行"，
候选 key 可能是已删除的 key，必须逐候选解析变更语义才能保证结果正确。

**改动（CDC 部分）**：
1. `table_provider.rs`：CDC 表的向量扫描把 `cdc_column != 'delete'` 编译成 `PhysicalExpr` 传给 exec；
2. `vector_search_exec.rs`：
   - 过滤快路径的触发条件从"有 Filter"放宽为"有 Filter **或** 有 CDC 谓词"；
   - 读回候选行后依次求值（plan 的 Filter 谓词 + CDC 谓词），再 `filter_record_batch`，
     所以墓碑行不会进入排序；不足 `keep_rows` 时照旧 ×4 扩探；
   - `expected_snapshot`/`snapshot_covered` 增加 `cdc_free` 参数：CDC/过滤候选路径使用
     **放宽的覆盖性证明** `candidate_files_covered()`——只要求"索引提交覆盖本快照的全部数据文件"，
     不再要求"无 mutation 链/无 CDC"；安全依据：①加载分片时 mutation 链会掩蔽被删 key，
     这些 key 根本不会成为候选；②满足覆盖后，候选行由 merge-on-read 读回，墓碑由
     reader 的 CDC 过滤 + 本进程谓词双重丢弃；
3. 测试 `sql_vector_search_cdc_drops_tombstones`（CDC 向量表，200 行，删掉 20 行）：
   - `count(*)` = 180（确认 merge-on-read 语义）；
   - `select id ... order by dist limit 10`：走候选路径（test-only 计数）、**返回 10 行**、
     不含任何被删 id、recall ≥ 8/10；
   - `where id > 100`：过滤 + CDC 组合，返回 10 行且全部 >100 且未删除。

**分区列（待续）**：`partition_cols` 非空仍回退 reader。原因是分区表上"按主键过滤的二次读取"
会跨分区取行（同一主键可能存在于多个分区），需要把读取按分区组分别加过滤条件才能真正放开；
当前行为正确的是回退。下一步计划：给 `build_configs_with` 增加"按组过滤"能力后放开分区表。

## P3（已完成）：过滤感知的迭代扩探

**问题**：`Filter` 出现在 scan 与 `Sort` 之间时（`WHERE ... ORDER BY dist LIMIT k`），旧实现是
"候选后过滤"：scan 先按索引取 `top_k*overfetch` 个候选，上层的 `FilterExec` 再过滤，`Limit`
只能拿到剩下的行。选择性低时返回行数远小于 `k`（记录过 0.08% 选择性下即便 overfetch=50 也返回 0 行），
且因为 `narrow=false` 直读路径不生效，只能走 reader 路径（比快路径慢 10–20×）。

**改动**：
1. **规则**（`vector_search_rule.rs`）：`detect` 收集 scan 与 Sort 之间的 `Filter` 谓词（多个用 AND 合并），
   随 marker 一起下推；`VectorSearchSpec.filter` 新增该谓词；
2. **marker**（`udf/vector_search_marker.rs`）：marker 末尾追加可选谓词参数，
   `VectorSearchRequest.filter: Option<Expr>`；旧 7/5 参数格式继续兼容；
3. **provider**（`table_provider.rs`）：把逻辑谓词编译成 `PhysicalExpr`（以数据列 schema 为准；
   编译失败——例如谓词引用分区列——则保持 `None`，扫描回退 reader 路径）；
4. **exec**（`vector_search_exec.rs`）：新增 `filtered_fast_path_eligible` + `try_filtered_batches`：
   - 用与直读路径相同的分片解析/覆盖性证明，按桶 probe 候选 key；
   - 把候选 key 解码成 `pk IN (...)`，用 **payload-only** reader 读取（新增 `build_configs_with(.., search=false)`，
     避免 native reader 再次把结果限制在它自己的向量候选集里——这是本轮发现并修掉的关键点）；
   - 在本进程用 `PhysicalExpr::evaluate` 对读回的行求值，`filter_record_batch` 保留通过行；
   - 通过行数 < `keep_rows` 时把候选集 **×4** 扩大（`nprobe` 不变），直到上限
     `LAKESOUL_VECTOR_FILTER_MAX_OVERFETCH`（默认 64）；起始倍率 `LAKESOUL_VECTOR_FILTER_OVERFETCH`（默认 4）；
   - 最后按精确距离排序、取 `keep_rows`、投影到计划 schema 返回。上层 `FilterExec` 对这些行是幂等的
     （全部已通过），`Sort`/`Limit` 于是拿到"过滤后 top-k"，而不是"候选里恰好通过的几行"。
5. 语义与边界：谓词与上层 `FilterExec` **完全相同**（同一逻辑表达式编译），所以不会多返回/错返回；
   仅对"单列、exact、无 CDC、无分区列、覆盖性证明通过"的查询生效，其它情况原样回退 reader 路径；
   `LAKESOUL_VECTOR_FILTER_EXACT=0` 可关闭。
6. 测试 `sql_vector_search_filter_narrows_probe`（400 行、`tag = id*7+1`）：
   - `where tag > 2000`（约 28% 选择性）：断言走候选探针路径（test-only 计数）、返回**恰好 10 行**、
     每行 `tag>2000`、top-10 recall ≥ 8/10；
   - `where tag > 2700`（14 行匹配，3.5% 选择性）：断言仍返回 **10 行**（扩探生效，旧行为会不足）；
   - `where tag < 0`：返回 0 行。

## P2（已完成）：任意投影保持快路径（向量列只用于内部打分）

**问题**：直读路径原先要求输出投影的每一列都是主键或搜索向量列，否则 `exact_fast_path_eligible`
返回 false，整条查询回退 reader 路径（13–25 ms/query）。实际业务几乎都会 `select id, title, ...`，
于是快路径被浪费。

**改动**：
1. `vector_search_exec.rs`
   - eligibility 改为：投影里出现"排名列（主键+搜索列）之外"的列时，仅要求
     `defers_payload(session_config)` 成立（即 narrow、已知 limit、未被 session 关闭），
     不再要求投影只有主键+向量列；
   - 直读路径的输出 schema 改为 **ranking schema**（主键 + 搜索列），精确距离排序不变；
   - `execute()` 在直读成功后：若投影含额外列，调用新增的 `payload_columns_for_ranked()`：
     `take_first_rows(keep)` → 构造 `pk IN (...)` 过滤 → `build_configs`/`read_configs`
     只读 keep 行的 payload 列 → `order_payload_by_keys` 重排 → `project_batch` 投影到
     计划 schema；若投影只有排名列，则直接 `project_batch`（零额外读）。
2. 语义边界：额外列的来源仍是同一批数据文件、同一批 keep 行，因此行/列对应关系与 reader 路径一致；
   代价是一次 keep 行（≤ limit，通常 100 行）的二次读取，而不是候选集全量回退。
3. 指标：直读 + 二次读取同样累加 `VectorSearchCounters` 的 `ranked`/`payload_rows`
   （`deferred_payload_ranked`/`deferred_payload_rows`），与 reader 路径的 deferred 语义一致；
4. 测试 `sql_vector_search_projects_extra_columns`：表增加 `tag` 列（Int64，非排名列），
   验证 `select id, tag ...` **仍走直读路径**（`EXACT_DIRECT_RUNS` 计数）、`tag` 与 `id` 对应关系
   正确、top-10 recall ≥ 8/10；以及 `select tag ...`（投影不含主键/向量列）也能返回 10 行。

## P1（已完成）：多文件桶候选解析（P1a 唯一命中 + P1b 多版本按年龄取新）

**问题**：`exact_fast_path_eligible` 要求 `file_groups.iter().all(|group| group.len() == 1)`；
多文件桶直接回退 reader 路径（实测 exact 单查询 13–25 ms，约 40–75 QPS，而快路径 1.7 ms/533 QPS）。
大表单桶数据量 > `max_file_size` 时永远压不成 1 文件，等于永久降级。

**改动**（提交见下方记录）：
1. `rust/lakesoul-io/src/pk_locator.rs`
   - 新增 `rows_per_prefix_lenient()`：与 `one_row_per_prefix` 相同的单调 gallop 查找，但
     "0 行/多行"的 key 返回 `None` 而不是整批失败（多文件解析需要知道每个 key 归属哪个文件）；
   - `VectorPayloadSource` 新增 `lookup_rows()`（哪些 key 在本文件唯一命中）与 `take_rows()`
     （按行号读 payload）；
   - 新增 `take_multi_file(sources, keys)`：对候选 key 逐个在桶内所有文件中定位，
     **恰好命中一个文件**才读取；命中 0 个或多个（多版本）→ 返回 `None`，上层回退
     merge-on-read reader 路径；读取后按原候选顺序用 `arrow::compute::interleave` 重排。
2. `rust/lakesoul-datafusion/src/datasource/file_format/vector_search_exec.rs`
   - `exact_fast_path_eligible`：不再要求每组 1 个文件（保留 `LAKESOUL_VECTOR_MULTI_FILE_EXACT=0`
     可恢复旧行为用于 A/B）；
   - 直读路径按桶打开**每个文件**的 payload source，任务内改用 `take_multi_file`。
3. 测试（`src/tests/vector_search_tests.rs`）
   - `sql_vector_search_multi_file_bucket`：单桶两次提交 = 2 个数据文件，断言**仍走直读路径**
     （test-only 计数 `EXACT_DIRECT_RUNS`）且 recall ≥ 8/10；
   - `sql_vector_search_multi_file_upsert_falls_back`：同一批 key 写两次（多版本），断言结果
     与"合并后"的暴力 top-k 一致（解析器返回 None → reader 路径，结果仍正确）。

**语义边界（P1 当前版本）**
- 支持：追加型多文件桶（不同 key 分散在多个文件）、每桶 1 文件（原快路径，行为不变）；
- 回退：候选 key 在桶内出现于多个文件（update/upsert 多版本），或命中 0 个（索引与文件不一致）、
  或存在索引 mutation/CDC 变更链、分区列、filter 等原有条件不满足时；
- 结果一致性：直读只读"唯一可见行"，与 merge-on-read 的可见定义一致；回退路径由通用 reader 保证。

**P1b（多版本解析，已完成）**：多文件桶里同一 key 可能出现在多个文件（upsert/重写）。解析器改为
**按文件年龄取最新**：
- 文件年龄 = 覆盖该文件的所有索引 segment 的 `birth_version` 最大值（catalog 修订号，索引提交顺序可比）；
  引擎在文件列表上按年龄升序排列 payload source，并把年龄数组传给解析器；
- 同一 key 命中多个文件时读年龄最大（严格更大）的文件，即 merge-on-read 的可见版本；**年龄并列**
  （无法证明谁更新）或零命中时整体回退 reader 路径；
- 覆盖性证明仍然要求"无 mutation、无 CDC、索引覆盖全部数据文件"，因此不会读到未提交/被删除的行。
这使 upsert 型多文件桶也能走直读快路径（此前会回退到 13–25 ms/query 的 reader 路径）。
（tombstone/CDC 的逐候选解析仍属于 P4。）

## 已知限制 / 待办
- 多文件解析成本 ≈ 每桶候选 key × 文件数（binary/gallop 查找），F=2–5 时预计直读 exact 由
  1.7 ms 升到 2–4 ms（仍远快于 reader 路径 13–25 ms），**待大表实测**；
- `LAKESOUL_PAYLOAD_SOURCE_CACHE_ENTRIES=16` 对多文件桶变小（每文件一个 source），大表需调大；
- P2 的额外列二次读取目前复用 reader（`build_configs`+`read_configs`，per-bucket 一次），
  单查询多一次 ~2–4 ms 的读；若额外列频繁出现，后续可把 payload 扩展到任意标量列；
- P3 的过滤路径目前按"候选 key → reader 读回 → 本进程求值"工作，每轮读取候选行的全部列；
  候选多、谓词选择性极低时会多读几轮（上限 64×top_k/桶）。后续可优化为：
  (a) 谓词只引用向量列时直接在 payload 上过滤；(b) 用统计信息估计选择性选起始倍率；
  (c) 需要更多列时把 payload 扩展到标量列；
- P4 分区列未放开：需要按分区组分别构造主键过滤（同一主键可存在于多个分区），当前回退 reader 路径；
- CDC 路径的覆盖性证明放宽为"索引覆盖全部数据文件"：若某次写只更新了索引的一部分或 mutation 链
  无法加载，`load_typed_shard` 会报错/回退，不会返回错误结果；但该放宽值得在更大数据量下复测。
