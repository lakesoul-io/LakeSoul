# DataFusion 向量查询使用说明（单查询 SQL + 批量入口）

> 适用于 `rust/lakesoul-datafusion`：在 DataFusion 55 上注册 LakeSoul catalog，用 SQL 或批量 API 做
> **向量索引检索**（IVF + RaBitQ，index-only / 精确重排两种排序模式）。
>
> 本文所有 API、字段名、默认值都取自本仓库代码；性能数字来自同一台 8 物理核 / 16 逻辑核
> KVM + AVX-512 机器上的 GloVe-200 实测（bits=1、nprobe 16、top_k 100、4 个 hash bucket，
> 构建与搜索分进程）。原理与逐次改动记录见
> `向量检索方案对比-最初与现在.md`、`向量查询优化日志.md`、`DataFusion向量查询逼近RustQPS方案.md`。

---

## 1. 概览：两条入口怎么选

| | 单查询 SQL | 快照批量入口 |
|---|---|---|
| 入口 | `SessionContext::sql()` → 逻辑/物理计划 → `LakeSoulVectorSearchExec` | `LakeSoulTableProvider::vector_batch_search(&SessionState, &VectorBatchRequest)` |
| 适用 | 交互式查询、BI、一条语句一个查询 | 一次要对同一快照打几百万/上千条 query（召回、评测、向量检索服务） |
| 每条语句固定成本 | 有（parse/analyze/plan + 2 次元数据 PG，约 1.4 ms） | 每批一次（一次快照列表、一次索引解析），200 条摊薄后 <0.01 ms/条 |
| 实测（GloVe-200、200 query） | **~526 QPS，p50 1.78 ms** | **11,410–12,113 QPS，p50 0.079–0.084 ms** |
| 10,000 query | 逐条发 = 10,000 条语句 | **13,318–14,250 QPS，p50 0.067–0.072 ms** |
| 结果 | 由 SQL 的 projection 决定（主键/任意列） | 固定返回每 query 的主键 top-k（index-only 顺序） |
| 快照 | 每条语句各自读最新快照 | 整批固定在同一快照上（调用时刻） |

一句话：**单条/少量查询用 SQL；成批查询用批量入口**（同批次能快 20× 以上，因为 lakehouse 协议成本被摊薄）。

## 3. 建表、写数据、建索引

### 3.1 SQL DDL（推荐）

```sql
-- 必须以 "lakesoul" catalog 为前缀（默认 catalog/schema 名见 session::DEFAULT_CATALOG/DEFAULT_SCHEMA）
CREATE EXTERNAL TABLE "lakesoul".default.vec_glove (
    id  BIGINT NOT NULL PRIMARY KEY,
    vec DOUBLE[] NOT NULL              -- List<Float32> / List<Float64> / FixedSizeList 都可以
) STORED AS LAKESOUL LOCATION '/data/vec_glove'      -- 对象存储写 's3://bucket/prefix'
OPTIONS (
    -- 向量索引声明（JSON 数组，可声明多列，列级融合在 SQL 里也是支持的）
    'vector_index_columns'
        '[{"column":"vec","dim":200,"nlist":1024,"total_bits":1,"metric":"L2"}]',
    -- hash 桶数：决定分片（shard）数，也决定批量入口的并行度
    'hash_bucket_num' '4'
);
```

要点：

- `dim` 必须等于向量列维度；`metric` 为 `"L2"` 或 `"IP"`（大小写不敏感）。
- 索引与检索的数学按 **float32** 计算：`DOUBLE[]`（`List<Float64>`）在写索引时会转 f32；
  若列是 `FLOAT[]`/`List<Float32>` 则零转换。
- `total_bits` 是 RaBitQ 的每维比特数（1–16，默认 7）。**bits=1** 时索引最小、最快，但
  Recall 有损（GloVe-200 上 Recall@100≈0.42；bits=7 约 0.64）。
- `hash_bucket_num` 决定 hash 分片数；越大单桶越小、单查询并行度越高（本说明的基准用 4）。
  SQL 选项键名接受 `hash_bucket_num` / `hashBucketNum`（DataFusion 会给无命名空间的选项加
  `format.` 前缀，内部两种都识别）。
- `LOCATION` 接受本地绝对路径（内部按 `file://` 处理）或 `s3://` / `s3a://` 等 URL；
  对象存储的 `AWS_*` 环境变量会被会话捕获。
- 表属性在 `TableInfo.properties` JSON 里，等价键名是 `vector_index_columns` / `hashBucketNum`。

### 3.2 写入与索引构建

```sql
-- 写入（LakeSoul 是 merge-on-read，INSERT OR REPLACE / UPSERT 都是先写数据文件、再按主键合并）
INSERT OR REPLACE INTO "lakesoul".default.vec_glove
SELECT CAST(g.value AS BIGINT), ARRAY[sin(g.value), cos(g.value), 0.1, 0.2, 0.3]
FROM generate_series(0, 999) AS g(value);
```

- 默认 `index_maintenance = inline`：每次写入提交后**自动增量构建**向量索引（见
  `lakesoul_datafusion::vector_index::auto_build_vector_index`），不需要手动触发。
- 需要延迟构建（先大批量导入再统一建索引）时：表属性 `index_maintenance` 设为 `deferred`
  （`TableInfo.properties` JSON 键，Rust 元数据 API / Python SDK 可设置；注意 SQL 的
  `CREATE EXTERNAL TABLE ... OPTIONS (...)` 目前**不透传**这个选项），数据提交后调用
  `lakesoul_datafusion::vector_index::rebuild_vector_index(&client, table_name, namespace,
  &primary_keys, object_store_options) -> Result<usize>` 做一次全量重建（返回重建的 shard 数；
  `object_store_options` 用 `lakesoul_common::misc::SecretMap::new()` 或你的 S3 配置）；
  或让后台任务按你的节奏构建。
- 批量导入用 writer API（`lakesoul_io::writer::create_writer_with_io_config` 等）比逐条 SQL 快得多；
  inline 模式下索引会随提交自动构建。

### 3.3 `vector_index_columns` 字段全表

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `column` | string | 必填 | 向量列名 |
| `dim` | usize | 必填 | 维度，必须与列一致 |
| `nlist` | usize | 256 | IVF 聚类数 |
| `total_bits` | usize | 7 | RaBitQ 每维比特数（1–16）；1 = 纯 1-bit 码 |
| `metric` | string | `"L2"` | `"L2"` 或 `"IP"`（`inner_product`/`dot_product`） |
| `rotator_type` | string | `"FhtKac"` | `"FhtKac"` 或 `"Matrix"` |
| `seed` | u64 | 42 | 旋转/聚类随机种子 |
| `use_faster_config` | bool | true | 快速量化模式 |
| `management.rebuild_mode` | string | `"auto"` | `auto` 触发重建；`none` 只追加 delta |
| `management.max_delta_ratio` | f32 | 1.0 | 自动重建的 delta/base 比例阈值 |
| `management.gc_enabled` | bool | true | 提交后清理被取代的索引文件 |
| `management.gc_grace_seconds` | u64 | 3600 | 宽限期（保护正在读旧 commit 的读者） |
| `management.gc_keep_generations` | usize | 1 | 保留代数 |

## 4. 单查询 SQL

### 4.1 最小完整程序

```rust
use std::sync::Arc;

use arrow::array::Int64Array;
use lakesoul_datafusion::cli::CoreArgs;
use lakesoul_datafusion::udf::vector_search_marker::LakeSoulVectorSearchConfig;
use lakesoul_datafusion::{
    MetaDataClient, create_lakesoul_session_config,
    create_lakesoul_session_ctx_with_config,
};

/// 把湖仓内部的 `rootcause::Report` 错误转成 `Box<dyn Error>`（也可以换成 anyhow 等）。
fn boxed<E: std::fmt::Display>(error: E) -> Box<dyn std::error::Error> {
    error.to_string().into()
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    // 1) 元数据客户端（环境变量见 §2.1）
    let client = Arc::new(MetaDataClient::from_env().await.map_err(boxed)?);

    // 2) 会话配置 + 向量检索选项（也可以之后用 SQL SET 改）
    let mut session_config = create_lakesoul_session_config().map_err(boxed)?;
    let mut vector = LakeSoulVectorSearchConfig::default();
    vector.nprobe = 16;                       // 每个 shard 探测的 IVF 聚类数
    vector.rerank = "index".to_string();      // index-only 排序；留空 = 精确重排
    vector.parallelism = 1;                   // shard 内 cluster 组并行度
    vector.deferred_payload = true;           // 单查询：只为最终保留的行读 payload
    session_config.options_mut().extensions.insert(vector);

    // 3) 建会话（自动注册 lakesoul catalog / schema）
    let ctx = create_lakesoul_session_ctx_with_config(
        client,
        &CoreArgs::from_env(),
        session_config,
    )
    .map_err(boxed)?;

    // 4) 查询向量（维度必须与索引的 dim 一致）
    let query: Vec<f32> = (0..200).map(|i| ((i as f32) * 0.01).sin()).collect();
    let literal = query.iter().map(|v| v.to_string()).collect::<Vec<_>>().join(", ");
    let sql = format!(
        "select id from \"lakesoul\".default.vec_glove \
         order by array_distance(vec, ARRAY[{literal}]) limit 100"
    );

    // 5) 执行并读取结果
    let df = ctx.sql(&sql).await?;
    for batch in df.collect().await? {
        let ids = batch.column(0).as_any().downcast_ref::<Int64Array>().unwrap();
        for id in ids.iter().flatten() {
            println!("{id}");
        }
    }
    Ok(())
}
```

也可以完全用 SQL 切换选项（无需改 Rust 代码）：

```sql
SET lakesoul_vector_search.rerank = 'index';
SET lakesoul_vector_search.nprobe = 16;
-- 之后同一 session 里的查询都按新选项执行
-- （数值型选项走字符串解析；也可以直接写入 session config，见上面的 Rust 写法）
```

### 4.2 SQL 形态要求（决定是否走索引）

向量下推（`VectorSearchPushdownRule`）要求整条语句是下面这个形状，**否则会退化成普通扫描**：

```
Limit(fetch = K)                       -- 必须有字面量 LIMIT；没有 LIMIT 不下推
  └─ Sort( <距离表达式> [ASC] )         -- L2 必须 ASC；IP 必须 DESC
       └─ [Projection / Filter]*        -- 可以有 WHERE，但会降低索引直返效率
            └─ TableScan(向量列所在表)
```

- **距离表达式**：单列 `array_distance(vec, ARRAY[...])` / `inner_product(vec, ARRAY[...])` /
  `dot_product(...)`；也支持多列加权融合 `0.7 * array_distance(a, ...) + 0.3 * inner_product(b, ...)`
  （同一 metric、系数为数值字面量）。
- **查询向量**：写成 `ARRAY[0.1, 0.2, ...]`（SQL 里是 `make_array(...)`）。全字面量时
  analyzer 会把它折成内部句柄（性能优化），不影响语义；也支持常量列表字面量形式。
- **必须有序**：`ORDER BY` 的距离方向要与 metric 匹配（L2 = 升序，IP = 降序），否则不下推。
- **可以有 WHERE**：过滤列必须是表的普通列；带 WHERE 时扫描无法只解码 `LIMIT` 行
  （`narrow=false` → 候选放大到 10×），性能低于纯 top-k。
- **投影**：`select id ...`（只投影主键）最快——命中"index-only 直返"，不读数据文件；
  投影其它列时仍然走索引，但需要回表读 payload（still 比全表扫描快，但慢于直返）。

### 4.3 两种排序模式

| 模式 | 开启方式 | 语义 | 性能（GloVe-200） |
|---|---|---|---|
| `exact`（默认） | `rerank` 留空/`"exact"` | 先用索引取候选，再按**存储向量**精确重排（需要读向量列） | 单查询 ~15–60 QPS 量级（本仓库早期基线 61.3） |
| **`index`** | `SET lakesoul_vector_search.rerank='index'` 或 session config | 直接按**索引距离**排序返回，不读向量列 | **~526 QPS，p50 1.78 ms** |

`index` 模式的 Recall 由索引精度决定（bits/nprobe）；`exact` 模式只在候选集合内精确重排，
两者都不改变表/事务/快照语义。

### 4.5 单查询性能特征（bits=1、index-only、GloVe-200）

| 阶段 | p50 | 说明 |
|---|---:|---|
| parse（含 200 浮点字面量） | ~0.21 ms | 与 SQL 文本长度相关 |
| analyze（含 catalog） | ~0.60 ms | 其中表信息 PG 查询 ~0.185 ms（每语句读最新快照） |
| 逻辑优化 | ~0.20 ms | 字面量已折成句柄，plan 很小 |
| 物理规划 | ~0.19 ms | 其中分区信息 PG ~0.18 ms |

| **合计** | **~1.78 ms** | ~526 QPS（顺序） |

## 5. 批量入口（快照批量）

### 5.1 最小完整程序

```rust
use std::sync::Arc;

use datafusion::catalog::{CatalogProvider, SchemaProvider};
use lakesoul_datafusion::cli::CoreArgs;
use lakesoul_datafusion::datasource::table_provider::LakeSoulTableProvider;
use lakesoul_datafusion::udf::vector_search_marker::LakeSoulVectorSearchConfig;
use lakesoul_datafusion::vector_batch::VectorBatchRequest;
use lakesoul_datafusion::{
    MetaDataClient, create_lakesoul_session_config,
    create_lakesoul_session_ctx_with_config,
};

fn boxed<E: std::fmt::Display>(error: E) -> Box<dyn std::error::Error> {
    error.to_string().into()
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let client = Arc::new(MetaDataClient::from_env().await.map_err(boxed)?);
    let mut session_config = create_lakesoul_session_config().map_err(boxed)?;
    session_config
        .options_mut()
        .extensions
        .insert(LakeSoulVectorSearchConfig::default());   // 批量入口不读 rerank，保持默认即可
    let ctx = create_lakesoul_session_ctx_with_config(
        client,
        &CoreArgs::from_env(),
        session_config,
    )
    .map_err(boxed)?;

    // 1) 从 catalog 取出 provider（批量入口挂在 provider 上，而不是 SQL）
    let state = ctx.state();
    let catalog = ctx.catalog("lakesoul").ok_or("lakesoul catalog missing")?;
    let schema = catalog.schema("default").ok_or("default schema missing")?;
    let table = schema.table("vec_glove").await?.ok_or("table missing")?;
    let provider = table
        .downcast_ref::<LakeSoulTableProvider>()
        .ok_or("not a LakeSoul table")?;

    // 2) 组批：每条 query 一个 Vec<f32>，长度必须等于索引 dim
    let queries: Vec<Vec<f32>> = (0..200)
        .map(|q| (0..200).map(|i| ((q * 200 + i) as f32 * 0.001).cos()).collect())
        .collect();

    // 3) 一次调用搜索整批（同一快照）
    let request = VectorBatchRequest {
        column: "vec".to_string(),
        queries,
        top_k: 100,
        nprobe: 16,
        parallelism: 1,
        batch_size: 0,          // 0 = 自适应（见 §5.3）
    };
    let results: Vec<Vec<i64>> = provider.vector_batch_search(&state, &request).await?;

    // 4) 结果：每个 query 一个按索引距离排序的主键列表
    for (query_index, ids) in results.iter().enumerate() {
        println!("query {query_index}: top1={:?} len={}", ids.first(), ids.len());
    }
    Ok(())
}
```

### 5.2 参数

| 字段 | 类型 | 说明 |
|---|---|---|
| `column` | `String` | 要搜索的向量列（必须有 `vector_index_columns` 里的索引） |
| `queries` | `Vec<Vec<f32>>` | 一批查询向量，每条长度 = 索引 `dim`；维度不符会报错 |
| `top_k` | `usize` | 每条 query 返回的邻居数 |
| `nprobe` | `usize` | 每个 shard 探测的 IVF 聚类数（越大越准越慢；基准用 16） |
| `parallelism` | `usize` | shard 内 cluster 组的并行度（1 = 顺序探测；>1 会把 probed clusters 分组并行，结果集不变） |
| `batch_size` | `usize` | 每次 ANN 批的 query 数；`0` = 自适应（推荐） |

**返回**：`Vec<Vec<i64>>`，长度 = `queries.len()`，每个内层是主键（`i64`）列表，按索引距离
（`metric` 决定方向；L2 最近在前）排序，长度 ≤ `top_k`。批量入口**只返回主键**，不读向量列/payload。

### 5.3 `batch_size` 与自适应、内存

- `batch_size = 0`（推荐）：
  - 能证明"索引 commit 覆盖该桶全部 active 数据文件、表无 CDC 列、无 mutation chain"时 →
    **自适应整批**（上限 1024 query/块）；
  - 需要 liveness 校验读时 → 退回 `DEFAULT_BATCH_SIZE = 64`。
- `batch_size = N > 0`：强制每块 N 条 query。
- 大批次（如 10,000 query）会按 1024/块分块、**最多 2 块同时在飞**，结果按块序还原；
  实测 10k query 13.3–14.2k QPS、peak RSS ≈350 MB（不分块时 peak RSS 547 MB）。
- 可用环境变量微调：`LAKESOUL_VECTOR_BATCH_CHUNK_QUERIES`（默认 1024）、
  `LAKESOUL_VECTOR_BATCH_CHUNKS_IN_FLIGHT`（默认 2）。

### 5.4 语义与正确性

- **同快照**：一次调用只读调用时刻的那一个快照（provider 用当前 snapshot 的文件列表驱动）。
  每批结果的正确性相对于该快照，调用方通过"何时调用"选择快照。
- **merge-on-read / 删除 / CDC 语义不变**：当无法证明"commit 覆盖桶内全部 active 文件"时，
  批量入口会执行与单查询相同的 liveness 校验读（`LakeSoulReader` 按主键校验存活）。
  可用 `LAKESOUL_VECTOR_BATCH_FORCE_VERIFY=1` 强制校验（A/B 或保守场景）。
- **与单查询一致**：同一批 query 的 top-k 与逐条 SQL 查询结果一致（仓库单测
  `batch_search_matches_single_query_results`）；Recall 与单查询逐位一致。
- **排序**：按索引距离（index-only 顺序）；`metric=IP` 时按内积降序。

### 5.5 性能特征（bits=1、GloVe-200、4 bucket、nprobe 16）

| 配置 | QPS | p50 | CPU/query | 查询期 RSS | Recall@100 |
|---|---:|---:|---:|---:|---:|
| 批量 200 query/快照 | 11,410–12,113 | 0.079–0.084 ms | 1.00–1.15 ms | 237 MB | 0.42035 |
| 批量 10,000 query/快照 | 13,318–14,250 | 0.067–0.072 ms | ~1.0 ms | 346–348 MB | 0.43784（自查询集） |
| 纯 Rust 参照（同 shard/query） | 检索段 13.4–14.3k；“检索+合并”≈10.7k | — | — | — | 0.42035 |

CPU/query ≈ 1.0–1.15 ms 基本就是 4 个 shard 的 ANN 本身（≈0.275 ms/query/shard 单线程），
DataFusion/IO 侧附加开销 <5%；端到端为纯 Rust 检索段的 83–85%。

## 7. 端到端最小示例（建表 → 写入 → 单查询 → 批量）

```rust
use std::sync::Arc;

use arrow::array::Int64Array;
use datafusion::catalog::{CatalogProvider, SchemaProvider};
use lakesoul_datafusion::cli::CoreArgs;
use lakesoul_datafusion::datasource::table_provider::LakeSoulTableProvider;
use lakesoul_datafusion::udf::vector_search_marker::LakeSoulVectorSearchConfig;
use lakesoul_datafusion::vector_batch::VectorBatchRequest;
use lakesoul_datafusion::{
    MetaDataClient, create_lakesoul_session_config,
    create_lakesoul_session_ctx_with_config,
};

fn boxed<E: std::fmt::Display>(error: E) -> Box<dyn std::error::Error> {
    error.to_string().into()
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let client = Arc::new(MetaDataClient::from_env().await.map_err(boxed)?);
    let mut session_config = create_lakesoul_session_config().map_err(boxed)?;
    let mut vector = LakeSoulVectorSearchConfig::default();
    vector.nprobe = 16;
    vector.rerank = "index".to_string();
    session_config.options_mut().extensions.insert(vector);
    let ctx = create_lakesoul_session_ctx_with_config(
        client,
        &CoreArgs::from_env(),
        session_config,
    )
    .map_err(boxed)?;

    // ---- 建表（若已存在可跳过）----
    let ddl = r#"CREATE EXTERNAL TABLE "lakesoul".default.demo_vec (
        id BIGINT NOT NULL PRIMARY KEY,
        vec DOUBLE[] NOT NULL
    ) STORED AS LAKESOUL LOCATION '/tmp/demo_vec'
    OPTIONS ('vector_index_columns'
        '[{"column":"vec","dim":4,"nlist":4,"total_bits":1,"metric":"L2"}]',
        'hash_bucket_num' '2')"#;
    ctx.sql(ddl).await?.collect().await?;

    // ---- 写入 100 行 ----
    let insert = r#"INSERT OR REPLACE INTO "lakesoul".default.demo_vec
        SELECT CAST(g.value AS BIGINT),
               ARRAY[(g.value % 10) / 10.0, 0.1, 0.2, 0.3]
        FROM generate_series(0, 99) AS g(value)"#;
    ctx.sql(insert).await?.collect().await?;

    // ---- 单查询 ----
    let sql = r#"select id from "lakesoul".default.demo_vec
        order by array_distance(vec, ARRAY[0.1, 0.1, 0.2, 0.3]) limit 10"#;
    for batch in ctx.sql(sql).await?.collect().await? {
        let ids = batch.column(0).as_any().downcast_ref::<Int64Array>().unwrap();
        println!("single-query ids: {:?}", ids.values());
    }

    // ---- 批量 ----
    let state = ctx.state();
    let catalog = ctx.catalog("lakesoul").unwrap();
    let schema = catalog.schema("default").unwrap();
    let table = schema.table("demo_vec").await?.unwrap();
    let provider = table.downcast_ref::<LakeSoulTableProvider>().unwrap();
    let request = VectorBatchRequest {
        column: "vec".to_string(),
        queries: vec![vec![0.1, 0.1, 0.2, 0.3], vec![0.2, 0.1, 0.2, 0.3]],
        top_k: 10,
        nprobe: 4,
        parallelism: 1,
        batch_size: 0,
    };
    let results = provider.vector_batch_search(&state, &request).await?;
    println!("batch results: {results:?}");
    Ok(())
}
```

> 说明：上面的 DDL/INSERT 来自仓库测试里已验证的写法（`src/tests/vector_search_tests.rs`）。
> 生产环境建议把表建在对象存储上（`LOCATION 's3://bucket/prefix'` + `AWS_*` 环境变量），
> 并让 `LAKESOUL_WORKER_THREADS` / `RAYON_NUM_THREADS` 与机器核数匹配。

## 8. 常见问题（FAQ）

**Q1. `EXPLAIN` 里没有 `LakeSoulVectorSearchExec`（没走索引）？**
逐项检查：① 有没有 `LIMIT`（字面量）；② 是不是 `order by array_distance(...)` 且方向正确
（L2 升序 / IP 降序）；③ 距离函数参数是否是 `(列, ARRAY[...])`；④ 表名是否经 LakeSoul catalog
解析（`"lakesoul".default.<table>`）；⑤ 是否在 DISTINCT/GROUP BY/JOIN 等不支持的上下文里。

**Q2. Recall 偏低？**
Recall 由索引精度决定：`nbits=1` 时 GloVe-200 上 Recall@100 ≈0.42（1-bit 码的固有精度损失）；
把 `total_bits` 调到 7 可到 ≈0.64（索引体积 ×3.2、批量 QPS −30%、RSS +43%）。也可以提高 `nprobe`
（16 → 32/64）用延迟换召回。修改 `total_bits` 需要重建索引。

**Q3. 单查询比批量慢很多？**
正常：单查询每条语句都要 parse/analyze/plan + 2 次元数据 PG（约 1.4 ms 固定成本）。
同一快照上要打很多 query 时请用批量入口（§5），或者用多并发单查询（c=8 约 2,055 QPS）。

**Q4. 批量内存高？**
10k query 默认分块（1024/块、最多 2 块在飞）时 peak RSS ≈350 MB；调小
`LAKESOUL_VECTOR_BATCH_CHUNK_QUERIES` 或 `LAKESOUL_VECTOR_BATCH_CHUNKS_IN_FLIGHT` 可进一步压低
（代价是 QPS 略降）。200 query 批次约 237 MB。

**Q5. 索引没建/没命中？**
确认表属性 `vector_index_columns` 存在且列名/维度与 schema 一致；确认写入提交后索引已构建
（inline 模式自动构建；deferred 模式需手动触发）；确认查询走的是 `rerank='index'` 或 exact，
且索引 commit 的 `data_files` 覆盖当前 snapshot 文件（批量入口会据此决定是否跳过校验）。

**Q6. 元数据连接失败？**
`LAKESOUL_PG_URL` 必须 `jdbc:` 前缀；`lakesoul_home` 属性文件优先于环境变量；本地测试库用
`script/meta_init_for_local_test.sh` 初始化。

**Q7. 想确认是哪一层慢？**
开 `LAKESOUL_VECTOR_SEARCH_PROFILE=1` + `RUST_LOG=lakesoul_datafusion=debug,lakesoul_metadata=debug`，
看 `lakesoul catalog table lookup`（analyzer）、`metadata client query split`（PG 往返）、
`vector index-only inner profile`（resolve/load/probe/candidates）、
`vector batch profile`（list/search）与 bench 自身的 plan/physical/exec 均值。

## 11. 只用 SQL 做批量查询？——实测对比

结论先说：**SQL 路径只能"一条语句一个查询向量"**；要拿到批量吞吐必须用批量入口（§5）。
下面是同样 200 / 10,000 条 query 在"纯 SQL"与"批量入口"下的实测（同一张 GloVe-200 表、
bits=1、nprobe=16、top_k=100，环境同 §10）。

### 11.1 三种"用 SQL 提交多条 query"的写法

| 写法 | 示例 | 能否下推 | 说明 |
|---|---|---|---|
| ① 逐条 SQL（推荐给少量查询） | `select id ... order by array_distance(vec, ARRAY[...]) limit 100` 重复 N 次 | ✅ 每条都下推 | 每条语句付一次 parse/plan + 2 次元数据 PG（约 1.4 ms 固定成本） |
| ② 一条语句里 `UNION ALL` 多个子查询 | `(select ... limit 100) union all (select ... limit 100) ...` | ✅ 每个分支都能下推（`EXPLAIN` 里出现多个 `LakeSoulVectorSearchExec`） | 分支可并行执行，实测 QPS 约 960；但 **SQL 不保证结果行序**，按分支拆分会错位（实测按分支取主键与逐条查询不一致），不适合需要"每 query 归因"的批量 |
| ③ 多 query 的 `JOIN`/`VALUES` 形式 | `from tbl t, (values (ARRAY[...]), (ARRAY[...])) q(qv) order by array_distance(t.vec, q.qv)` | ❌ **不下推**（实测 `vector_exec=false`） | 退化成全表扫描 + 精确排序，绝对不要用 |

> ② 的 `EXPLAIN` 实测：`multi_query_sql[union_all]: vector_exec=true`；
> ③ 的 `EXPLAIN` 实测：`multi_query_sql[cross_join_values]: vector_exec=false`。

### 11.2 实测吞吐

| 提交方式 | 条数 | 并发 | QPS | p50 | Recall@100 | RSS |
|---|---:|---:|---:|---:|---:|---:|
| 纯 SQL 逐条 | 200 | 1 | **529.5** | 1.874 ms | 0.42035 | 239 MB |
| 纯 SQL 逐条 | 200 | 8 | **2,654.7** | 2.719 ms | 0.42035 | 233 MB |
| 纯 SQL 逐条 | 10,000 | 1 | **501.7** | 1.974 ms | 0.43784 | 262 MB |
| 纯 SQL 逐条 | 10,000 | 16 | **3,349.9** | 4.522 ms | 0.43784 | 290 MB |
| UNION ALL（20 query/语句） | 200 | 1 | 961.4 | — | 行序不可靠 | 232 MB |
| **批量入口（§5）** | 200 | — | **14,605** | 0.0685 ms/query | 0.42035 | 244 MB |
| **批量入口（§5）** | 10,000 | — | **14,761–15,151** | 0.066–0.068 ms/query | 0.43784 | 356–387 MB |

**解读**：

- 纯 SQL 顺序 = 每条 query 一次完整语句（1.9 ms 里 ~1.35 ms 是 planning + 元数据）；
  并发 c=8/c=16 能把吞吐提到 2.7k / 3.3k QPS（元数据读已并发化），但仍是**每条语句一次 planning**。
- 批量入口把"一次快照列表 + 一次索引解析 + 一次 ANN 批"摊薄到整批，因此 **≈29×（顺序）/ 4.4×（c=16）**。
- 10,000 条 query 时：纯 SQL 顺序需要 10,000 条语句（约 20 s），批量入口一次调用约 0.68 s。

### 11.3 建议

- **交互式/少量查询（1～几十条）**：直接写 SQL（§4），简单且 500+ QPS。
- **成批查询（上百到上万条）**：用批量入口（§5），吞吐差 4～30 倍。
- **必须只用 SQL 时**：用多并发（`c=8~16`，2.7k–3.3k QPS），并且**不要**用 JOIN/VALUES 形式把
  多个 query 放进一条语句（不下推，会全表扫描）。

复现命令（本文 example 支持纯 SQL 批量模式）：

```bash
# 纯 SQL 逐条提交（并发 8）
cargo run --release -p lakesoul-datafusion --example vector_query_qps -- \
  --table vec_glove_qps --query-file glove-query.fvecs --gt-file glove-gt.ivecs \
  --iterations 20 --query-limit 200 --top-k 100 --nprobe 16 --rerank index \
  --batch-rounds 1 --sql-batch --sql-concurrency 8

# 单条语句里 UNION ALL 多条 query
cargo run --release -p lakesoul-datafusion --example vector_query_qps -- ... \
  --union-batch 20

# 检查"多 query 单语句"是否下推
cargo run --release -p lakesoul-datafusion --example vector_query_qps -- ... --explain-multi
```

## 12. 重排（`rerank=exact`）为什么慢，怎么把它的 QPS 提上去

上一节 §4/§10 的数据：index-only 524 QPS、exact 只有 17 QPS。本节是实测拆解 + 提高手段。

### 12.1 根因：每条查询都要把"候选行的真实向量"从数据文件里取回来

exact 模式必须读存储向量算精确距离，而候选行散布在整个桶的数据文件里。profile 拆解
（bits=1、top_k=100、nprobe=16、warm）：

| 阶段（每桶） | 耗时 | 说明 |
|---|---:|---|
| reader 物理计划的 `listing/schema/flatten/merge` | 1.8 ms | 可以忽略 |
| **候选行取回 `pk_locator::take_rows`** | **45–66 ms** | 1000 个候选 → **~50 µs/行** |
| 其中 key index 缓存命中 | 27–40 µs | 索引查找本身很快 |
| scan / exec 启动 | 0.7–2.5 ms | — |
| DataFusion 精确距离 + Sort（4000 行） | ~1 ms | 也可以忽略 |

原因：Vortex/Parquet 按 **chunk（数千行）** 解码。1000 个随机候选几乎覆盖了每个 chunk，
等于把该桶的整列向量（每个 vortex 文件 209 MB ≈ 236 MB/桶，4 桶 ≈ **944 MB/查询**）解压一遍。
这就是 exact 只有 ~17 QPS、RSS 1 GB 的根本原因，与索引/ANN 无关（ANN 只有 1.5 ms/桶）。

### 12.2 手段一：降低 `exact_overfetch`（本次新增可调项）

新增会话选项 `lakesoul_vector_search.exact_overfetch`（默认 10，即每桶取 `top_k × 10` 候选），
也可以用环境变量 `LAKESOUL_VECTOR_EXACT_OVERFETCH` 覆盖；SQL：`SET lakesoul_vector_search.exact_overfetch = 4`。
实测（bits=1、200 条真实 query、单查询）：

| `exact_overfetch` | QPS | p50 | Recall@100 | RSS |
|---:|---:|---:|---:|---:|
| 10（默认） | 17.3 | 57.1 ms | 0.64015 | 1013 MB |
| 6 | 18.2 | 53.9 ms | 0.63975 | 885 MB |
| 4 | 21.0 | 47.5 ms | 0.63850 | 786 MB |
| 2 | **25.6** | **39.0 ms** | 0.62885 | 751 MB |

候选越少、要解压的 chunk 越少，所以能快 ~50%，代价是召回小幅下降。

### 12.3 手段二：并发（IO/解压并行）

exact 是 IO/解压密集型，多语句并发可以叠吞吐（`--sql-batch --sql-concurrency`）：

| 并发 | QPS | p50 | Recall | RSS |
|---:|---:|---:|---:|---:|
| 1 | 14.6 | 68.1 ms | 0.65070* | 887 MB |
| 4 | 30.1 | 127 ms | 0.65070* | 1170 MB |
| 8 | 33.8 | 219 ms | 0.65070* | 1488 MB |
| 8 + `exact_overfetch=2` | **39.8** | 167 ms | 0.63960 | 1248 MB |

\* 该组只跑前 100 条 query 的子集，所以召回数值与全量不同；同一组内各并发档完全一致。

### 12.4 手段三（推荐）：把精度烘焙进索引，用 index-only 拿到同样的召回

实测对比（同一 GloVe-200 表，只有索引 `total_bits` 不同；`nlist=1024`、nprobe=16、top_k=100）：

| 配置 | 单查询 QPS / p50 | 单查询 Recall@100 | 批量 200 QPS | 索引体积 |
|---|---:|---:|---:|---:|
| bits=1 + **exact**（重排） | 17.3 / 57.1 ms | 0.64015 | —（批量只支持 index-only） | 103 MB |
| **bits=7 + index-only** | **482.5 / 2.05 ms** | **0.63805** | **8,654**（0.116 ms/query） | 330 MB |
| bits=1 + index-only | 524 / 1.79 ms | 0.42035 | 13,959 | 103 MB |

**结论：要 0.64 级召回，不要用查询期重排——把 `total_bits` 调到 7（或更高）重建索引后直接用
index-only：召回 0.638（几乎等于 exact 的 0.640），单查询快 28×、批量快数百倍**，代价是索引体积
×3.2、批量 QPS 从 ~14k 降到 ~8.7k（仍然远高于 exact）。
`bits=7` 上的 exact 仍是 ~15 QPS / recall 0.6402——重排只再多 0.002 召回，不值得。

### 12.5 手段四：存储向量 payload 缓存（`LAKESOUL_VECTOR_RERANK_CACHE=1`，opt-in）

前三个手段都是在"每查询必须解码整列向量"这个前提下微调；本手段把这个前提去掉：首次 exact 重排时，
把每个数据文件的向量列按行序写成一份本地 payload（之后用 `pread` 随机读 800 B/行），主键列直接从
`pk_locator` 自己的 mmapped key index 解码，于是候选行取回**不再打开数据文件、也不再解码整列**。

开关（进程级环境变量，默认关）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `LAKESOUL_VECTOR_RERANK_CACHE` | 关 | `1`/`true`/`yes`/`on` 开启 |
| `LAKESOUL_VECTOR_RERANK_CACHE_DIR` | `${LAKESOUL_CACHE_PATH}/rerank-payload`，否则 `${TMPDIR}/lakesoul-rerank-payload` | payload 目录 |
| `LAKESOUL_VECTOR_RERANK_CACHE_BYTES` | 16 GiB | 目录预算；超预算的文件不缓存、自动回退原路径 |

实测（同一张表、同一二进制；bits=1、nlist=1024、nprobe=16、top_k=100、200 条真实 query）：

| 配置 | QPS | p50 | p99 | Recall@100 | 查询期 RSS | take/桶 |
|---|---:|---:|---:|---:|---:|---:|
| exact，缓存关（原路径） | 15.8 | 61.9 ms | 89.2 ms | 0.64015 | 1093 MB | 45–60 ms |
| exact，缓存开（冷启动，含构建） | 46.6 | 21.2 ms | 23.2 ms | 0.64015 | 484 MB | — |
| exact，缓存开（热，3 次） | **48.5 / 48.6 / 48.8** | **20.2 ms** | 22.3–23.9 ms | 0.64015 | **352 / 353 / 364 MB** | **0.49–0.54 ms** |
| index-only（对照，未受影响） | 495 | 1.90 ms | 2.55 ms | 0.42035 | 232 MB | — |

- QPS **3.1×**、p50 **3.1×**、查询期 RSS **3.1× 低**，Recall **完全不变**；
- 热路径数字含 R40 的"exec 内精确排序 + 截断"（只把 limit×2+16 行交给上层 Sort，
  越界行数 4000 → 216，见优化日志 R40）；
- 磁盘：payload ≈ 行数 × 维度 × 4 B（本表 903 MB，约等于向量列 f32 原始大小）；冷启动构建约 0.66 s，
  按每条 query 省 41 ms 算**约 16 条查询回本**，单条 ad-hoc 查询不要开；
- 只在"投影列 ⊆ 主键列 ∪ 存储向量列 + Vortex 数据文件 + 文件为单有序段"时生效，其它情况自动回退到
  原来的 `take_rows`（两种模式结果一致，Recall 相同）；
- 是**派生缓存**：数据文件不可变，payload 文件名与头部都带 location 与列布局指纹，表/snapshot/MOR/
  commit 语义完全不变；删目录即回收，换表、重建索引后自动重建；
- 复现：在 §12.4 的复现命令前加
  `LAKESOUL_VECTOR_RERANK_CACHE=1 LAKESOUL_VECTOR_RERANK_CACHE_DIR=/dev/shm/rerank-payload`，
  先跑一遍（构建 payload），再跑第二遍测 QPS；
- 对照结论：如果只是要 0.64 级召回且**能改索引参数**，§12.4 的 `total_bits=7 + index-only`
  （482 QPS / 2.05 ms / Recall 0.638）仍快约 10×；本手段适用于"索引参数不能改（例如 bits 固定为 1）
  但又必须按存储向量精确重排"或"需要 exact 语义的重复查询"。

#### 12.5.1 缓存打开后，参数最优点会被改写

候选行取回从 ~50 µs 降到 ~0.5 ms/桶之后，"多取候选"不再昂贵，而"候选更准"（提高 nprobe）反而
更划算：**提高 `nprobe` + 降低 `exact_overfetch`** 可以同时提升 QPS 和召回。实测
（bits=1、top_k=100、4 桶、200 条真实 query、缓存打开、同一二进制）：

| nprobe | `exact_overfetch` | QPS | p50 | Recall@100 |
|---:|---:|---:|---:|---:|
| 16 | 10（旧默认点） | 49.3 | 19.9 ms | 0.6401 |
| 16 | 2 | **64.5** | **15.3 ms** | 0.6289 |
| 64 | 2 | 64.1 | 15.3 ms | 0.7334 |
| 128 | 2 | 64.1 | 15.4 ms | 0.7772 |
| 256 | 2 | 62.0 | 15.8 ms | 0.8082 |
| 256 | 3 | 59.8 | 16.5 ms | 0.8438 |
| 256 | 4 | 57.4 | 17.2 ms | 0.8630 |
| 512 | 3 | 58.8 | 16.8 ms | 0.8757 |
| 512 | 4 | 55.2 | 17.7 ms | 0.8995 |
| 1024 | 4 | 53.1 | 18.6 ms | 0.9123 |

- 同召回（0.640）下 QPS **15.8 → 49.3（3.1×）**；
- 同 QPS 区间（60–64）下召回 **0.63 → 0.73–0.84**；
- 0.90 级召回只需 **~55 QPS**（旧 exact 的召回上限只有 0.640——瓶颈是候选集不是排序）；
- 建议：开缓存时用 `nprobe=128~256`、`exact_overfetch=2~3`（SQL：`SET lakesoul_vector_search.nprobe = 128`
  与 `SET lakesoul_vector_search.exact_overfetch = 2`）；
- 仍要提醒：只要 0.64 级召回且能改索引参数，`total_bits=7 + index-only`（482 QPS）还是最快；
  exact 重排现在的定位是"更高召回（0.8–0.9）+ 存储向量精确语义"。

### 12.6 手段五：底层 Rust 直读（当前默认路径）

R39/R40 之后 exact 仍要付"每桶一个 reader + 物理计划 + merge 计划"的固定开销（4 桶并行约 11 ms）。
现在 exact 重排直接在 scan 内部用 Rust 完成，不再创建任何 reader：

1. 复用 index-only 的快照解析、覆盖性证明和分片 probe；
2. 候选 key 直接交给 `pk_locator` 的 `VectorPayloadSource`：在 mmapped key index 上定位行号
   （候选 key 排序后单调 galloping，一次扫过），再从 payload 缓存 `pread` 800 B/行；
   **4 个桶的读取在 blocking 池并行**；
3. 8 路累加 f32 打分排序，只把 `keep_rows`（limit×2+16）行交给上层 Sort（上层仍用原 UDF 精确排序）；
4. 主键只对最终这些行解码。

生效条件（任一不满足自动回退到 R39/R40 的 reader 路径，结果不变）：单列 exact 查询、scan 与 Sort
之间没有 filter、投影 = 主键列 + 被搜向量列、**每个 hash bucket 只有 1 个数据文件**、payload 缓存
开启、无 CDC 列/分区列，并且**每次查询都重新通过覆盖性证明**（索引提交覆盖本快照全部文件、无
mutation 链、无 CDC 变更）；任一候选 key 在文件里不是恰好一行也会回退。`LAKESOUL_VECTOR_EXACT_DIRECT=0`
可以强制走旧 reader 路径做 A/B。

实测（bits=1、top_k=100、4 桶、200 条真实 query、payload 缓存开；同机 index-only 519–548 QPS /
p50 1.70–1.77 ms）：

| 路线 | nprobe | overfetch | QPS | p50 | Recall@100 | 占 index-only | RSS |
|---|---:|---:|---:|---:|---:|---:|---:|
| 最初 exact（R38 之前） | 16 | 10 | 15.8 | 61.9 ms | 0.64015 | 3% | 1093 MB |
| R39/R40（缓存 + reader） | 16 | 10 | 49.1 | 20.1 ms | 0.64015 | 9% | 355 MB |
| **直读** | 16 | 10 | 192.5 | 4.95 ms | 0.6401 | **37%** | 290 MB |
| **直读** | 32 | 1 | **310.9** | **3.04 ms** | **0.6419** | **60%** | 274 MB |
| 直读 | 64 | 1 | 307.9 | 3.11 ms | 0.6756 | 59% | 275 MB |
| 直读 | 24 | 2 | 293.3 | 3.23 ms | 0.6638 | 56% | 275 MB |
| 直读 | 64 | 2 | 282.2 | 3.27 ms | 0.7334 | 54% | 275 MB |
| 直读 | 256 | 1 | 269.1 | 3.55 ms | 0.7224 | 52% | 277 MB |
| 直读 | 128 | 3 | 253.0 | 3.72 ms | 0.8043 | 46% | 276 MB |
| 直读 | 256 | 3 | 229.5 | 4.15 ms | 0.8438 | 42% | 277 MB |

- **同召回（0.640 级）QPS 15.8 → 310.9（19.7×）**；等于 index-only 的 **60%**；
- 推荐参数：`nprobe=32~64`、`exact_overfetch=1~2`（SQL：`SET lakesoul_vector_search.nprobe = 32`、
  `SET lakesoul_vector_search.exact_overfetch = 1`）——召回 0.64–0.68，QPS 300±10；
- 需要更高召回：`nprobe=128~256` + `overfetch=2~3` → 召回 0.80–0.84，仍是 index-only 的 42–52%；
- 回退一致性：`LAKESOUL_VECTOR_EXACT_DIRECT=0` 与关 payload 缓存两条对照的召回都与直读路径逐位相同；
- 剩余 3.0 ms 里约 1.5 ms 是 SQL planning（与 index-only 相同），exec 内部约 1.5 ms
  （probe 0.5 + 取向量 ~0.9 + 排序 0.05）。

### 12.7 结论与建议

| 需求 | 建议 | 实测 |
|---|---|---|
| 高频/服务/批量 | index-only（`rerank='index'`） | 524 QPS 单查 / 13–14k 批量 |
| 需要 0.64 召回 + 高 QPS | **重建索引 `total_bits=7`，继续 index-only** | 482 QPS 单查 / 8.7k 批量，recall 0.638 |
| 少量 ad-hoc 精确校验 | exact（默认），可调低 `exact_overfetch` + 并发 | 17–40 QPS（overfetch 2 + c=8） |
| 需要 exact 语义 + 重复查询 | **开 `LAKESOUL_VECTOR_RERANK_CACHE=1`**（首次构建 ~0.7 s） | **47 QPS 单查 / 355 MB**，recall 0.64015 |
| 需要高召回 exact（0.85–0.9） | 开缓存 + `nprobe=256~512`、`exact_overfetch=3~4` | 55–60 QPS，recall 0.84–0.90 |
| exact 想要接近 index-only 的吞吐 | 开缓存（自动直读）+ `nprobe=32~64`、`overfetch=1~2` | **300±10 QPS（index-only 的 52–60%）**，recall 0.64–0.68 |
| 超大批量精确 | 用批量入口（index-only）+ bits=7 | 8.7k QPS，recall 0.638 |

> 开了 payload 缓存之后，候选行取回不再是瓶颈，`exact_overfetch` 保持默认 10 换取召回即可；
> 降 overfetch 的收益（§12.2）主要来自少解码候选，缓存模式下已不明显。

复现：

```bash
# 重排（可调 overfetch / 并发）
LAKESOUL_VECTOR_EXACT_OVERFETCH=2 cargo run --release -p lakesoul-datafusion \
  --example vector_query_qps -- --table vec_glove_qps --query-file glove-query.fvecs \
  --gt-file glove-gt.ivecs --iterations 200 --query-limit 200 --top-k 100 \
  --nprobe 16 --rerank exact --batch-rounds 1 --sql-batch --sql-concurrency 8
# 对照：bits=7 + index-only（需先用 --total-bits 7 --build-only 重建表）
```

拆解 exact 的耗时：`LAKESOUL_PK_PROFILE=1 LAKESOUL_VECTOR_SEARCH_PROFILE=1
RUST_LOG=lakesoul_io=debug,lakesoul_datafusion=debug`（会打印 `pk_locator: keys=... cache=... take=...`
和 `lake_soul io plan profile`）。
