## 2. 改动记录

### R1 — 索引缓存复用（已提交 `b5874e9d`，收益小）

- **假设**：`search_resolved_shard` 每次查询重新解码 shard 段、重新推导 coverage，是热点。
- **改动**：`rust/lakesoul-io/src/vector/search.rs`（`LoadedVectorShard` 缓存已解码
  shard + `CoveredFiles`；段解码移入 cache miss 闭包；新增 4 个单测）。
- **结果**（locator on，nprobe 16，3 轮交错）：old 23.29 / 23.52 / 22.70，new 23.91 /
  23.57 / 23.75 QPS → 均值 23.17 → 23.74（**+2.5%**），三轮不重叠；Recall 不变；
  peak RSS 6122 → 6063 MiB（不升）。
- **结论**：真实但极小，**不是主瓶颈**；保留（无 RSS 代价），若最终组合相对基线无可重复
  提升则与其它改动一起回滚。→ 揭示下一层瓶颈：`exec ≈ 39–42 ms` 中 `pk_locator take`
  占 17–22 ms。

### R2 — `pk_locator::take_rows` 窄列投影（已提交 `b5ab6932`，收益大）

- **证据**：`LAKESOUL_PK_PROFILE=1` 原始日志（804 行采样）：
  `keys=200 files=1 rows=200 cache≈30µs take=17–22ms total≈18–23ms`
  ——key 索引早已 warm，成本全在 `take`。
- **根因**：`take_rows` 用 `root().bind(file.dtype())` 做**整文件全列投影**，取 200 个
  随机行时几乎覆盖全部 chunk，于是每条 query 都要解码该 bucket 的 `id` + 200 维向量列
  （≈295k 行 × 800 B ≈ 236 MB/bucket）；而真正需要的只是投影后的 1–2 列。
- **改动**：`rust/lakesoul-io/src/pk_locator.rs::take_rows` 改为
  `select(FieldNames::from_iter(projection_names), root())`，只解码调用方请求的列。
  输出行/列/顺序完全不变（parquet/其它 locator 调用方同样受益，无语义变化）。
- **结果**（同上基准，3 轮交错，old 首轮为冷启动离群点单列）：

  | 指标 | old（稳态） | new | 变化 |
  |---|---:|---:|---:|
  | QPS | 22.31 / 23.82（中位 22.31） | 44.02 / 44.04 / 44.60（中位 44.04） | **+97%** |
  | p50 | 41.5–44.6 ms | 22.2–22.4 ms | −47% |
  | p99 | 50.4–56.1 ms | 26.0–29.2 ms | −50% |
  | exec_mean | 39.2–42.0 ms | 19.7–19.9 ms | −50% |
  | plan / physical plan | 1.25 / 1.56 ms | 1.21 / 1.56 ms | 不变 |
  | peak RSS | 6025–6134 MiB | 5600–5769 MiB | **−6%** |
  | Recall@100 | 0.63805 | 0.63805 | 不变 |
  | `take` | 17–22 ms | **0.69–0.83 ms** | −96% |

- **结论**：接受；`temp → new`（sha256 `0776a837…`）。剩余 `exec ≈ 19.9 ms` 待分解。

### R3 — `build_configs` 串行残差（分析；结论见 R3a/R3b）

- **证据**（`LAKESOUL_VECTOR_SEARCH_PROFILE=1` + bench opt-in `RUST_LOG` 订阅器，
  4 bucket / 60 query）：每桶（4 桶并行）
  `create≈0.03 ms, start≈4.8 ms, scan≈1.05 ms`，桶内合计 ≈5.9 ms；`exec=19.9 ms`
  ⇒ **串行残差 ≈14 ms**，且只可能在 `LakeSoulVectorSearchExec::build_configs`
  （4 次串行 `reader_config`：每桶一次 `VectorCatalog::resolve_cached` PG 查询 +
  `is_loaded` + `LakeSoulIOConfig` 构建，且每个都 `block_in_place` +
  `GLOBAL_RUNTIME.block_on` 跨 runtime 驱动）。
- **对照实验**（1 bucket，120 query，同代码）：`exec=10.35 ms`，桶内 ≈7.25 ms
  （start 6.1 + scan 1.13，桶更大所以 start 变长）⇒ 串行残差 ≈3.1 ms/桶，
  即残差随桶数**线性增长**（1→4 桶：3.1→14 ms），确认是 per-bucket 串行开销。
- **计划**：
  1. 给 `execute()`/`reader_config` 增加 env-gated 计时（`LAKESOUL_VECTOR_SEARCH_PROFILE`），
     把 14 ms 拆成「PG resolve / 缓存查询 / 配置构建 / 跨 runtime 驱动」；
  2. 依据拆分结果做**向量检索路径内**的结构调整（把 setup 改为在任务 runtime 上的
     异步流内执行 + 各桶并发解析；必要时把 N 个 shard 的 commit 解析合并成 1 次批量
     PG 查询，保持“每次查询都看最新 index commit”的新鲜度语义不变）；
  3. 目标：串行残差 14 ms → 3–5 ms，`exec` 19.9 → ~10 ms，QPS 44 → ~80；
  4. 用同一基准 A/B（新构建进 `temp`），不达标即删除 `temp` 并回滚该项。
- **不改**：Reader/表扫描/事务/snapshot/MOR；不做“为压测而改”的 Reader 改动。

### R3a — 诊断：每桶串行 `resolve` 的 2.3 ms 来自“永远为 false 的 is_loaded”

- **拆分**（同一 temp 构建、4 bucket、60 query、`LAKESOUL_VECTOR_SEARCH_PROFILE=1`）：
  `execute` 中 `build_ms≈9.5 ms`（4 个 `reader_config` 串行，每个 `resolve_ms≈2.28 ms`、
  其余配置构建仅 0.02 ms），`read_ms≈10.0 ms`（4 桶并行，桶内 start 4.8 + scan 1.0）。
  即 **串行 9.5 ms 全部落在每个桶的 resolve 上**。
- **根因**（逐字打印 cache probe）：
  - exec 侧 store 的 Display：`MonitoredObjectStore(local, LocalFileSystem(file:///))`
  - native reader 侧 store 的 Display：`LocalFileSystem(file:///)`
  - 两侧 `prefix` 与 `commit_id` 完全一致，但 `cache_key(kind, store, prefix)` 把
    store 的 Display 也编进 key，于是同一 shard 在缓存里有两个 key：
    reader 命中自己的 key，exec 的 `is_loaded` 永远 false ⇒ **每条 query、每个桶都白写一次
    PG reader lease**（`insert index_lease` + drop 时 `delete`，~2 ms/桶），
    这也是 `leases=1`、`index_lease` 表历史 78k 次 insert 的来源。
- **改动（R3b，待验证）**：把 cache 身份改成 `(kind, index_prefix)`，与系统自身的
  shard 身份一致（`index_shard` 有 `unique (kind, index_prefix)`；prefix 已含表路径）；
  `is_loaded`/`get_or_load` 不再接收 store（store 只用于实际加载，由调用方闭包持有）。
  这样 exec 与 reader 必然命中同一 entry，稳态查询不再申请 lease；首次加载（cache miss）
  仍照旧申请 lease，GC 保护语义不变。
- **预期**：`build_ms` 9.5 → ~1.5 ms（只剩 4 次 `select commit_id`），`exec` 19.9 → ~11 ms，
  QPS 44 → ~80。若实测提升可重复、RSS 不升、Recall 不变 → 覆盖 `temp → new` 并 commit；
  否则删除 `temp` 并回滚 R3b（保留 R1/R2 的 commit）。

### R3b — cache 身份对齐 catalog shard 身份（已提交 `a10cccce`）

- **改动**（向量/文本索引 cache 层与两个 search exec）：
  - `rust/lakesoul-io/src/index/cache.rs`：`cache_key(kind, prefix)`，去掉 object store 的

  - `rust/lakesoul-io/src/vector/search.rs`、`rust/lakesoul-io/src/text/search.rs`：调用点同步；
  - `rust/lakesoul-datafusion/.../vector_search_exec.rs`：exec 不再为 cache 探测取 store

  - `.../text_search_exec.rs`、`rust/lakesoul-es-gateway/src/search.rs`：同上签名同步。
- **结果**（同一基准，R2 二进制 vs R3b 二进制，3 轮交错）：

  | 指标 | R2（old） | R3b（new） | 变化 |
  |---|---:|---:|---:|
  | QPS | 45.21 / 45.46 / 45.34 | 56.66 / 57.86 / 58.01 | **+27.6%** |
  | p50 | 21.9–22.0 ms | 17.1–17.6 ms | −22% |
  | exec_mean | 19.35–19.45 ms | 14.56–14.98 ms | −24% |
  | plan / physical plan | 1.17 / 1.50 ms | 1.18 / 1.50 ms | 不变 |
  | peak RSS | 5791–5941 MiB | 5773–5819 MiB | 不升 |
  | Recall@100 | 0.63805 | 0.63805 | 不变 |
  | `build_ms`（4 桶串行） | 9.5 ms（resolve 2.28/桶、leases=1） | 4.8 ms（resolve 1.15/桶、**leases=0**） | −49% |
  | `read_ms`（4 桶并行） | ~10.0 ms | ~9.5 ms | 不变 |

- **附带实验**：`RAYON_NUM_THREADS` = 1 / 4 / 16 时 QPS 分别为 56.0–57.3 / 58.2 / 56.7–58.0，
  `exec` 14.6–15.1 ms —— 说明当前 read 阶段（每桶 start≈4.8 ms + scan≈1.0 ms，4 桶并行）
  **不是** ANN 的 Rayon 并行度受限，调线程数无收益。
- **结论**：接受，`temp → new`。剩余 exec ≈14.6 ms = build 4.8 ms（4 次串行
  `select commit_id`，每次 ≈1.15 ms）+ read ≈9.5 ms（桶内 5.9 ms + 并行开销）；下一步 R4
  计划把这 4 次 commit 解析合并成 1 次批量 PG 查询（保持每次查询看最新 commit 的语义），
  预计 build 4.8 → ~1.5 ms、QPS → ~70。

### R4 — 各桶 index commit 合并为一次批量解析（已提交 `11a78144`，+5.7%）

- **改动**：
  - `rust/lakesoul-metadata/src/index_catalog.rs`：新增
    `IndexCatalog::resolve_cached_many(&[prefix]) -> HashMap<prefix, Option<IndexCommitView>>`，
    用一条 `unnest($2::text[]) left join ... left join lateral(... limit 1)` 查询返回每个
    shard 的当前 commit（新鲜度契约与 `resolve_cached` 相同：每次调用都读当前 commit，
    只有本进程没见过的 commit 才去取 header/segments）；view 缓存与单 shard 版本共用。
  - `rust/lakesoul-metadata/tests/vector_index_catalog.rs`：新增
    `resolve_cached_many_matches_single_resolution`（两 shard 不同 commit + 缺失 prefix，
    断言批量结果与单 shard `resolve` 一致；已通过）。
  - `rust/lakesoul-datafusion/.../vector_search_exec.rs`：`group_files()` 拆出纯路径计算，
    `build_configs()` 先对所有桶做一次批量解析再逐桶构建。
- **结果**（R3b vs R4，3 轮交错）：QPS 57.59 / 58.04 / 57.37 → 60.92 / 59.85 / 60.89
  （**+5.7%**）；p50 17.2 → 16.5 ms；exec 14.56–14.78 → 13.72–14.07 ms；
  `build_ms` 4.8 → **3.55–3.62 ms**；RSS 5644–5980 → 5691–5839 MiB（不升）；Recall 不变。
- **分析**：预期 build −3 ms，实际只 −1.2 ms。把 4 次 `resolve_cached`（≈1.15 ms/次）换成
  1 次批量查询后仍剩 3.6 ms，说明 **`block_in_place` + `GLOBAL_RUNTIME.block_on` 的跨
  runtime 交接本身约 0.7–0.9 ms/次**，4 次串行交接（1 次解析 + 4 次逐桶配置构建）比 PG
  查询更贵。这也解释了此前 `resolve_ms≈1.15 ms` 而 PG 服务端实测只有 0.11–0.19 ms。

### R5 — 配置阶段只做一次 runtime 交接：解析+租约一次 block_on，配置构建改同步（实测中性）

- **改动**：`build_configs()` 在**一次** `block_in_place(GLOBAL_RUNTIME.block_on(...))` 内完成
  「批量解析 + 为 cache miss 的 shard 申请 lease」，`reader_config()` 变成**同步**函数
  （只做纯配置组装）；`deferred_payload_batches` 走同一路径。
- **结果**（R4 vs R5，3 轮交错）：old 52.80（首轮冷启动离群）/ 60.95 / 60.71，new 61.30 /
  59.71 / 60.77 → **QPS 无差异**（中位 60.71 vs 60.77）。`build_ms` 仍为 3.55–3.8 ms。
- **结论**：无独立可测收益，作为 R4 同一 commit（`11a78144`）内的结构简化保留
  （交接次数 5→1、配置构建不再需要 async）；若要求严格执行“无改进即回滚”，可单独
  revert 该结构改动（预期性能不变）。

### R6/R7 — 追查那 2.6 ms：`block_in_place` 交接成本（未解决，记录结论）

- R4/R5 的 `build_ms≈3.6 ms` 细分（临时计时）：`groups_ms≈0.014`、真实异步工作
  `work_ms≈0.77`（其中 `resolve_cached_many` 一条查询 0.31 ms + view 缓存循环 0.43 ms）、
  **`handoff_ms≈2.55–2.62 ms`**，即 `block_in_place + GLOBAL_RUNTIME.block_on` 的交接本身。
  （对照：同一条批量 SQL 在 psql 里 0.25–1.3 ms；`is_loaded` 4 次合计仅 0.009 ms。）
- R6：把交接内的 `GLOBAL_RUNTIME.block_on` 换成 `futures::executor::block_on`（外部 executor
  驱动 future）→ QPS 无变化（61.4/61.7/60.4 vs 61.3/61.5/60.5），说明成本在
  `block_in_place` 一侧，而不是 tokio `block_on`。
- R7：完全去掉 `block_in_place`（裸 `futures::executor::block_on`）→ 运行失败：
  `postgres pool error: Timed out in bb8`。连接池在无 tokio runtime 上下文时需要 reactor
  建连，因此不能简单脱离 runtime；该方向需要「把 setup 放进返回的 stream 里异步执行 +
  `spawn_blocking` 驱动阻塞段」的结构性改动（尚未实施）。
- 现状：该 2.6 ms 交接成本在 build 阶段一次、read 阶段一次（4 桶并行）≈ 合计约 5 ms，
  是单 query 剩余延迟里最大的一块。

2. **read 阶段桶内 `start≈4.8 ms`**：进一步拆分 reader 计划构建（key codec、locator 索引
   打开、fs scan 配置）与 ANN 搜索各自占比；这部分在 native reader 内，改动需要保持 Reader
   语义不变（只做等价优化）。
3. **每 query SQL/物理计划 ≈2.6 ms**：确认是否可在 plan 阶段复用 snapshot/listing；
   不做任何绕过 snapshot 语义的缓存。
4. **单 query 之外的批次 API（方案文档阶段 B）**：同一 snapshot 下多条 query 共享 shard
   加载与 reader 计划，把上述固定成本摊薄；这是“逼近 Rust core QPS”的主要手段，但需要在
   文档与 API 上明确“同一 snapshot”的一致性契约。

### R8 — 端到端 vs 纯 Rust：固定开销的量化（诊断）

**基准**：GloVe-200，4 bucket，nprobe 1 / 16 / 256（其余同第 1 节，每档 2 次 120-query，
用于斜率；后续标准测量统一 200 query）。

| nprobe | exec | p50 | Recall@100 |
|---:|---:|---:|---:|
| 1 | 13.1–13.5 ms | 15.7–16.3 ms | 0.2836 |
| 16 | 13.8–13.9 ms | 16.3–16.7 ms | 0.6335 |
| 256 | 14.8–15.1 ms | 17.3–17.8 ms | 0.9002 |

**结论**：nprobe 1→16（16 倍探测）只增加 0.6 ms，16→256（再 16 倍）再增加 1.4 ms ——
**ANN 本身只占 0.6–2.0 ms，端到端 16.2 ms 里约 15 ms（93%）是每 query 的湖仓协议固定开销**：

| 组成 | 耗时 | 性质 |
|---|---:|---|
| SQL 解析/分析/优化 | 1.16 ms | 每 query plan |
| 物理计划（snapshot 文件列表 + exec 构造） | 1.47 ms | 每 query |
| exec 配置阶段 | 3.4–3.6 ms | 真实工作 0.77 + `block_in_place` 交接 2.6 |
| exec 读 4 桶 | ~9.6 ms | 桶内 create 0.03 + start 4.8 + scan 1.0（并行）；其余≈3.7 为第二次交接 2.6 + join/合并 |
| 排序/投影 | ~0.3 ms | |

纯 Rust core 只调用 `index.search()`（内存索引、单 shard、无 SQL/reader/locator/MOR），
0.62 ms/query，所以看起来“没有固定开销”——它量的是 ANN，不是湖仓查询。
纯 Rust 16 worker 是单线程的 10×（1604→16239 QPS），说明**并发/批处理**是把固定成本摊薄的
主要手段；当前 e2e 基准是串行单 query，把全部固定成本都暴露在延迟上。

### R9 — 去掉两次 `block_in_place` runtime 交接（待验证）

- **改动**（`vector_search_exec.rs`）：`execute()` 不再在同步上下文里做 setup，而是把
  「解析 shard → 构建 reader 配置 → 读桶 → 排序」作为**返回的 DataFusion stream 的异步
  阶段**：catalog 查询在任务 runtime 上直接 `await`（无交接），只有 native reader 的阻塞段

  stream）；`read_buckets_blocking` 变成无 `self` 的关联函数，`deferred_payload_batches`
  复用第一阶段已解析的 views/leases（不再二次解析）。
- **预期**：省掉 2×2.6 ms 交接 → exec 13.6 → ~9 ms，QPS 61.8 → ~85。
- **门槛**：200 query × 3 轮交错、RSS 不升、Recall 不变；不达标即删 `temp` 并回滚。

### R13 — 批量走 provider（snapshot 一致）+ 安全校验跳过（已验证，默认 64）

  logical plan 1.07 ms + physical plan 1.44 ms —— 单条 SQL 的**每 query 规划/快照解析**
  已成为主项；下一步要么压缩这块，要么给单查询提供“同一快照多次查询”的显式入口。

### R18 — 批量入口按桶并行探测（已提交）

- **动机**：R17 的批量入口用 `try_join_all` 轮询 4 个桶 future，而每个桶的 `batch_search`
  是同步 CPU 工作——同一个 task 上 4 个桶实际一个接一个跑，profile 显示 1.15–1.2 ms/query
  的 CPU 只换来 **~5.3/16 核**（200 query 的 chunk 43 ms wall：probe 41 + merge 1.8）。
- **改动**：
  1. `lakesoul-io` 新增 `LoadedShard`（`search_batch` 同步、可跨线程调用）与
     `load_typed_shard`；DataFusion 侧先把 4 个 shard 一次性装好（缓存命中），再把每个桶
     放到自己的 OS 线程上「探测 + 排序」（每桶内部仍由 rayon 用满全池做 ANN）。
  2. 跳过校验时不再构建候选并集与 liveness 过滤（覆盖证明保证每个候选都是活行），
     省掉每 chunk ~7 ms 的 HashSet 开销。
  3. 跨桶合并按 query 切分到多个线程（`merge_query`）。
  4. 批量路径改用 typed shard 装载，不再每批把 ~1024 个 segment 序列化成 JSON 再解析。
- **实测**（bits=1、200 query、同一 harness 每版 6 次、构建/搜索分进程）：

  | 版本 | QPS（6 次） | 中位 | p50 | CPU/query | 查询期 RSS | Recall |
  |---|---:|---:|---:|---:|---:|---:|
  | R17（串行探测） | 4247 / 4350 / 4331 / 4144 / 4350 / 4332 | 4331 | 0.226–0.238 ms | 1.10–1.15 ms | 238–241 MB | 0.42035 |
  | **R18（按桶并行）** | 8469 / 7900 / 7837 / 8574 / 8777 / 8569 | **8512** | **0.110–0.124 ms** | 1.15–1.20 ms | 239–242 MB | 0.42035 |

  批量 **+96.5%**；p50 减半；CPU/query 不变、核利用率从 ~5.3/16 提到 ~13–15/16；
  RSS 不变；Recall 不变。
- **桶级 profile**（`LAKESOUL_VECTOR_SEARCH_PROFILE=1`）：chunk(200 query) =
  load 1.05 + probe 17.0 + merge 0.87 ≈ 19 ms；单桶 `search_ms≈15.2`（ANN，rayon 全池）、
  `rank_ms≈3.2`。本轮试过再把 rank 切到 4 个子线程：rank 降到 1.45 ms，但 QPS 中位
  7034 且 6–9 k 抖动 → **按回滚规则撤掉**，只保留“按桶并行”。
- **强制校验路径复测**：`LAKESOUL_VECTOR_BATCH_FORCE_VERIFY=1` → 1090–1191 QPS、
  p50 0.84–0.92 ms、CPU/query 4.1 ms、RSS 385–394 MB、Recall 0.42035
  （与跳过校验完全一致，说明并行化没有改变结果）。
- **结论**：批量入口 CPU/query ≈ 1.15 ms，其中约 1.1 ms 就是 4 个 shard 的 ANN 本身
  （≈0.275 ms/query/shard 单线程），SQL/DataFusion 侧附加开销已压到 ~5%。纯 Rust 口径上限
  约 200×1.15 ms/16 核 ≈ 14 ms/chunk ≈ 14 k QPS，当前 8.5 k ≈ 60%，其余是每 chunk 固定
  成本（load 1.05 + merge 0.87 + probe 尾巴）与 provider 每批的 list/snapshot 开销。
  再往上要么动 nprobe/bits（按用户要求不动），要么优化索引内核本身。

### R19 — 单查询按 shard 并行探测 + 命中缓存时跳过 segment 转换（已提交）

- **动机**：R17 的单查询快路径在每个 shard 上串行调用 `search_typed_shard`；`LAKESOUL_VECTOR_SEARCH_PROFILE=1`
  的分解显示 exec 2.8 ms 里 **resolve 0.69 + 4 个 shard 的装载/搜索 1.77**（每 shard 0.44 ms，
  其中 ANN 只有 0.1 ms），顺序等待纯属浪费；装载阶段还有 `segment_entries`（~1024 条）克隆 +
  header 反序列化，命中缓存时本该完全跳过。
- **改动**：
  1. 单查询快路径先把 4 个 shard 从缓存装好，再用 `std::thread::scope` 并行探测
     （`LoadedShard::search_batch` 是同步的，可跨线程），`probe` 从 1.77 ms 降到 0.32 ms。
  2. `lakesoul-io` 新增 `cached_typed_shard`（配合 `cache::get_loaded`）：缓存命中时直接拿
     `Arc<LoadedVectorShard>`，不再克隆 segment 列表、不再解析 header；`LoadedVectorShard`
     记录 `key_kind`，布局变化时命中失效。批量入口同样改用它，只有冷启动才走
     `segment_entries` + `load_typed_shard`。
- **实测**（bits=1、200 query、同一 harness、构建/搜索分进程）：

  | 版本 | 单 query QPS | 单 p50 | 单 CPU/query | 查询期 RSS | 批量 QPS | Recall |
  |---|---:|---:|---:|---:|---:|---:|
  | R17 基线 | 183.3（2 次 181.9/184.8） | 5.24–5.29 ms | 4.90–4.95 ms | 235–236 MB | 4331（6 次中位） | 0.42035 |
  | R19a 并行探测 | 204.4–207.3（5 次） | 4.64–4.69 ms | 5.05–5.15 ms | 233–236 MB | 8512（6 次中位） | 0.42035 |
  | **R19b + 缓存命中直取** | **226.8 / 233.1 / 227.4** | **4.08–4.18 ms** | **4.55–4.65 ms** | **233–237 MB** | **8816 / 8890 / 8950** | 0.42035 |

  单查询相对 R17 **+24%**（相对最初 reader 路径 61.3 QPS 为 **3.7×**）；批量相对 R18 再 **+4.4%**；
  p50 5.26 → 4.1 ms；RSS 不变；Recall 不变。
- **profile**（单查询，p50）：resolve 0.79 + load 0.68 → `probe` 0.32，exec 内部合计 1.93 ms；
  剩下的 4.1 ms 里 logical plan 1.07 + physical plan 1.44 已是主项 —— 每条 SQL 都要重新解析
  快照与列文件，这是单查询继续提升的下一步（需要“一个 statement 固定 snapshot 的多次查询”
  入口或快照缓存策略）。
- **回滚**：`LAKESOUL_VECTOR_INDEX_ONLY=0` 仍可强制回 reader 路径；本轮无强制校验语义改动。

### R20 — 缓存命中不再克隆 segment 视图 + 批量只解析一次 shard（已提交）

- **动机**：R19 之后单查询 4.1 ms 里 `exec` 的 resolve 仍要 0.75–0.9 ms，批量入口每批 resolve
  1.08 ms；但同一次 profile 里 PG 侧同类查询（`get_all_partition_info`）只要 0.2 ms。原因是
  `resolve_cached_many` 命中 `VIEW_CACHE` 后仍然 `clone()` 整个 `IndexCommitView`——每个 shard
  约 1024 条 segment（每条含 filename + data_files 字符串），4 个 shard 每次查询要克隆几千个
  小对象。另外批量入口在 `adaptive_batch_size` 和 chunk 里**各解析一次** shard，等于每批两次
  PG 往返。
- **改动**：
  1. `IndexCatalog::resolve_cached_many` 返回 `HashMap<String, Option<Arc<IndexCommitView<S>>>>`：
     缓存里存的就是 `Arc`，命中只做 Arc 克隆 + 类型下行，不再克隆 segment 列表；冷未命中才
     构建一次并共享。文本/ES 走的是单 shard 的 `resolve_cached`，行为不变。
  2. 批量入口每次调用只解析一次 shard，把 `views`/`buckets` 传给各个 chunk（原来 chunk 内再解析一次）。
  3. 批量合并线程数扫了 8（7839/7288 QPS，比默认更差）→ 保持默认全核，相关 env 旋钮删除。
- **实测**（bits=1、200 query、同一 harness、构建/搜索分进程）：

  | 版本 | 单 query QPS | 单 p50 | 单 CPU/query | 批量 QPS | 查询期 RSS | Recall |
  |---|---:|---:|---:|---:|---:|---:|
  | R19 | 226.8 / 233.1 / 227.4 | 4.08–4.18 ms | 4.55–4.65 ms | 8816 / 8890 / 8950 | 233–241 MB | 0.42035 |
  | **R20** | **264.3 / 269.1 / 273.5** | **3.43–3.54 ms** | **3.95–4.05 ms** | **8612 / 9466 / 9935** | **233–238 MB** | 0.42035 |

  单查询 **+17%**（相对最初 reader 路径 61.3 QPS 为 **4.4×**），批量中位 **8890 → 9466（+6.5%）**，
  p50 3.43–3.54 ms，RSS 略降，Recall 不变。
- **剩余**：单查询 3.4 ms = logical plan 1.07 + physical plan 1.44 + exec ~0.9
  （resolve ~0.2 + load/probe/rank ~0.7）；批量 CPU/query 1.05–1.1 ms 已基本等于 4 个 shard 的 ANN。

### R21 — 批量：探测与排序分阶段（排序铺满全部核）（已提交）

- **动机**：R20 的批量快路径让"每个桶一个线程"同时做 ANN 与排序。探测阶段 rayon 已经能用满
  16 核，但紧随其后的**逐 query 去重 + 主键解码**只能在每桶单线程上跑（4 个桶 = 4 核），
  16 核里有 12 个在那段时间空转。profile 也显示每桶 `rank_ms≈3.2` 串行在 `search_ms` 之后。
- **改动**：快路径拆成两个阶段——阶段 1 仍按桶并行探测（返回原始 hits）；阶段 2 把
  4×200 个「桶×query」单元按 query 切分到全部核上做去重/解码（新增 `rank_buckets`，
  `rank_query` 从 `rank_bucket` 拆出复用）。校验路径不变。
- **实测**（bits=1、200 query、两版各 6 次交错、构建/搜索分进程）：

  | 版本 | QPS（6 次，升序） | 中位 | Recall | 查询期 RSS |
  |---|---:|---:|---:|---:|
  | R20 | 6463 / 7346 / 7596 / 9178 / 9317 / 9844 | 8387 | 0.42035 | 237–240 MB |
  | **R21** | 8572 / 10859 / 10890 / 10997 / 11038 / 11117 | **10943** | 0.42035 | 237–240 MB |

  批量中位 **8387 → 10943（+30.5%）**，最小值也超过 R20 的中位；p50 0.107 → 0.089–0.093 ms；
  CPU/query 1.1–1.25 ms 基本不变（省下的是并行度），RSS 不变，Recall 不变。
- **profile**（200 query/批）：chunk 21.5 ms = load 0.18 + probe 20.4 + merge 0.89；单桶
  `search_ms≈18.5`（4 桶并行、rayon 全池）、新的 `rank_ms=1.29`（16 核，此前约 12.8 ms CPU
  只铺 4 核）。探测本身 18.5 ms vs 理想 13.75 ms（220 ms CPU/16 核），即 ANN 阶段并行效率
  约 73%，剩下的差距主要是 SIMD/内存带宽与频率，不是调度。

### R22 — 批量：排序与跨桶合并融合（已提交）

- **动机**：R21 之后 chunk = load 0.18 + probe 20.4 + **merge 0.89 ms**，merge 是独立的并行区
  （200 个 query 各合并 4×100 候选），和排序阶段各自 spawn 一次线程，光 spawn 就约 0.5 ms。
- **改动**：快路径把「按桶排序（去重 + 主键解码）」与「跨桶 top-k」融合成单个按 query 的并行区
  （`rank_and_merge` / `merge_one_query`），不再有独立合并阶段；校验路径不变。
- **实测**（bits=1、200 query、同一 harness 各 6 次）：

  | 版本 | QPS（6 次，升序） | 中位 | p50 | Recall | RSS |
  |---|---:|---:|---:|---:|---:|
  | R21 | 8572 / 10859 / 10890 / 10997 / 11038 / 11117 | 10943 | 0.089–0.093 ms | 0.42035 | 237–240 MB |
  | **R22** | 10867 / 11078 / 11164 / 11248 / 11280 / 11376 | **11206** | 0.086–0.092 ms | 0.42035 | 237–240 MB |

  中位 **+2.4%**，且抖动收窄（最小值 8572 → 10867）；最终二进制再测 4 次：
  11224 / 11733 / 11793 / 9359（中位 11478）。CPU/query 1.1–1.25 ms 不变，RSS/Recall 不变。

### 纯 Rust 参考场景（新增 `--scenario rust-shard-batch`）

- **目的**：把"手写 Rust 跑同一批 shard、同一批 query"作为天花板，直接回答"DataFusion 路径离
  纯 Rust 还有多远"。场景用 catalog 直接加载表里的 4 个 shard，按「每 shard 一个线程调用

- **实测**（bits=1、200 query、nprobe 16、top_k 100、16 rayon 线程、3 次）：

  | 指标 | 纯 Rust 参考 | DataFusion 批量入口（R22） |

### R23 — 向量扫描路径复用不可变 partition 版本的文件列表（已提交）

- **动机**：单查询 3.4–3.5 ms 里 physical planning 还有 1.44–1.54 ms，其中
  `list_files_for_scan` 每次查询都要重新做 2 次 PG 查询 + 每个文件一次 HEAD（meta 0.18 +
  list 0.31 ms）。而 `partition_info(partition_desc, version)` 一旦发布就**不可变**：同一版本的
  数据文件永远不会变，列表结果完全可以复用。
- **改动**：只给**向量扫描路径**新增 `LakeSoulTableProvider::list_files_for_vector_scan`：仍然每次
  查询都重新解析当前 partition 版本（`get_all_partition_info`，保证 snapshot 新鲜度），但
  `(table_id, partition_desc, version)` 的文件列表（含 partition values）走进程内 LRU（512 项，
  约 0.5 MB 上限，按版本号失效）。普通扫描/文本索引扫描仍走原来的 `list_files_for_scan`，
  湖仓原有的列表/快照语义一点没动。
- **实测**（bits=1、200 query、同一 harness、6 次/3 次）：

  | 版本 | 单 query QPS | 单 p50 | physical plan | 单 CPU/query | 批量 QPS | Recall | RSS |
  |---|---:|---:|---:|---:|---:|---:|---:|
  | R22 | 264–274（中位 269） | 3.43–3.54 ms | 1.44–1.54 ms | 3.9–4.05 ms | 11206（中位） | 0.42035 | 233–240 MB |
  | **R23** | **290 / 296 / 301 / 301 / 301 / 302（中位 301）** | **3.12–3.20 ms** | **1.13–1.17 ms** | **3.65–3.8 ms** | **11421 / 11547 / 11903（中位 11547）** | 0.42035 | 234–238 MB |

  单查询 **+10%（301 QPS）**，physical planning 正好省下 0.3 ms；批量 **+3%**；
  p50 3.5 → 3.15 ms；Recall/RSS 不变。

### R24 — 批量排序零拷贝解码 + 单查询并行取缓存句柄（已提交）

- **动机**：R23 的批量排序里，每个「桶×query」都对去重后的候选 key 做一次 `clone()` 再解码
  （200 query × 4 桶 × ~100 key ≈ 8 万次分配/批）；单查询快路径的 4 个 `cached_typed_shard`
  是顺序 await，而它们只是 4 次 moka 读。
- **改动**：
  1. `KeyCodec::decode_refs(&[&IndexKey])`：排序时把 BTreeMap 里借用的 key 直接交给 codec 解码，
     不再为每个候选克隆一个 `IndexKey`；批量的 `rank_query` 改用它。
  2. 单查询快路径先做完 4 个 shard 的覆盖证明，再用 `futures::future::join_all` 并行取 4 个
     已加载句柄（命中只是一次 moka 读），冷 shard 仍在 miss 分支里加载。
- **实测**（bits=1、200 query、交错 6 次/版）：

  | 版本 | 单 query QPS（4 次中位） | 批量 QPS（6 次，升序） | 批量中位 |
  |---|---:|---:|---:|
  | R23 | 290 | 11138 / 11319 / 11347 / 11422 / 11602 / 11958 | 11384 |
  | **R24** | 292（±噪声） | 9922 / 11399 / 11597 / 11879 / 11888 / 11975 | **11738（+3.1%）** |

  单查询在噪声内持平；批量中位 +3.1%（均值被一次 9922 的离群值拉平，剔除后 +2.5%），
  CPU/query、RSS、Recall 均不变。属于"小而确实"的清理型优化。

### 硬件上限复核（本轮结论的重要背景）

`lscpu` 显示本机是 **KVM 虚拟机：8 个物理核 / 16 个超线程（SMT2）**，并非 16 物理核。因此：

- 之前按"16 物理核"算出的 ANN 并行效率（73%）其实低估了自己；
- 实测 `RAYON_NUM_THREADS=8` 的批量只有 **8.8–9.5k QPS**，`=16` 是 **11.6–11.7k**（SMT 带来约 +28%），
  说明 16 线程确实还在线性收益区；
- 按"每批 200 query、CPU/query 1.05 ms"折算：批量端到端 17.1 ms ≈ **13.2 个逻辑核**在跑，
  而纯 Rust 参考场景的检索段 ≈ 14.5 个 —— 也就是说 DataFusion 批量路径的检索阶段已达纯 Rust
  同一流程的 **约 91%**，端到端（再算上合并/列文件/index 解析）**优于**纯 Rust 参考流水线
  （11.7k vs 10.7k）。批量路径基本到硬件上限，剩下的是每批约 2 ms 的固定成本。

### 3.1 最终实测（HEAD `4e1da05c` 构建的 `new` 二进制，bits=1、GloVe-200、200 query、index-only、构建/搜索分进程）

| 快照批量入口（200 query/快照） | 8489* / 9776* / 11457 / 11753 / 11819 / 12022 | **11605** | 0.080–0.114 ms | 1.0–1.15 ms | 237–238 MB | 0.42035 |

`*` 为机器后台负载导致的离群值（同批其它 4 次都在 11.5–12.0k）。会话开始（同 bits=1 基线）为

### 3.2 与纯 Rust 天花板（同一 4-shard 布局、同一 200 query、`--scenario rust-shard-batch`）

| 指标 | 纯 Rust 手写流程 | DataFusion |
|---|---:|---:|
| 检索段 QPS（3 次） | 13656 / 14039 / 14338（中位 **14039**） | — |

结论：**批量入口端到端 = 纯 Rust 检索段的 83%、纯 Rust「检索+合并」的 108%**；单 query SQL 的

### 3.3 单查询并发伸缩（补充结论）

### R25 — 单查询：按快照文件集复用已解析的 shard（已提交）

- **动机**：R24 之后单查询 3.15 ms 的构成是 logical plan 1.13 + physical plan 1.22 + exec 1.05，
  而 exec 里 **resolve（查 index 提交）0.305 ms + 装载 4 个 shard 句柄 0.201 ms** 每个 query
  都要重做一次 —— 但同一条 SQL 语句模板在同一个快照上会连续执行很多次（GloVe 压测就是 200 次），
  快照没变时这两步的结果完全一样。
- **关键观察（为什么可以复用）**：向量扫描的 exec 是**按 planning 阶段的文件组**构造的，
  数据文件不可变 → **同一组文件 = 同一批行**；数据提交会新增/替换文件 → 文件组变化 → 键不同 →
  自动 miss。因此把「这个文件集对应的 index 提交视图 + 已加载 shard」按文件集缓存是快照语义内的。
- **安全阀**：缓存命中后**仍然逐 shard 重跑覆盖证明**（`can_skip_verification`：无 mutation 链、
  无 CDC 列、`covered == active files`，且校验缓存里的 prefix 顺序与本次文件组一致），证明不成立
  就回落到 reader 路径；`LAKESOUL_VECTOR_SNAPSHOT_CACHE=0` 可整体关闭（A/B 用）。
- **改动**：
  1. `LakeSoulVectorSearchExec` 增加进程内快照缓存（键 = object_store_url + key layout + 搜索列/度量/
     排序 + 分组文件路径；最多 2 个快照、总预算 512 MB，只持有 `Arc` 引用不复制索引）；
     命中时跳过 resolve + 装载。
  2. 缓存条目里预存「去重后的 covered 文件名」，覆盖证明不再从每个 shard 的 ~1024 条 segment
     里重建集合（原来每次 4×1024 次哈希）。
  3. 4 个 shard 的探测改为提交到共享的 `GLOBAL_RUNTIME` blocking 池（线程已预热），
     不再每个 query 新建 4 个 OS 线程。
- **实测**（bits=1、200 query、同一二进制内 A/B、6 次）：

  | 配置 | 单 query QPS（6 次，升序） | 中位 | p50 | exec 均值 | CPU/query | RSS | Recall |
  |---|---:|---:|---:|---:|---:|---:|---:|
  | 关闭缓存（≈修改前） | 291 / 296 / 296 / 297 / 299 / 302 | 296 | 3.12–3.23 ms | — | 3.65–3.75 ms | 233–235 MB | 0.42035 |
  | R25a 仅快照缓存 | 308 / 314 / 320 / 320 / 323 / 324 | 320 | 2.91–2.97 ms | 0.69–0.77 ms | 3.6–3.75 ms | 232–235 MB | 0.42035 |
  | **R25 全部（+covered 预存 + blocking 池探测）** | **332 / 339 / 341 / 345 / 347 / 347** | **343** | **2.72–2.86 ms** | **0.50–0.53 ms** | **3.35–3.5 ms** | **232–234 MB** | **0.42035** |

  单查询相对会话内上一个基线（298 QPS / 3.15 ms）**+15%**，p50 3.15 → 2.74 ms，exec 1.05 →
  ~0.51 ms，RSS 不升、Recall 逐位不变；批量入口不受影响（10.8–11.7k，属噪声）。
  相对最初 reader 路径（61.3 QPS / 16.0 ms）现为 **5.6× / 5.8×**。

### R31 — planner 剩余成本的归因（两个假设再次被证伪，已回滚）

- **背景**：R30 的折叠把 logical optimizer 从 0.82 降到 0.31 ms；再对改写后的 plan 优化只要
  0.03 ms，说明剩下的 0.31 ms 在「第一次 optimize 对 analyzer 产出 plan 的处理」上。200 维与
  2 维查询的 optimizer 差 0.16 ms，怀疑与 marker 里的 2.6 KB CSV 或不变量检查有关。
- **诊断增强**：`plan-probe` 现在额外测量「对已优化 plan 再 optimize 一次」的耗时
  （`logical_optimizer_again`）并打印当前 optimizer 规则顺序，便于确认规则插桩是否生效。
- **两个尝试（均实测无收益、已回滚）**：
  1. **marker 只携带句柄**（`@q<hex>` + 进程内 registry，`LAKESOUL_MARKER_HANDLE=0` 可关）：
     6+6 次交错 A/B，句柄 494 QPS vs 字面量 500 QPS（中位），**无收益**。原因：句柄只在
     *optimizer 的 pushdown 改写时*才生成，而成本发生在**改写之前**对 analyzed plan 的处理
     （那时 plan 里仍是 200 值 list 字面量）。
  2. **pushdown 规则前置**（`LAKESOUL_PUSHDOWN_RULE_FIRST`，已用 probe 打印确认规则确实位于
     index 0/1）：optimizer 0.313 → 0.326 ms，**无收益**，同上原因。
- **结论**：那 0.16 ms 属于 optimizer 对 analyzed plan 的**规则前处理**（不变量检查/plan 签名）
  及对 200 值字面量的改写克隆，靠 marker 编码或规则顺序都去不掉；要消除它必须让 **analyzed
  plan 本身**只带小载荷（即 analyzer 阶段就把 `array_distance(col, ARRAY[…])` 换成携带句柄的
  内部距离 UDF）——预计 ~8%，但需要改 pushdown 规则的匹配/测试，复杂度高，本轮未做。
- **当前单查询下界（保持"每条语句读最新快照"语义）**：parse 0.21 + analyze 0.59 +
  optimizer 0.33 + planner 0.19 + exec 0.51 ≈ 1.83 ms，其中 **0.40 ms 是两次元数据 PG 查询**
  （表信息 0.215 + 分区信息 0.18）。再去掉只能靠新鲜度策略或固定快照入口。
- **回归确认**：回滚后单查询 487–489 QPS / p50 1.86–1.91 ms、批量 11.6–12.0k、Recall 0.42035、
  RSS 233 MB —— 与 R30 基线一致。

- **测试**：新增 3 个 analyzer 规则单测（改写成句柄调用、IP metric 保留、非常量不动）+ 2 个 UDF
  单测（句柄往返、求值结果与内置函数相差 < 1e-12）；`lakesoul-datafusion --lib` **192 项全绿**。
  端到端等价性：exact-rerank 模式 Recall 在「句柄改写」与「list 字面量」两种实现下**完全相同**

- **实测**（bits=1、200 query、同一二进制 12+12 次交错 A/B）：

### R36 — 元数据客户端读锁并发化：单查询并发吞吐 2.5×（已提交）

- **动机**：R35 验收发现单查询并发 c=4 只有 770 QPS、c=8 831 QPS，而每 query CPU 只有 2.4 ms
  （8 并发 × 2.4 ms = 19 ms CPU，却跑了 9.6 ms 墙钟 → 机器没吃满），说明存在串行点。定位到
  `MetaDataClient`/`IndexCatalog` 里的 `Arc<Mutex<PooledClient>>`：**进程内所有元数据查询（含
  纯读）被同一把互斥锁串行化**，每条语句的两次元数据查询（表信息 + 分区信息）以及索引 resolve
  都要排队。
- **改动**：把 `Arc<Mutex<PooledClient>>` 换成 `Arc<tokio::sync::RwLock<PooledClient>>`：
  - **纯读路径**（`execute_query`、`resolve` / `resolve_cached` / `resolve_cached_many`、
    `list_shards_under` 等）取 `.read()`，多个语句的读查询可以真正并行；
  - **写路径**（insert/update、DDL `init_tables`、lease 增删续、commit/`try_commit`、事务体、
    `delete_shard` 等）取 `.write()`，保持与原来一样的独占性（比原来更强：写入现在也不会与读并发）；
  - 锁的**粒度不变**（仍是一条语句/一次查询持有，多步操作原本就在步骤之间释放锁），因此没有削弱
    任何原子性契约；语句缓存（内部已有 RwLock）与 bb8 连接池本身都是并发安全的。
- **实测**（bits=1、GloVe-200、同一二进制 A/B、顺序 8+8 次 + 并发）：

  | 场景 | 改动前 | 改动后 | 变化 |
  |---|---:|---:|---:|
  | 顺序单查询 | 509 QPS / p50 1.814 ms | **526 QPS / p50 1.770 ms** | +3.3% |
  | 并发 c=4 | 770 QPS / p50 4.51 ms | **1,221 QPS / p50 2.74 ms** | **+59%** |
  | 并发 c=8 | 831 QPS / p50 8.10 ms | **2,068 QPS / p50 2.91 ms** | **+149%** |
  | 并发 c=16 | 约 415（R25 时） | **2,496 QPS / p50 4.43 ms** | **6×** |

  批量路径不受影响（200 query 11.5k、10k query 13.6k）；Recall 0.42035 不变。
- **测试**：`lakesoul-datafusion --lib` 192 项全绿；`lakesoul-metadata --lib` 23/24（唯一失败仍是
  既有的 `jwt::tests::test_verify_token_expired` 定时炸弹，与本改动无关）。

### R37 — 并发调度实验三则（一项保留、两项回滚）

R36 之后顺序单查询 ~526 QPS、c=8 2,068 QPS、c=16 2,518 QPS。本轮继续压并发，做了三个实验：

### R39 — 重排（`rerank=exact`）的存储向量 payload 缓存（已提交 `98c63bce`）：3× QPS、3× 低 RSS

（目标："持续优化重排的 QPS，同时降低重排 RSS；不改变湖仓一体的特性；每次测完清理无关索引/缓存"。）

**问题定位**：R38 的拆解（使用说明 §12）显示 exact 的时间几乎全在 `pk_locator::take_rows`（每桶
45–66 ms/查询）：候选行随机散布在桶文件里，Vortex 按 chunk 解码，1000 个候选几乎覆盖整列向量
（4 桶 ≈ 944 MB/查询）。ANN 只有 ~1.5 ms/桶，DataFusion 精确距离+Sort ~1 ms，reader 计划 1.8 ms。
所以在这条路径上继续改执行计划/引擎没有空间，必须改变"候选行向量从哪里读"。

**改动**（`98c63bce`，新增 `rust/lakesoul-io/src/pk_locator/payload.rs`，`pk_locator.rs` 只加挂载点）：
- 按（数据文件, 向量列）把存储向量按**行序原样**写成一份本地 payload 文件（f32/f64，首查懒构建，
  跨进程复用）；候选行取回改为 `pread` 只读命中的 800 B/行（1000 行 = 800 KB），不再解码整列；
- 主键列由 locator 自己的 mmapped key index（arrow-row 编码）直接解码，**完全不打开数据文件**；
- 只在"投影列 ⊆ 主键列 ∪ 存储向量列"、数据文件为单有序段、格式为 Vortex 时启用，否则回退原路径；
- 纯派生缓存：数据文件不可变，文件名 hash location、头部再带 location/列布局指纹，条目不可信即重建；
  目录预算默认 16 GiB，超预算回退；删目录即回收；
- 开关：`LAKESOUL_VECTOR_RERANK_CACHE=1`（默认关）、`LAKESOUL_VECTOR_RERANK_CACHE_DIR`、
  `LAKESOUL_VECTOR_RERANK_CACHE_BYTES`。

**结果**（GloVe-200、1,183,514×200d、bits=1、nlist=1024、nprobe=16、top_k=100、4 hash bucket、
构建/搜索分进程、200 条真实 query、**同一二进制** `035090ba…`）：

| 配置 | QPS | p50 | p99 | Recall@100 | 查询期 peak RSS | 单次 take/桶 |
|---|---:|---:|---:|---:|---:|---:|
| exact，缓存关（对照） | 15.8 | 61.9 ms | 89.2 ms | 0.64015 | 1093 MB | 45–60 ms |
| exact，缓存开（冷启动，含构建） | 46.6 | 21.2 ms | 23.2 ms | 0.64015 | 484 MB | — |

- 收益：QPS **3.0×**、p50 **2.9×**、查询期 RSS **3.1× 低**，Recall **完全不变**（0.64015）；
- 4 个 payload 共 903 MB，冷启动多花 **0.66 s**（wall 5.17 s vs 热 4.51 s），之后每进程直接打开；
  按 41 ms/query 的节省算，**约 16 条查询**回本，单条 ad-hoc 查询不建议开；
- index-only 不经过该缓存（投影只有主键），复核 495 QPS 与历史 524–526 的差异在机器噪声内。

**被证伪的中间方案**（都已回退，只留记录）：
1. `mmap` 随机读、不重置：QPS 47.3、p50 20.8 ms，但 200 条查询把 236 MB/文件的页几乎全部 fault
   进来，peak RSS 反而升到 **1250 MB**（文件页计入进程 RSS）；
2. `mmap` + 每次 take 后 `MADV_DONTNEED` 重置：RSS 574 MB，但内核按页表扫描整个映射，QPS 掉到
   **39.9/39.2**、p50 24.8/25.2 ms；
3. `mmap` + 每 2048 行重置一次：QPS 40.9/41.6/41.6、RSS 866–876 MB（重置后重新 fault 的成本仍在，
   峰值反而更高）；
4. 最终选 `pread`：QPS 46.5–47.1、RSS 354–361 MB，两个指标同时最好（读入的页只进 page cache，
   不计入进程 RSS）。这也是本轮的最终实现。

**测试**：`lakesoul-io --lib` 193 项全绿（含新增 `payload_round_trip`：手工写 payload 文件后校验
行序取回、List/FixedSizeList 两种输出类型、行数/指纹不符时拒绝）。

**后续可做**（下一轮候选）：① 批量精确重排入口（一次快照 + 一次 payload 读摊薄到整批，
潜力数千 QPS）；② payload 改 f16（磁盘 903 MB → ~452 MB，召回需复测）；③ 索引构建时预生成 payload
（把 0.66 s 冷启动前移）；④ exact 剩余 21 ms 的拆解（候选数 1000/桶 的 ANN 解码 + merge + 排序）。

### R41 — 重排改为底层 Rust 直读实现：index-only 的 52–60%，同召回 19.7×（已提交 `3c49c107`）

**用户问**："重排序是否可以用底层的 rust 实现，重排序的 QPS 至少要达到 index-only 的 50–60%？"
→ **可以，已实现并达标**：同召回（0.6419）下 **310.9 QPS = index-only（519 QPS）的 60%**。

**改动**（exec 内新增 exact 直读快路径 `exact_batches_inner`，完全跳过每桶 reader / 物理计划 / merge）：
1. 复用 index-only 的 snapshot 解析、覆盖性证明与并行 probe（重构出 `expected_snapshot`、`probe_shards`）；
2. 每个桶的候选 key 直接交给 pk_locator 新增的 `VectorBlockSource`：在 payload 缓存 + mmapped

### R42 — 批量入口的精确重排（已提交 `0ac706a3`）：5.7k–6.1k QPS，批量 index-only 的 44–53%

**用户要求**："之后再测一下批量检索的重排的 QPS。" 批量入口（snapshot batch）此前只输出
index-only 排序，没有重排能力；本轮补上并给出实测。

**改动（`0ac706a3`）**：`VectorBatchRequest` 新增 `exact`、`exact_overfetch`。exact 模式下：

### R43 — 批量 exact 的取向量量化：10k query 6.1k→6.3k，并定位到 pread 系统调用（已提交 `682ce3f4`）

**背景**：R42 的批量 exact 在 10k query 时只有 index-only 的 44%。profile（每 chunk = 1024 query）
显示 probe 74–165 ms、rank_merge 201–241 ms（其中 fetch 180–211、merge 16–32）。

**改动**：
1. `payload::PayloadView::score_rows` + `pk_locator::VectorBlockSource::score_keys`：候选行按行号
   直接 `pread` 到复用缓冲、8 路累加**就地**算 L2/IP，**不再为每个 query 构造 Arrow ListArray**
   （省掉每个 chunk 4096 次的 80 KB 分配与拷贝）；批量 exact 改走该入口。
2. 批量合并（跨桶 top-k）按 query 分块并行（原单线程 25 ms/chunk → 13–20 ms）。
3. **被证伪并回退**：把每个 shard 的 query 再拆 4 段并行 probe（想用满 16 核）——实测 probe 仍是
   74–95 ms/chunk（`search_batch` 内部已并行，拆分只加固定开销），且 200-query 批量回退约 5%
   （5,658 → 5,402）。已回退，保留"每 shard 一次调用"。

**结果**（同表同参数，200/10k 条真实 query；index-only 同机对照）：

|---|---:|---:|---:|---:|
| 批量 200q exact np=32/of=1 | 5,658 | **5,865（+3.7%）** | 0.6419 | 281 MB |

**瓶颈定位**：批量 exact 的每 query CPU ≈ 2.5 ms，构成为：
- 候选行取回（每 query 400 次 `pread`：4 桶 × 100 行）≈ **2.0 ms（约 80%）**；
- ANN probe ≈ 0.07 ms/query（分片内部已并行）；
- 就地打分 + 跨桶合并 + 解码 ≈ 0.2 ms。
即现在受**"每个候选行一次 `pread`"的系统调用开销**（~2–5 µs/次）限制，而不是算力。

① payload 用 mmap 随机读（页错误 ~0.3–0.5 µs vs syscall ~2–5 µs）：预计 fetch 2.0 → 0.6–0.9 ms，

   需要周期性 `MADV_DONTNEED` 控制峰值；
② payload 常驻内存（opt-in）：fetch 降到 ~0.05 ms/query，批量逼近 probe 上限（~13k），RSS +944 MB。
两者都是"吞吐 vs 内存"，默认保持 pread（低 RSS）。

**测试**：`lakesoul-io --lib` 193 项、`lakesoul-datafusion --lib` 192 项全绿。

### R44 — mmap 读 payload 被证伪并回滚：RSS 无法满足"不增长"

**背景**：R43 定位到批量 exact 的每 query CPU ~2.5 ms 中约 80% 是"每个候选行一次 `pread`"的
系统调用开销。按用户选择试做 opt-in mmap 模式（`LAKESOUL_VECTOR_RERANK_CACHE_MMAP=1` + 驻留窗口
`..._MMAP_WINDOW_BYTES`，超窗口 `MADV_DONTNEED` 重置），目标是在可控 RSS 增量内提速。用户随后
明确要求：**RSS 最好不要增长；达不到 RSS 要求就回滚**。

**实现与实测**（GloVe-200、bits=1、top_k=100、4 桶、10k/200 条真实 query）：

| 配置 | QPS | Recall | 查询期 peak RSS | 相对 pread 基线 |
|---|---:|---:|---:|---:|
| pread（基线，热） | 6,253–6,291 | 0.6686 | **399–408 MB** | — |
| mmap，窗口 64 MB | 6,818 | 0.6686 | 1,299 MB | RSS **+225%** |
| mmap，窗口 256 MB | 6,319 | 0.6686 | 1,305 MB | +225% |
| mmap，窗口 16 MB | 5,946 | 0.6686 | 1,253 MB | +212% |
| mmap，窗口 8 MB | 5,610 | 0.6686 | 1,118 MB | +178% |
| mmap，窗口 4 MB | 5,080 | 0.6686 | 963 MB | +140% |
| mmap，窗口 1 MB | 4,223 | 0.6686 | 868 MB | +117% |
| pread，200 query | 5,454 | 0.6419 | 279 MB | — |
| mmap（64 MB），200 query | 5,889 | 0.6419 | 1,161 MB | +316% |

payload 换到真实磁盘（`/tmp`）后规律相同（pread 5,228 QPS / 472 MB vs mmap 6,074 QPS / 1,171 MB）。

**根因**：Linux 缺页的 fault-around 会一次性把 64 KB（16 页）映射进进程页表，而 payload 文件已
全部在 page cache 里，于是"随机读一行"实际把相邻 16 页计入 RSS；payload 每文件 236 MB、4 个文件
共 944 MB，批量 10k 时几乎全部被映射。窗口缩小只能靠**更频繁的 `MADV_DONTNEED`**（重置代价随已映射
页数增长）来压峰值，压缩到 1 MB 窗口时 RSS 仍 868 MB，而 QPS 反而比 pread 低 33%。也就是说，
mmap 在这个数据规模上**要么快 8–13% 但要 2–3 倍 RSS，要么 RSS 接近可用但比 pread 更慢**，
没有满足"RSS 不增长"的可行点。

**决定**：按约定**回滚**（`git checkout` 撤销 mmap 改动，未提交）。回滚后复核：批量 10k
6,253–6,291 QPS / p50 0.156–0.157 ms / recall 0.6686 / **peak RSS 399–408 MB**；批量 200 query
5,454 QPS / 279 MB；单查询 exact 311.5 QPS / p50 3.03 ms / 273 MB。二进制 sha 与 R43 完全一致
（`376f23e9…`，可复现构建）。

**约束记录（后续轮次遵守）**：重排优化**不得增加 RSS**；基线为：单查询 exact 273 MB、
批量 exact 200q 279 MB、批量 exact 10k 400 MB（pread 模式）。因此批量 exact 在当前形态下
（`pread` 每候选一行）已接近"零内存增量"下的上限（约 batch index-only 的 45%）；再往上必须
改变候选读取方式（需要内存）或改变候选选择策略（影响召回），两者都需用户明确批准。

### R45 — 批量 exact 的取向量任务调度改写：10k query 6.3k→6.9k QPS，RSS 反而 −10%（已提交 `22b2b51c`）

**背景**：R43/R44 后批量 exact 受"每候选行一次 `pread`"限制，且 fetch 阶段把每个（桶 × 32 query）
小任务提交到 blocking 池（10k query 时每 chunk 128 个任务），每个任务还要**预先把整块候选 key 克隆
出来**（256 query × 100 key ≈ 19 MB 峰值）。R44 的 mmap 方案被回滚后，剩一条零内存增量路线：
**改写任务调度本身**。

**改动**（`vector_batch.rs` 的 exact 取向量阶段）：
1. 任务改成 **scoped 线程池 + 每核一个任务**：任务数 = min(核数, 描述符数)，用原子计数器领任务，
   不再每 32 query 提交一次 `spawn_blocking`；
2. 任务大小自适应：`chunk = clamp(batch_query × bucket_count / cores, 32, 320)`
   （10k/1024 的 batch 内 chunk 取 256，200 query 取 32~50），可用 `LAKESOUL_VECTOR_EXACT_CHUNK` 覆盖；
3. 每个任务**边遍历 query 边构建该 query 的 key/score**，不再整块预克隆 → 每任务常驻内存从
   ~19 MB 降到 KB 级；
4. 结果按 query 汇总后仍走原有的并行跨桶合并。

**A/B（同一二进制，只改 chunk）**：

| 场景 | 旧（chunk=32，等价 R43/R44） | 新（自适应） | 变化 |
|---|---:|---:|---:|
| 批量 10k query（3 次） | 5,784 / 5,909 / 5,927 → 中位 5,909 | 7,057 / 6,982 / 6,854 → 中位 **6,982** | **+18%** |
| 批量 200 query（2 次） | 5,308 / 5,655 → 5,482 | 6,230 / 6,205 → **6,218** | **+13%** |
| 10k RSS | 359–362 MB | 359–362 MB | 不变 |
| 200q RSS | 291–292 MB | 292 MB | 不变 |

**最终数字**（表重建、ref 单独测；bits=1、np=32、of=1、payload 缓存开）：

| 配置 | R44 | R45 | Recall | 查询期 RSS |
|---|---:|---:|---:|---:|
| 批量 10k exact（bs=1024） | 6,253–6,291 | **6,841 / 6,969 / 6,841** | 0.6686 | **359 MB**（原 399–408） |
| 批量 200 query exact | 5,454–5,865 | **6,096 / 6,152** | 0.6419 | 292–294 MB（持平） |
| 批量 10k index-only（对照） | 13,5xx | 13,227 / 13,513 / 13,730 | 0.4378 | 345–347 MB |
| 批量 200 query index-only（对照） | — | 11,142 / 11,314 / 11,578 | 0.4204 | 239 MB |
| 单查询 exact（np32/of1） | 311–320 | **315.4** | 0.6419 | 275 MB |
| 单查询 index-only（对照） | 519–537 | 519.9 | 0.4204 | 231 MB |

- 批量 exact 从 index-only 的 45% 提到 **51–54%**，且 **RSS 从 400 MB 降到 359 MB（−10%）**，
  满足"不增长"要求；单查询 exact 保持 index-only 的 ~61%，无回归；
- 冷启动（首次含 payload 构建）RSS 532 MB，属一次性构建开销，与 R44 相同量级。

**测试**：`lakesoul-datafusion --lib` 192 项全绿。

**下一步**：fetch 仍是每候选一次 `pread`（现在占单 query CPU 的大头），零内存增量下已接近上限；
后续可考虑（需用户批准内存或改动候选策略）：正序合并读、常驻 payload、或降低候选数换召回。

### R46 — 精确重排的 SQL 快速物理计划被证伪并回滚：物理计划只占 ~0.2 ms

**假设**：R26 为 index-only 语句加了 `QueryPlanner` 层的快速物理计划（跳过默认物理计划 + 物理优化器），
exact 模式是否也能照做——exact 的逻辑计划形状是
`Limit(fetch) → Sort(distance) → [Projection] → TableScan(marker)`，直接拼
`scan → ProjectionExec → SortExec(fetch) → GlobalLimitExec` 即可，理论上能省掉物理计划 + 物理优化器。

**实现**（已回滚）：`build_fast_plan_exact` 匹配上述形状（要求投影全是列引用、无 Filter、schema 与逻辑
计划一致），成功则直接返回物理计划，任何不匹配回退默认 planner；`LAKESOUL_VECTOR_FAST_PLAN=0` 可关。

**实测**（同一二进制，A/B 只切 `LAKESOUL_VECTOR_FAST_PLAN`；GloVe-200、bits=1、4 桶、200 query）：

| 场景 | 快速计划 | 默认 planner | 结论 |
|---|---:|---:|---|
| 单查询 exact np=32/of=1 | 316.2 / 316.0 QPS（p50 2.99 / 2.99 ms） | 304.8 / 318.6 QPS（p50 3.10 / 2.97 ms） | 噪声内（±2%） |
| 单查询 exact np=16/of=10 | 188.4 QPS | 183.9 QPS | +2.4%，噪声内 |
| 并发 SQL exact c=8 | 1,026 QPS | 1,031 QPS | 无差别 |
| Recall | 0.6419 / 0.6401 | 完全相同 | 计划正确 |

**结论**：物理计划不是 exact 语句的瓶颈。按 R38 的 plan-probe 拆解，单查询 exact 的 ~3.0 ms 里
`parse 0.21 + analyze 0.60 + 逻辑优化 0.20` 合计约 1.0 ms **发生在 QueryPlanner 钩子之前**，
钩子能省的只有 "物理计划 0.19 + 物理优化器" 这一小段；换算成 QPS 上限只有几个百分点，低于
逐次运行的噪声。按"没改进就回滚"的约定**回滚**（`git checkout`，未提交），重建后二进制 sha 与 R45
逐字节一致（`713cc4fe…`）。

**回滚后复核**：单查询 exact 310.5–316.3 QPS / p50 3.00–3.06 ms / recall 0.6419 / 274 MB；
单查询 index-only 516.7 QPS；批量 10k exact 7,043 QPS（0.139 ms/query）/ recall 0.6686 / 358 MB；
批量 200 query exact 6,297 QPS（0.156 ms）/ 0.6419 / 293 MB——与 R45 完全一致，RSS 未增长。

**记录**：单查询 exact 的剩余成本 = 逻辑阶段 ~1.0 ms（parse/analyze/optimize，需跳过 SQL 解析才能省）
+ 物理计划 0.2 + exec ~1.5（probe 0.5 + 取向量 0.9）。下一步若要在单查询上再提速，只能：
① 新增"预编译/句柄化查询"入口（绕过 parse/analyze，需新 API，用户批准）；② 降低取向量的
pread 开销（需内存，已否决）；③ 降低 probe 成本（nprobe/索引参数，换召回）。

### R47 — 精确重排语句的快速物理计划：单查询 +5%、并发 SQL exact +5.5%（提交 `4c6fb852`）

**背景**：R46 试过这个思路但**匹配错了计划形状**（当时假设根节点是 `Limit`，实测优化后的逻辑计划根是
`Projection`，limit 已被折进 `Sort.fetch`），因此从未命中快速路径，测得"无收益"并回滚。
本轮先让 plan-probe 打印优化后的逻辑计划，确认 exact 形状为：

```
Projection: id
  Sort: __lakesoul_vector_distance(...) ASC NULLS LAST, fetch=<top_k>
    TableScan: ... projection=[id, vec], unsupported_filters=[__lakesoul_vector_search(...)]
```

**改动**：`QueryPlanner::build_fast_plan` 在 index-only 快路径之外再加 exact 快路径
（`build_fast_plan_exact`）：根节点可选 `Limit`（skip 必须为 0）→ 若干**纯列引用** `Projection`
→ `Sort(distance, fetch)` → 带 marker 的 `TableScan`。命中时直接拼
`scan → SortExec(fetch) → ProjectionExec* → [GlobalLimitExec]`，跳过默认物理计划 + 物理优化器；
形状不符（offset、非列投影、中间有 Filter、其它节点）一律回退默认 planner；schema 不一致也回退。
`LAKESOUL_VECTOR_FAST_PLAN=0` 同时关闭两条快路径。

**plan-probe 定量**（top_k=10 语句）：默认路径 single exact 计划耗时 = parse 0.211 + analyze 0.617
+ 逻辑优化 0.249 + **物理计划 0.546** = 1.63 ms；index-only 的物理计划只有 0.248 ms——exact 多出的
~0.3 ms 正是 Sort/Projection 的物理计划 + 物理优化开销，快路径把它整段省掉。

**A/B（同一二进制，只切 `LAKESOUL_VECTOR_FAST_PLAN`；GloVe-200、bits=1、np=32、of=1）**：

| 场景 | 快路径 | 默认路径 | 变化 |
|---|---:|---:|---:|
| 单查询 exact（3 对交替） | 326.5 / 324.2 / 337.2 QPS（p50 2.90 / 2.89 / 2.77 ms） | 311.4 / 315.8 / 311.0 QPS（p50 3.03 / 2.96 / 3.04 ms） | **+5%，p50 −0.13 ms** |
| 并发 SQL exact c=8（2 对） | 1,044.9 / 1,039.1 QPS | 1,007.5 / 982.4 QPS | **+5.5%** |
| Recall | 0.6419 | 0.6419 | 完全相同 |
| 查询期 RSS | 273–277 MB | 273–275 MB | 不变 |

- 单查询 exact 现在 326–337 QPS，是同表单查询 index-only（553.9 QPS / p50 1.686 ms）的 **59–61%**；
- 批量入口不受影响（无 SQL 计划阶段）：本轮复测 10k exact 6,023–7,049 QPS、200q exact 6,073 QPS，
  recall 0.6686 / 0.6419，RSS 293–364 MB——与 R45 一致；
- 测试：`lakesoul-datafusion --lib` **192 项全绿**（含向量检索结果断言）；快速计划只在"形状+列投影"
  完全匹配时生效，任何不匹配都回退，因此不影响其它 SQL 语义。

**说明**：R46 的负结论作废——不是思路不行，而是形状匹配错；本轮修正后收益稳定可复现。

### R48 — exact 单查询：probe 与取向量融合为一个阻塞阶段（exec 1.10 → 0.80 ms，提交 `6648ed50`）

**背景**：R47 之后 exact 单查询 exec ≈ 1.0–1.1 ms 的构成是 **probe（4 桶并行，~0.25 ms）+ 取向量
（4 桶并行，~0.70 ms）两个串行阶段**，且每桶命中的去重/排序（~0.03 ms × 4）在 query 线程上串行。

**改动**（`vector_search_exec.rs` 的 `exact_batches_inner`）：
1. 每个 hash bucket 变成**一个阻塞任务**：probe 本桶 shard → 去重/排序出候选 key → 直接读 payload
   取这 100 行向量（原来"全部 probe 完再统一取"）；
2. 于是某桶 probe 一返回就能开始自己的 pread，不用等最慢的 shard；候选 key 的去重/排序也并行；
3. payload 的 `open` 仍是异步、在任务启动前完成；跨桶打分累加、TopK、kept 行回取仍在线程上串行。

**实测**（GloVe-200、bits=1、np=32、of=1、200 条真实 query、同机同表）：

| 指标 | 融合前（R47） | 融合后 |
|---|---:|---:|
| exec 阶段（in-process profile） | 1.03–1.16 ms（probe 0.25–0.35 + fetch 0.69–0.74） | **0.75–0.88 ms**（probe+read 0.67–0.86） |
| 端到端 p50（5 对交替） | 2.93 ms（均值） | 2.90 ms |
| 端到端 QPS（5 对交替） | 均值 320.7 | 均值 323.7 |
| Recall@100 | 0.6419 | 0.6419 |
| 查询期 RSS | 271–280 MB | **271–274 MB** |

- exec 阶段稳定少 ~0.25 ms（−25%），但端到端只体现在噪声内：SQL 前端（parse/analyze/逻辑优化
  ~1.1 ms 与快照解析）占 p50 的大头，且跨进程运行噪声 ±5%，5 对交替的均值差在 +1~4% 之间；
- 选择"阻塞池任务"而不是 `std::thread::scope`：后者在本机再快 ~2–3%，但每个短命线程会新开 glibc
  arena，RSS 观测到 +2~8 MB；阻塞池复用已有线程，RSS 与融合前持平；
- 批量入口与 index-only 路径未改动：本轮复测批量 10k exact **7,003 QPS** / recall 0.6686 / 348 MB，
  批量 200q exact **6,211 QPS** / 0.6419 / 282 MB；单查询 index-only **525 QPS** / p50 1.77 ms（对照）。

**测试**：`lakesoul-datafusion --lib` 192 项全绿。

**结论**：单查询 exact 的 exec 已压到 ~0.8 ms（probe ~0.25 + 读 ~0.45 + 排序 0.04 + 解码），端到端
p50 ≈ 2.9 ms 中 SQL 前端 ~2.0 ms 是主要部分；纯 fetch 侧只剩 ~0.45 ms，进一步需要减少 syscall
（io_uring，内核 5.15 可用但需自研 ~300 行 unsafe，风险高）或降低候选数（换召回）。

### R49 — pgvector 兼容服务 QPS 实测：与 datafusion 持平，但 payload 缓存是 P0 前提

**目的**：按用户要求，用与 datafusion 相同的 GloVe-1.18M×200d 数据集和 200 条真实 query，测
`postgres-lakesoul` 的 pgvector 查询 QPS，判断是否需要优化。

**方法**：用 datafusion bench 建同构表 `vec_glove_pg`（vortex、4 bucket、bits=1、nlist=1024、
top-100）；起 `postgres-lakesoul -p 6543 --worker-threads 16`；用 libpq（psql）单连接顺序 / 8 连接
并行跑 200 条 `ORDER BY vec <-> '[...]' LIMIT 100`，会话参数用 `SET lakesoul_vector_search.*` 控制。

| 会话配置 | c=1 QPS | c=8 QPS | 对照 datafusion SQL |
|---|---:|---:|---:|
| 默认（exact np64/of10） | 182–194 | — | 192.5（np16/of10） |
| `rerank='index'; nprobe=16` | 490–495 | 1,962–1,985 | 519–554（−5~7%） |
| `rerank='exact'; nprobe=32; of=1` | 303–318 | 1,202–1,227（c16: 944–1,029） | 316–337 / c8 1,039–1,045 |
| **payload 缓存关闭** + exact np32/of1 | **10.0** | — | 回退 reader 路径 |
| **payload 缓存关闭** + 默认 np64/of10 | **0.5** | — | 每查询约 2 s |

- **PG wire 不是瓶颈**：index-only 只多 5–7%，exact 与 datafusion 持平（都受 probe + pread CPU 限制）；
- **P0 发现**：服务进程默认未开 `LAKESOUL_VECTOR_RERANK_CACHE`，而 pgvector 的 `<->` 默认 exact
  重排，缓存关闭时回退慢速 reader 路径，QPS 掉 30–370×（默认配置 0.5 QPS/查询约 2 s）。已在
  `postgres-lakesoul` 启动时加 WARN（提交见下），并写入 `rust/postgres-lakesoul/pgvector.md` §九；
- 服务进程 RSS ≈ 504 MB（index cache 15 MB；payload 903 MB 在 tmpfs 上走 pread 不映射）；
  payload 冷构建 0.96 s，之后单查询端到端 28–39 ms；
- 召回与 datafusion 同源（抽样 0.435 / 0.637，对应全量 0.4204 / 0.6419）。

**结论**：pgvector 路径无需为 QPS 单独优化；优先把 payload 缓存变成服务默认/强提示，其次是会话
参数工作点（exact np32/of1 或 index np16）。若要对齐原生 pgvector"只按索引距离排序"的语义，
默认 `rerank='index'` 更贴切，但属行为/召回取舍，待用户决策。

### R50 — io_uring 批量读 payload 被证伪并回滚：微基准 4.4×，端到端 0–1%

**动机**：R48 之后 exact 单查询 exec ~0.8 ms 中"读候选向量"仍 ~0.45 ms，而 `pread` 800 B 实测
0.9–1.3 µs/次；批量路径每 query 400 次 pread。若把每批随机读合并成一次 `io_uring` 提交，理论可把
syscall 成本降一个量级。

**微基准**（400 次随机 800 B 读，tmpfs，单线程）：

| 方式 | µs/read | 相对 pread |
|---|---:|---:|
| pread（逐行） | 0.94 | 1.0× |
| io_uring depth 8 | 0.36 | 2.6× |
| io_uring depth 32 | 0.27 | 3.5× |
| io_uring depth 64 | 0.23 | 4.0× |
| io_uring depth 128/256 | 0.22 | 4.2–4.4× |

**实现**（已回滚）：`pk_locator/batched_read.rs`，raw io_uring（`io_uring_setup`/`io_uring_enter` +
mmap 三个环），每线程一个 ring（thread-local，24 KB 映射），批量 64 行；io_uring 不可用（旧内核/
seccomp/非 Linux）或 `LAKESOUL_VECTOR_PREAD=1` 时逐行 pread 回退；单测
`batched_reads_match_pread` 逐字节对齐两条路径；`PayloadView::score_rows` / `take_vectors` 都改走
批量读。

**同二进制 A/B（`LAKESOUL_VECTOR_PREAD=1` vs ring；GloVe-200、bits=1、np32/of1、payload 缓存开）**：

| 场景 | pread | io_uring | 结论 |
|---|---:|---:|---|
| 单查询 exact（3 对） | 306.4 / 306.8 / 312.7 QPS | 311.0 / 309.6 / 314.9 QPS | +0.7%，噪声内 |
| 单查询 exec profile | fetch 0.91 ms / exec 1.00 ms | fetch 0.77 ms / exec 0.85 ms | **fetch −15%、exec −15%** |
| 批量 10k exact（2 对） | 6,874 / 6,803 QPS | 6,741 / 7,048 QPS | 无差别 |
| 批量 200q exact（2 对） | 5,020 / 6,088 QPS | 6,052 / 6,051 QPS | 无差别（pread 自身方差大） |
| Recall / RSS | 0.6419 / 0.6686；267–353 MB | 完全相同 | 无回归 |

**原因**：
1. 批量路径早已是**内存带宽受限**：16 线程 pread 已达 ~6.6M 次/s（800 B/次 ≈ 5.3 GB/s），
   io_uring 要发挥 0.22 µs/read 需要 >50 GB/s，tmpfs/memcpy 给不了——所以批量无收益；
2. 单查询 fetch 里 syscall 只占一部分，其余是候选 key 排序/galloping（mmap 随机页）、Arrow 数组
   构建、逐行判分与每批 scratch 分配；ring 只把那 0.45 ms 里的 ~0.15 ms 省掉，占 p50(≈2.9 ms) 4%，
   落在运行噪声内。

**决定**：按"没改进就回滚"约定回滚（450 行 unsafe 换 0–1% 不划算）。删除 `batched_read.rs` 与两处
调用点，重建后二进制与 R48 逐字节一致（sha256 `07a81c84…`），并复核：单查询 exact
323.8–329.5 QPS / p50 2.86–2.95 ms、批量 10k 7,183 QPS、批量 200q 6,201 QPS、index-only
13,016 / 11,968 QPS，recall 0.6419 / 0.6686 / 0.4378，RSS 272–351 MB。

**下一步**：单查询剩余 ~2.9 ms 中 SQL 前端 ~2.0 ms 是主体，只能靠"预编译/句柄化查询"新入口；
exec ~0.8 ms 已无低垂果实（probe 0.25 + 读 0.45 + 排序 0.04）。

### R51 — 元数据 TTL 记忆化（可选，默认关）：单查询 index-only +31%、exact +15%（提交 `ed4139b4`）

**动机**：R50 之后用 bench 的三段计时（`plan_mean_ms` / `physical_plan_mean_ms` / `exec_mean_ms`）
定位到单查询里 **physical 阶段 ~0.55 ms 不是物理计划本身**（快速计划下 `default_planner_ms≈0.0005`），
而是 `provider.scan` 期间的两条元数据查询：
1. `LakeSoulTable::for_namespace_and_name`（table_info，PG 往返，table lookup `table_info_ms`
   0.22–0.44 ms/语句）；
2. `get_all_partition_info`（分区列表，PG 往返，`list_ms` 0.16–0.25 ms/语句）。

两者每语句都重查，R38 曾估算"TTL 记忆化可省 ~0.36 ms（约 +20%）"，但当时因**新鲜度口径变化**未做。

**改动**：新增 `catalog/metadata_cache.rs`，用 `LAKESOUL_METADATA_TTL_MS` 控制：
- 未设置或 `0`（**默认**）= 关闭，行为与之前完全一致（每语句查最新元数据）；
- `N` = 允许语句复用 `N` ms 内的 table_info / 分区列表；缓存进程内、按
  （metadata client 实例, namespace, table）与（client, table_id）分键，不同 warehouse/测试客户端不共享；
  DDL / 新提交的可见延迟上界为 N ms。表/分区缓存各留 4096 条上限并在超限时清理过期项。

**A/B（同一二进制、GloVe-200、bits=1、payload 缓存开；index-only 4 对、exact 2 对）**：

### R53 — 稀疏块索引加速 key→行号查找被证伪并回滚：查找是"内存延迟受限"而非"搜索结构受限"

**动机**：R52 之后给 `VectorBlockSource::take` / `score_keys` 加了临时打点，首次看清取向量成本的拆分
（单查询、每桶 100 个候选）：

| 阶段 | 单查询（每桶，4 桶并行） | 批量（每 query，16 线程共享） |
|---|---:|---:|
| key 排序 | ~0.001 ms | ~0.001 ms |
| **`one_row_per_prefix`（mmap key index 查找行号）** | **0.20–0.22 ms** | **0.05–0.07 ms** |
| 读 payload（pread + Arrow 组装） | 0.12–0.13 ms | 0.11–0.15 ms |
| 合计 | 0.34–0.36 ms | 0.15–0.22 ms |

即 key→行号查找占单查询 fetch 的 **60%**（约 0.2 ms/4 桶并行 → 每 query ~0.2 ms，占 p50 的 7–8%）。
原实现是对每 key 在 1.2 MB 偏移表上 gallop + 二分（每 key ~15–20 次随机内存访问）。

**实现（已回滚）**：给 `MmapIndex` 加**稀疏块索引**——每 128 行的首 key 前 8 字节（大端 u64）+ 块起始行，
共 ~28 KB/文件（L2 常驻）；查找时先在 u64 数组上二分（命中缓存），再在 2 个块（≤256 行）内二分，
`LAKESOUL_PK_SPARSE=0` 可回退；首次构建 ~0.5 ms/文件、一次性。诊断打点确认 `sparse_hits=100/100`（确实走了稀疏路径）。

**实测**（同二进制 A/B）：

| 场景 | 稀疏关 | 稀疏开 | 结论 |
|---|---:|---:|---|
| **`one_row_per_prefix` 实测耗时**（100 key） | 0.175–0.229 ms | **0.175–0.254 ms** | **无变化** |
| 单查询 exact（3 对） | 353.9 / 364.0 / 359.4 QPS | 353.1 / 358.8 / 366.9 QPS | 噪声内 |
| 批量 10k exact（2 对） | 6,971 / 6,273 QPS | 7,319 / 7,293 QPS | 噪声内（pread 侧方差大） |
| 批量 200q exact（2 对） | 6,189 / 6,003 QPS | 5,205 / 5,497 QPS | 噪声内/偏慢 |
| 单查询 index-only（不经过该路径，对照） | 507.0 QPS | 543.7 QPS | 纯噪声（该路径不调用查找） |
| Recall / RSS | 0.6419 / 0.6686；231–352 MB | 完全相同 | 无回归 |

**结论**：把"~18 次随机访问"降到"~2 次"没有降低耗时，说明这 0.2 ms 主要不是**二分/步数**，而是**每 key 至少
一次的随机内存/TLB 缺失**（本机 tmpfs + 二级页表的随机访问实测 ~1–2 µs/次，与 pread 1 µs/次同量级）。
因此：
1. 稀疏块索引无法解决（已回滚，重建后二进制与 R52 逐字节一致 `8ec09615…`）；
2. 想再降只能**减少查找次数**（例如批量路径对 query 块内的候选 key 去重，度量上界 ~16%；
   或减少每桶候选数，换召回）或**改布局/预取**（需要更多内存或改变 payload 组织）；
3. 该发现也解释了 R50 的 io_uring 为什么无收益：瓶颈在内存延迟而非 syscall。

**回滚后复核**：单查询 exact 350.9 / 356.1 QPS（p50 2.69 ms）、批量 10k 6,761 QPS、批量 200q 6,110 QPS、
单查询 index-only 539.5 QPS，recall 0.6419 / 0.6686 / 0.4204，RSS 232–352 MB——与 R52 一致。

可关）。假设：R53 已证单次查找是内存延迟受限（~2 µs/键、~18 次依赖加载），预取应能省一半 offset 缺失。

| 场景 | 预取开 | 预取关 | 结论 |
|---|---:|---:|---|
| 单查询 exact（TTL=200、3 对） | 505.9 / 524.1 / 531.0 QPS（exec 0.75–0.84） | 529.0 / 539.4 / 535.4 QPS（exec 0.72–0.74） | 无收益（略慢，噪声内） |

### R59 — exact 扫描在 `narrow` 计划下只保留目标行数（单查询 +2~5%、c=8 +3.6%、c=32 +3.9%）

### R61 — pgvector 服务的每语句 SQL 兼容解析器改为进程级复用（服务端 exact +31%、index-only +39%）

**发现**：pgvector 兼容服务里每条语句都要先过 `split_statements()` 判断是否多语句批次，而它**每次都
`PostgresCompatibilityParser::new()`** —— 这个构造函数会用 sqlparser 把黑名单映射里的几十条 SQL 全部
解析一遍（每次 ~0.3–0.5 ms）。实测：`SELECT 1` 经服务端每条 **0.79 ms**，其中 0.68 ms 花在这里，而
真实 PostgreSQL 只要 **0.03 ms**；对向量查询，这相当于每条语句白白多付 ~0.3 ms。

**改动**（`e24303da`，`postgres-lakesoul/src/server.rs`）：
1. 兼容解析器在构造后不可变（`parse(&self)`，规则 `Send + Sync`），改为进程级 `LazyLock` 复用；
2. 早退：**文本里没有语句分隔符 `;` 就不可能是多语句批次**，直接按单语句交给上层（调用方把 `None`
   当作单语句），连解析都省掉。带 `;` 的文本（含尾分号）仍走解析，语义完全不变。

**服务端实测**（GloVe-1.18M×200d、200 条真实 query、单 psql 连接、TTL=200 + payload/source 缓存、
每配置 2 轮）：

| `SELECT 1` 每条语句 | 0.79 ms | **0.31 ms** | −61% |
| `rerank='exact'; nprobe=32; of=1` | 450–462 QPS | **591 / 598 QPS**（p50 1.56 ms） | **+31%** |

### R64 — 交互式语句把桶内取向量再拆两线程：无线程池/无收益，已回滚

**动机**：单查询 exact 的 exec≈0.72 ms 里，每桶取向量 ≈0.33 ms（key→行号 0.2 + pread 0.13）是延迟
链；4 个桶已在 4 个线程并行，若每桶再把 100 个候选拆成两半、交给 1 个辅助线程，理论上每桶 0.33→0.17，
整条语句可省 ~0.15 ms（≈+8%）。用进程内 `EXACT_IN_FLIGHT` 计数做门控（仅当 in-flight==1 才拆，
并发时保持原样），`LAKESOUL_VECTOR_SPLIT_FETCH=0` 可回退。

**实测（同二进制 A/B，GloVe-200、np=32/of=1、TTL=200）**：

| 场景 | 不拆（基线） | 拆两半 | 结论 |
|---|---:|---:|---|
| 单查询 exact（3 对） | 503.6 / 530.6 / 515.7 QPS（exec 0.76–0.84） | 524.6 / 520.5 / 511.0 QPS（exec 0.74–0.80） | **无差异**（QPS 噪声内） |
| 并发 exact c=8（2 对） | 2,224.7 / 2,254.4 QPS | 2,258.9 / 2,158.7 QPS | 无差异（门控生效、无回归） |
| Recall | 0.6419 | 0.6419 | 不变 |

**原因**：在这台 KVM guest 上 `std::thread::scope` 新建线程的开销（~0.1–0.2 ms，含 clone/mmap 栈）
与拆半省下的 0.15 ms 延迟相当，收益被抵消；exec 均值确实略降（0.80→0.75），但端到端 QPS 无变化。
**若改用 `spawn_blocking`**（复用池线程、单次调度 ~11 µs）理论上可省 ~0.1 ms，但需把 4 个 fused 任务
拆成两阶段 8 个任务（+8 次调度/语句），净收益预计 ≤3%、低于当前测量噪声，故不实现。已回滚，
重建后二进制与 R59 逐字节一致（`220705fe…`）。

**回滚后复核**：单查询 exact 557.8 / 547.6 QPS（p50 1.66/1.67 ms，exec 0.69/0.73）、c=8 2,317.4 QPS、
recall 0.6419 —— 与 R63 状态一致。

### R65 — payload 缓存改为"显式目录即开启"（避免忘配开关导致 30–370× 减速）

**动机**：exact 重排依赖存储向量 payload 缓存；过去的规则是必须显式 `LAKESOUL_VECTOR_RERANK_CACHE=1`，
只配 `LAKESOUL_VECTOR_RERANK_CACHE_DIR` 不算开启。服务端启动只会打一条 WARN，用户很容易在配好目录后
仍然跑在 fallback reader 路径上（实测 10 QPS 对 591 QPS，慢 30–370×）。

**改动**（`67ae4ebd`，`lakesoul-io/src/pk_locator/payload.rs` + `postgres-lakesoul/src/main.rs`）：
- 规则改为：显式 `LAKESOUL_VECTOR_RERANK_CACHE` 决定开关（`1/true/yes/on` = 开，其它 = 关）；
  **未设置但 `LAKESOUL_VECTOR_RERANK_CACHE_DIR` 配了非空目录时，视为开启**；
- 不引入新的隐式来源：`LAKESOUL_CACHE_PATH` 单独设置**不会**开启（payload 目录对大表是真实磁盘
  占用，只有明确指定目录的人才会写出它）；
- 服务端启动 WARN 也按同一规则判断（不再出现"配了目录却仍提示缓存关闭"）。
- 语义不变：payload 是从不可变数据文件派生的缓存，命中与否只影响速度，结果逐位一致。

**验证**（GloVe-200、np=32、TTL=200；nprobe/overfetch 默认走 of10，故 recall 0.7178）：

| 运行配置 | QPS | payload 目录 | 说明 |
|---|---:|---|---|
| 只设 `..._CACHE_DIR` | **255.2** | 已生成 903 MB | 新规则下自动开启 ✓ |
| `..._CACHE=1` + DIR | 257.9 | 已生成 | 基线（等价） |
| DIR + `..._CACHE=0` | **17.5**（p50 56.8 ms） | 未生成 | 显式关闭仍优先 ✓ |

三种运行 recall 完全相同（0.7178），再次确认缓存只影响速度、不影响结果。测试：
`lakesoul-io --lib` **193 通过（1 ignored）**。

### R66 — exact 重排的 nprobe × overfetch 工作点前沿重测（nprobe 现在几乎"免费"，推荐改为 np48–64/of1）

**背景**：R51/R54/R59 之后 exact 单查询的成本结构变了（前端规划 ~0.70 ms + 物理 0.33 + exec ~0.72，
其中 probe 只占 exec 的 1/4 左右），旧的 nprobe 曲线（R47 时代：np64/of1 只有 307.9 QPS）已经不适用。
本轮重测完整前沿（GloVe-200、bits=1、4 桶、`LAKESOUL_METADATA_TTL_MS=200`、payload/source 缓存开）：

|---|---|---|---|---|---|
| 8 | 1 | 560–570 | 1.62–1.69 ms | 0.5406 | — |
| 16 | 1 | 544.5 | 1.71 ms | 0.5980 | 2,388 |
| 24 | 1 | 544.2 | 1.65–1.75 ms | 0.6246 | — |
| 32 | 1 | 531.2 | 1.74 ms | 0.6419 | 2,307 |
| **48** | **1** | **533.7** | **1.72 ms** | **0.6623** | 2,235 |
| 64 | 1 | 528.6 | 1.71–1.83 ms | 0.6756 | 2,150 |
| 24 | 2 | 468.8 | 2.01 ms | 0.6638 | — |
| 64 | 2 | 455.2 | 2.04 ms | 0.7334 | — |
| 128 | 1 | 498.3 | 1.89 ms | 0.7045 | — |
| 128 | 3 | 387.4 | 2.40 ms | 0.8043 | — |

### R67 — CPU 成本模型（为什么剩余空间有限）：单查询 5.8 core-ms、批量 2.0 core-ms；c=8 已达 90% 核利用率

用 `/usr/bin/time -v` 记录每个优化状态下的**进程 CPU 时间**，把"墙钟 QPS"与"每查询 CPU"分开，得到
当前成本模型（GloVe-200、np=32/of=1、200 条 query、c=1）：

| 状态 | QPS | **CPU/query** | 占用核 | plan | phys | exec（墙钟） |
|---|---:|---:|---:|---:|---:|---:|
| 0. R47 前基线（无快速计划/缓存/TTL） | 321.7 | 6.95 ms | 2.24 | 0.914 | 0.741 | 1.306 |
| 1. + 快速物理计划 | 350.9 | 6.65 ms | 2.33 | 0.911 | 0.511 | 1.293 |
| 2. + 融合精确排序 | 366.3 | 6.80 ms | 2.49 | 0.905 | 0.481 | 1.217 |
| 3. + payload source 缓存 | 429.4 | 5.90 ms | 2.53 | 0.956 | 0.509 | 0.729 |
| 4. + 元数据 TTL=200（当前） | **526.9** | **5.80 ms** | **3.06** | 0.697 | 0.319 | 0.771 |

- **单查询是延迟受限而非 CPU 受限**：c=1 只用到 3.06/16 核；TTL 的收益几乎全是省"等 PG 往返"的墙钟
  （CPU 只降 0.1 ms，墙钟降 1.38→1.90 的 0.43 ms 来自等待消失）；payload source 缓存同时省 CPU
  （6.8→5.9）与墙钟（exec 1.2→0.73）；
- **并发 c=8 已接近 CPU 上限**：CPU/query 6.35 ms、用到 14.47/16 核（90%）→ 2,278 QPS；
  c=32 时 15.52 核（97%）→ 2,300 QPS。按 CPU/query 6.35 的理论上限 2,520 QPS，实际达成 90%；
- **批量 10k 也是 CPU 受限**：6,734 QPS、**2.01 CPU-ms/query**、13.56/16 核（85%），理论上限
  ~7,960 QPS；其 CPU 约一半是 rabitq probe（1 ms），一半是 400 次候选 pread（~0.9 ms）。

**结论**：在"零语义变化 + 不修改索引内部"的约束下，单查询/批量都已按 CPU 或 PG 等待定价到接近下限；
继续提升必须减少 CPU 工作，而 CPU 的两大块（probe、候选行读取）分别需要改 `lakesoul-vector`
（用户 WIP）或降低召回。**这也解释了 R60–R64 的五轮尝试为何全部无效**（调度/线程/切分类调整不改
CPU 总量，只改等待分布）。

### R68 — DataFusion SQL 与 pgvector 服务支持 IP（内积）距离，index-only 也可用

**背景**：RaBitQ 的 `Metric::InnerProduct` 本来就完整实现（簇选择/估计器/SIMD/`SearchResult.score`
语义都是"IP 越大越好"），但我们的上层把 index-only 排序锁死在 L2，并且 pgvector 的 `<#>` 算子
（datafusion-postgres 会重写成 `-inner_product(...)` ASC）不被下推规则识别。结果：**原来 pgvector
的 `<#>` 查询无法走索引**，DataFusion SQL 只有 exact 模式能用 IP，index-only 直接回退全表扫描。

**改动**（`lakesoul-datafusion` 三个文件 + 测试）：
1. `planner/vector_search_rule.rs`：
   - `collect_terms` 识别 `Expr::Negative`，把 pgvector 的 `-inner_product(vec, q)` 归一化为
     "正权重 + 规范方向"（扫描输出仍是 IP 降序，与 `-IP ASC` 的排序完全一致）；
   - 方向校验从"L2 ASC / 其它拒绝"放宽为"L2 ASC、IP DESC，或负内积 ASC"；
   - `order_by`（index-only）从"仅 L2"放宽为"L2 **或** IP"（单列）；
   - `sort_matches_spec` 记录计划原本的 ASC 标志，负内积形式也能正确删除 Sort 走融合物理计划。
2. `datasource/file_format/vector_search_exec.rs`：候选去重/排序按 metric 取方向（L2 取最小距离、
   IP 取最大内积），两处（index-only 路径、融合 exact 路径）。
3. `datasource/table_provider.rs`：允许**单列 IP** 的 index-only 请求（多列融合排序仍排除，因为
   多列融合距离目前只对 L2 定义），否则会静默回退成全表扫描并返回错误结果（这是本次抓到的真实 bug：
   rule 删了 Sort、provider 又回退，最终返回的是无排序的任意行）。
4. 测试：新增 rule 单测 2 个（`inner_product DESC`、pgvector 负内积）、端到端 1 个
   （IP 索引 + `order_by=true` + recall 断言）；`lakesoul-datafusion --lib` 全量通过。

**实测**（GloVe-1.18M×200d、4 bucket、nlist=1024、bits=1、top_k=100、200 条真实 query、
`LAKESOUL_METADATA_TTL_MS=200` + payload/source 缓存；IP 索引由 bench `--metric ip` 构建）：

| 查询形态 | 模式 | QPS | Recall@100 |
|---|---|---:|---:|
| `ORDER BY inner_product(vec, ARRAY[...]) DESC`（DataFusion SQL） | exact | 341.4 | 0.7006 |
| 同上 | index-only（np16） | 398.2 | 0.4395 |
| **`ORDER BY vec <#> '[...]'`（pgvector 服务）** | **exact** | **590.8** | **0.7006** |
| **同上** | **index-only（np16）** | **779.1** | **0.4395** |

- 两种 SQL 写法结果**逐条一致**：exact 200/200、index-only 200/200 查询的 id 列表完全相同；
- 归一化数据上 IP 排序 ≡ L2 排序，所以 recall 可直接对照 L2 的 0.6419 / 0.4204（IP exact 0.7006 略高，
  因为 IP 索引的候选质量在这份数据上更好）；
- 与 L2 index-only 的 694–791 QPS 持平，说明 IP 的 index-only 已经和 L2 一样快。
- **batch 批量入口仍只支持 L2 的 exact**（`vector_batch.rs` 里显式报错），IP 的批量支持留待后续。

### R69 — P1：多文件桶候选解析（去掉"每桶必须 1 个数据文件"的前提）

**问题**：之前 exact 直读路径要求 `exact_fast_path_eligible` 里"每个 hash bucket 只有 1 个数据文件"，
否则回退 reader 路径（单查询 13–25 ms / 40–75 QPS）。而大表单桶数据量一旦超过 `max_file_size`，
compaction 也压不成 1 文件 → 快路径永久不可用。这正属于"给向量检索加特殊要求"，必须去掉。

**改动**：
1. `lakesoul-io/src/pk_locator.rs`：
   - `rows_per_prefix_lenient()`（0 行/多行返回单个 `None`，不再整批失败）；
   - `VectorBlockSource::lookup_rows()` / `take_rows()`；
   - `take_multi_file(sources, keys)`：候选 key 在桶内各文件解析，**恰好命中 1 个文件**才直读，
     多命中/零命中返回 `None` 交回 merge-on-read 路径；读取结果按原候选顺序 `interleave` 重排。
2. `lakesoul-datafusion/.../vector_search_exec.rs`：eligibility 放宽（`LAKESOUL_VECTOR_MULTI_FILE_EXACT=0`
   可回退），直读路径按桶打开全部文件的 payload source，任务内用 `take_multi_file`。
3. 新增 e2e 测试：`sql_vector_search_multi_file_bucket`（两次追加提交 = 2 文件/桶，断言仍走直读、
   recall ≥ 8/10）、`sql_vector_search_multi_file_upsert_falls_back`（同 key 写两次 → 多版本回退，
   结果与合并后暴力 top-k 一致）。

**语义**：追加型多文件桶现在与 1 文件桶同路径；多版本（upsert）桶仍回退 reader，结果正确但慢
（P1b 再按 commit 序解析可见版本）。详细设计/记录见
[向量检索去限制改造.md](../lakesoul-vector/向量检索去限制改造.md)。

**验证**：`lakesoul-datafusion --lib` 全量通过（含 2 个新测试与 3 个 IP 测试）。

### R70 — IP（内积）距离扩展到**批量入口**（单查询/批量、index-only/exact 全覆盖）

**背景**：R68 已让单查询（DataFusion SQL 与 pgvector `<#>`）在 index-only/exact 两种模式下支持 IP；
但快照批量入口 `search_vector_batch` 仍硬编码 L2（排序、去重、精确打分都按"距离越小越好"），
provider 对非 L2 的 exact 批量请求直接报错。

**改动**：
1. `vector_batch.rs`：`VectorBatchRequest` 新增 `metric` 字段与 `ascending()`；候选去重（L2 取最小距离、
   IP 取最大内积）、跨桶合并排序、exact 打分的 `score_keys(ascending)` 全部按 metric 走方向
   （IP 的 exact 分数是"负内积"，因此两种 metric 都只需一次升序排序）；
2. `table_provider.rs`：批量入口不再拒绝非 L2，而是校验 `request.metric` 与表索引 metric 一致
   （不一致明确报错，避免候选与打分方向不一致）；
3. bench/示例更新（`--metric ip` 时批量请求自动带 `"IP"`）；
4. 新增端到端测试 `sql_vector_batch_ip_metric`：IP 索引表上批量 index-only 与 exact 两种模式的
   recall 断言（用 Int64 主键表，因为批量入口目前只解码 Int64 主键）；
5. 顺手修复直读路径一个潜在 bug：`exact_batches_inner` 的 keep 行 gather 用"原桶号"索引压缩后的
   `taken_vectors`，某些桶在最终 top-k 中没有行时会导致越界（多文件桶更容易触发）；改为显式
   `array_of_bucket` 映射并在越界时安全回退。

**实测**（GloVe-1.18M×200d、10k query、bs=1024、np32/of1、本机，2 轮）：

| 表 metric | index-only QPS | exact QPS | Recall@100 |
|---|---:|---:|---:|
| L2 | 11,605–11,789 | 6,701–7,031 | 0.4531 / 0.6686 |
| **IP** | **8,661–9,110** | **5,450–5,514** | **0.4679 / 0.7152** |

单查询侧（R68 实测，pgvector `<#>`）：IP exact 590.8 QPS / index-only 779.1 QPS，与 L2 的 533 / 694
持平或更快。**批量侧 IP 目前约为 L2 的 76–80%**（exact 890 MB RSS 也偏高，L2 ~340 MB），
已记录为后续优化项（先排查批量 exact 的 IP 打分/内存路径，再决定是否需要 SIMD dot 专用内核）。

**测试**：`lakesoul-datafusion --lib` **198 项全绿**（含新增批量 IP 测试与 gathered 修复后的回归）。

### R71 — 批量 IP 的 QPS/RSS 已与 L2 对齐（根因在 benchmark，不在引擎）

**现象**：R70 记录批量 IP exact 5,450–5,514 QPS / index-only 8,661–9,110 QPS（L2 的 76–80%），
且 IP exact 峰值 RSS ~890 MB（L2 ~350 MB）。

**定位过程**（逐层排除）：
1. 用 `LAKESOUL_VECTOR_SEARCH_PROFILE=1 RUST_LOG=debug` 对比每 chunk 阶段耗时：L2 与 IP 的
   `probe/fetch/merge` 几乎相同（80/61/2 ms vs 80/62/2 ms），差异不在批检索本身；
2. 发现 IP 运行的前两个 chunk 出现 `load_ms≈230–330 ms`、`rank_merge_ms≈890 ms`，而其后正常；
3. 控制实验（全新 payload 目录、冷/热各跑一次、`nq=64/500/2000/10000`）：L2 冷启动 RSS 500 MB →
   热 277 MB；IP 冷 900 MB → **热 861 MB 不下降**；payload 文件 mtime 未变化 → 不是 payload 重建；
4. 最终定位：bench 的 SQL 场景在进入批量测量前会跑 `EXPLAIN ANALYZE ... order by array_distance(...)`
   和单查询探针，而 bench 的 SQL 文本**硬编码 `array_distance`（L2）**。对 IP 索引表，L2 表达式与
   IP 索引 metric 不匹配 → 计划回退全表扫描 → `EXPLAIN ANALYZE` 真的执行扫描，读整个向量列
   （~1.6 s、~500 MB 高水位内存）→ 既拉长墙钟又抬高 RSS；L2 表则走索引快路径，所以"看起来"IP 慢。

**修复**（仅 benchmark，产品代码无改动）：
1. `benches/vector_rebuild_bench.rs` 新增 `metric_order_by(metric, query)`：L2 → `array_distance(...) ASC`，
   IP → `inner_product(...) DESC`；SQL 场景的 EXPLAIN/EXPLAIN ANALYZE、单查询循环、并发循环以及
   plan-probe 场景全部改为按 `--metric` 生成 SQL；
2. 批路径在测量前用 64 条 query 预热一次（此前只有单查询 SQL 预热，而单查询预热对 IP 表反而触发
   全表扫描，形成不对称）。

**复测**（GloVe-1.18M×200d、4 bucket、bits=1、top_k=100、TTL=200ms、payload/index 缓存已热）：

| 场景 | L2 | IP | IP / L2 |
|---|---:|---:|---:|
| 单查询 exact（200 query） | 507.9 QPS（p50 1.747 ms，RSS 276 MB） | **511.7 QPS**（p50 1.758 ms，RSS 274 MB） | 101% |
| 单查询 index-only（np16） | 689.1 QPS（p50 1.318 ms，RSS 234 MB） | **675.1 QPS**（p50 1.303 ms，RSS 231 MB） | 98% |
| 批量 10k exact（bs=1024） | 6,745–6,991 QPS，RSS 349–352 MB | **7,060–7,146 QPS**，RSS 351–354 MB | 102–104% |
| 批量 10k index-only | 11,915–12,388 QPS，RSS 346–348 MB | **11,833–11,915 QPS**，RSS 346–347 MB | 96–99% |

召回与之前一致（单查询 IP 0.7007 / 0.4396；批量 0.7152 / 0.4679）。**结论**：IP 的 QPS 与 RSS
在单查询、批量、index-only、exact 四种组合下都已与 L2 对齐，引擎侧无需再改；此前的差距是测量方法
问题（benchmark 探针 SQL 未按 metric 生成 + 批路径缺预热）。

**记录**：`向量查询使用说明.md` 的批量对照表与 `向量检索去限制改造.md` 的变更记录已同步。

### R72 — P1b：多文件桶的多版本（upsert）解析，按文件年龄取最新

**背景**：P1a 只支持"候选键在桶内唯一命中一个文件"；同一 key 被写多次（upsert/重写）时，
候选键会出现在多个文件里，P1a 直接回退 reader 路径（13–25 ms/query，约 40–75 QPS）。

**改动**：
1. `lakesoul-io/src/pk_locator.rs`：新增 `take_multi_file_ranked(sources, ranks, keys)`：
   - 同一 key 命中多个文件时，读 **rank 严格最大**的文件（rank 由上层给出，越大越新）；rank 并列
     视为无法证明先后，整体返回 `None` 回退；空 ranks 保持"唯一命中才可读"的旧行为（P1a）；
2. `lakesoul-datafusion/.../vector_search_exec.rs`：
   - 由 snapshot 的索引提交视图构造"文件年龄"：`file_age[file] = max(覆盖该文件的 segment 的
     `birth_version`)`；
   - 每个桶按年龄升序排列 payload source（最老在前），把对应年龄数组一起传给解析器，任务里改用
     `take_multi_file_ranked`；
   - 覆盖性证明未放宽：仍要求无 mutation/CDC、索引覆盖快照全部文件，因此可见行与 merge-on-read 一致
     （年龄取最新 = LSM 的"新覆盖旧"）；tombstone/CDC 解析仍留待 P4。
3. 端到端测试 `sql_vector_search_multi_file_upsert_uses_newest_version`：同 key 写两次（两个文件/桶），
   断言**仍走直读路径**（test-only 计数）且返回**最新向量**的邻居（recall ≥ 8/10）。

**验证**：`lakesoul-datafusion --lib`、`lakesoul-io --lib` 全量通过。性能预期：upsert 型多文件桶
从 reader 回退的 ~40–75 QPS 提升到直读路径（多文件解析比单文件多约 1 次/文件的 key 查找，预计
exact 2–4 ms/query），完整大表实测留待下一轮（需要构造 2 文件/桶的大表）。

### R73 — P2：投影泛化（任意 select 列都能走直读快路径）

**背景**：直读路径原先要求"投影的每一列都是主键或搜索向量列"，否则 `exact_fast_path_eligible`
返回 false，整条查询回退 reader 路径（13–25 ms/query）。业务 SQL 几乎都会 `select id, title ...`，
这让快路径在真实查询里很难命中。

**改动**（`vector_search_exec.rs`）：
1. eligibility：投影含"排名列（主键 + 搜索列）之外"的列时，只要求 `defers_payload` 成立
   （narrow、已知 limit、session 未关闭 deferred payload），不再要求投影只有主键+向量列；
2. 直读路径输出改为 **ranking schema**（主键 + 搜索列）；
3. `execute()` 在直读命中后：
   - 投影只有排名列 → `project_batch` 直接投影（零额外读）；
   - 投影含额外列 → `payload_columns_for_ranked()`：`take_first_rows(keep)` 取 plan limit 行 →
     `pk IN (...)` 过滤 → `build_configs`/`read_configs` 只读这些行的 payload 列 →
     `order_payload_by_keys` 按排名重排 → `project_batch` 到计划 schema。
4. 语义：额外列来自同一批数据文件、由同一批 keep 行（主键）定位，行/列对应与 reader 路径一致；
   代价是 ≤ limit 行（通常 100）的二次读取，而不是候选集全量回退。

**指标一致性**：直读 + 二次读取同样写入 `VectorSearchCounters` 的
`deferred_payload_ranked` / `deferred_payload_rows`（此前只有 reader 路径的 deferred 会记），
因此 `sql_vector_search_defers_payload_reads` 的计数断言在直读命中时仍然成立。

**测试**：新增 `sql_vector_search_projects_extra_columns`（表：`id` pk + `vec` 向量 + `tag` Int64）：
- `select id, tag ... limit 10`：断言仍走直读路径（`EXACT_DIRECT_RUNS` 计数）、`tag == id*7+1` 逐行成立、
  top-10 recall ≥ 8/10；
- `select tag ... limit 10`（投影不含主键/向量列）：返回 10 行且 tag 值合法。
`lakesoul-datafusion --lib` 全量通过。

**遗留**：额外列目前复用 reader 做二次读（每桶一次 reader 启动，单查询 +2–4 ms）；若后续常见
"大量额外列"场景，可把 payload 格式扩展到任意标量列，把这次二次读也变成 payload pread。

### R74 — P3：过滤感知的迭代扩探（`WHERE` 不再让结果变少/变慢）

**背景**：`WHERE ... ORDER BY distance LIMIT k` 的旧语义是"候选后过滤"——scan 只取
`top_k*overfetch` 个候选，`FilterExec` 在上层过滤。选择性低时返回行远少于 k（历史记录：0.08% 选择性
即使 overfetch=50 也返回 0 行），且 `narrow=false` 让直读快路径失效，只能走 reader 路径（慢 10–20×）。

**改动**：
1. 规则把 scan 与 Sort 之间的 `Filter` 谓词（AND 合并）作为 marker 的追加参数下推；
   `VectorSearchRequest.filter: Option<Expr>`（旧 marker 参数格式兼容）；
2. provider 用数据列 schema 把谓词编译成 `PhysicalExpr`；编译失败（如引用分区列）→ 不启用，扫描回退；
3. exec 新增过滤快路径：probe 候选 key → 解码成 `pk IN (...)` → **payload-only** reader 读回这些行
   （新增 `build_configs_with(.., search=false)`，跳过 native reader 的向量检索选项）→
   `PhysicalExpr::evaluate` + `filter_record_batch` 只留通过行；通过行不足 `keep_rows` 时把候选集 ×4
   扩（起始 `LAKESOUL_VECTOR_FILTER_OVERFETCH=4`，上限 `LAKESOUL_VECTOR_FILTER_MAX_OVERFETCH=64`）；
4. 结果按精确距离排序后返回，上层 `FilterExec` 幂等、`Sort`/`Limit` 得到过滤后的 top-k；
   `LAKESOUL_VECTOR_FILTER_EXACT=0` 可回退旧行为。

**过程中修掉的关键 bug**：最初直接用 `build_configs` 读候选行，读回的永远是 native reader 自己的
向量候选集（top_k*overfetch 很小），导致 `WHERE` 过滤后每轮只有 2 行通过、扩探无效。新增
`search=false` 的 payload-only 配置后，读回的正是 `pk IN` 指定的候选行。

**测试**：`sql_vector_search_filter_narrows_probe`（400 行，`tag = id*7+1`）：
- 28% 选择性（`tag > 2000`）：走候选探针路径（test-only 计数），返回恰好 10 行、全部满足谓词、recall ≥ 8/10；
- 3.5% 选择性（`tag > 2700`，仅 14 行匹配）：扩探后仍返回 10 行；
- `tag < 0`：返回 0 行。
`lakesoul-datafusion --lib` **200 项全绿**。

**边界**：只对单列 exact、无 CDC、无分区列、覆盖性证明通过的查询生效；谓词求值失败自动回退 reader 路径。
**后续**：谓词只引用向量列时可直接在 payload 上过滤；可用统计信息选起始倍率；候选行目前读全部列。

### R75 — P4（CDC 部分）：删除墓碑不再迫使查询回退 reader 路径

**背景**：CDC 表的删除写在数据文件里（`op='delete'` 的墓碑行），旧实现要求
`cdc_column.is_empty()` 才能走直读/过滤快路径，CDC 表因此全部回退 reader。同时删除会在索引里
留下 **mutation 链**（实测 `mutation_head=true, records=1`），旧的覆盖性证明把它当成"状态不可信"
而进一步拒绝候选路径。

**改动**：
1. `table_provider.rs`：CDC 表把 `cdc_column != 'delete'` 编译成 `PhysicalExpr`（基于数据列 schema）传给 exec；
2. `vector_search_exec.rs`：过滤快路径触发条件改为"有 Filter 或 有 CDC 谓词"；候选行读回后依次求值
   （plan 谓词 + CDC 谓词）再过滤；`expected_snapshot`/`snapshot_covered` 新增 `cdc_free` 参数；
3. `vector_batch.rs`：新增放宽的覆盖证明 `candidate_files_covered()`：重读候选行的路径只需
   "索引覆盖快照全部数据文件"，不再要求"无 mutation 链/无 CDC"。安全性依据：
   - 分片加载时 mutation 链会掩蔽被删 key（`load_from_segments_with_mutations`），这些 key 不会成为候选；
   - 候选行由 merge-on-read 读回，墓碑由 reader 的 CDC 过滤 + 本进程 `op != 'delete'` 谓词双重丢弃；
   - 覆盖证明仍要求 pending 文件为空，未进索引的新 commit 不会漏。

**测试**：`sql_vector_search_cdc_drops_tombstones`（CDC 向量表，200 行、删 20 行）：
- `count(*)` = 180；
- 无 WHERE 查询：走候选路径、返回 10 行、不含被删 id、recall ≥ 8/10；
- `where id > 100`：过滤 + CDC 组合，返回 10 行、全部 >100 且未被删。
`lakesoul-datafusion --lib` **201 项全绿**。

**遗留（分区列）**：`partition_cols` 非空仍回退 reader——分区表上"主键过滤的二次读取"会跨分区取到
同一主键的多份行，需要先支持"按分区组分别加过滤条件"；正确性当前由回退保证。

### R76 — P4（分区列）：范围分区表走候选路径，并修掉分区表的 schema 不匹配

**背景**：`range_partitions` 非空时直读/过滤快路径一律回退，且旧 reader 兜底路径在分区表上
返回的 batch 缺少分区列（`PhysicalExpr Column references column 'part' ... input schema only has 2 columns`），
分区向量表实际处于不可用状态。

**改动**：
1. `table_provider.rs`
   - `scan_vector_search` 的 read schema 保留被投影的分区列（`compute_project_column_indices` 的结果
     已含分区列，调试确认后删除了重复追加的分支）；
   - 新增 `candidate_schema`（文件列 + 分区列）传给 exec；Filter/CDC 谓词的 `PhysicalExpr`
     统一以 `candidate_schema` 为输入 schema（列下标一致）；
2. `vector_search_exec.rs`
   - 候选路径对 `partition_cols` 非空也生效：每个"分区×桶"work unit 独立 probe 候选 key，
     读取用 `candidate_schema`（reader 从 file group 填默认分区值）；各 work unit 只读自己的文件，
     主键过滤不会跨分区命中重复行，因此不需要按组过滤；
   - 分区表即使没有 Filter/CDC 也走候选路径（谓词为空 → 只做候选读回 + 精确排序）；
   - reader 兜底路径对分区表读 `candidate_schema` 并在末尾 `project_batch` 回 `self.schema`，
     修掉分区表输出 schema 缺列的问题；
3. 测试 `sql_vector_search_range_partitioned_table`（`part` 两分区、各 100 行）：
   - 跨分区：走候选路径、10 行、`part == id % 2`、recall ≥ 8/10；
   - `where part = 0`：裁剪后 10 行且全部 `part = 0`。
`lakesoul-datafusion --lib` **202 项全绿**。

**结论**：四层改造（P1b 多版本桶、P2 投影泛化、P3 过滤扩探、P4 分区/CDC）全部完成；
余下为多文件桶大表 QPS 实测、P2 二次读取优化、P3 统计信息选倍率等性能类遗留。

### R77 — 多列加权融合支持 IP（index-only 排序 + 精确重排，含 pgvector `<#>` 加权和）

**背景**：多列加权融合此前只有 L2 能走索引排序：`table_provider` 对
`order_by && metric != "L2" && columns > 1` 直接回退，reader 融合也把 IP 的 dot product 当"距离"
直接相加（方向相反），exec 的 `order_by_index_distance` 对 IP 还按降序排。结果是 IP 多列融合
要么回退、要么顺序错误。

**改动**：
1. `lakesoul-io/src/reader.rs`：多列融合前把每列 score 统一成"越小越好"的距离——L2 取
   `sqrt(squared distance)`，IP 取 **负内积**；weighted sum 后按升序即"加权相似度降序"，
   单列 index-only 的 reserved distance 列也随之统一；
2. `vector_search_rule.rs`：
   - `negated_ip` 从"单列且权重为负"推广为"IP 且所有项权重为负、Sort 升序"（pgvector 多列 `<#>` 加权和）；
   - `collect_terms` 新增 `push_term`：系数作用在 `Negative(inner_product)` 上时（`0.7 * -(vec <#> q)`）
     先解包负号再加权，权重取正；此前这种写法会因项不是距离调用而整条不下推；
3. `table_provider.rs`：去掉"多列 + 非 L2 直接回退"，改为只要求**各列 metric 一致**
   （rule 已保证；手写 marker 也校验）；
4. `vector_search_exec.rs`：`order_by_index_distance` 不再按 metric 决定升降序——reader 已统一为
   "越小越好"，融合排序恒为升序；
5. 测试：
   - 规则级 `rule_multi_column_inner_product_fusion`：canonical `Σ w·IP DESC` 与 pgvector
     `Σ w·(-IP) ASC` 两种写法都生成 `order_by=true`、两列、权重 0.7/0.3、metric IP 的 marker；
   - 端到端 `sql_vector_search_multi_column_fusion_ip`（两列都建 IP 索引，`vec_b=vec_a` 让两列排名一致）：
     exact 模式保留 Sort 且 recall ≥ 0.5；`rerank=index` 时 Sort 消失、两列都进 exec、recall ≥ 0.5。
     原 L2 融合端到端测试 `sql_vector_search_multi_column_fusion` 同步回归通过。

**验证**：`lakesoul-datafusion --lib` **204 项全绿**；`lakesoul-io --lib` 全绿（reader 融合改动）。

**遗留**：混合 metric（L2+IP）加权和仍不下推（量纲不可比，属预期）；IP 融合的 QPS 未单独实测
（候选交集 + 融合在 reader 内完成，与 L2 融合同路径，预期同量级）。

### R78 — index-only 三级缓存：S3→SSD 复用 LakeSoul、SSD→Memory 借鉴 moka；MinIO 端到端验证

**背景**：index-only 之前只有进程内索引缓存（Memory）；重启/新节点/内存淘汰后仍要从 S3 重读
全部 segment 文件。payload 缓存只服务 exact，与 index-only 无关。

**改动**：

1. 新增 `rust/lakesoul-io/src/index/ssd_cache.rs`：
   - `IndexSsdCache`：持久化本地索引文件缓存，复用 `DiskCache` 的 moka 加权 LRU / 容量字节预算 /
     淘汰监听删除文件；索引文件按 whole-file 缓存；下载到 `.tmp` → fsync → rename；
     目录不清空，重启后已有文件按需惰性注册；env `LAKESOUL_INDEX_SSD_BYTES`（默认 0=关）、
     `LAKESOUL_INDEX_SSD_DIR`、`LAKESOUL_INDEX_SSD_KIND`；
   - `IndexCachedStore`：实现 `ObjectStore` 的 `get_opts`（HEAD/条件 GET 委托；普通 GET 从 L2 本地
     文件服务；miss 时从 S3 下载到 L2）；写/列举/删除全部委托；
   - 单测 3 项：字节/range、跨实例持久化、容量淘汰。
2. `rust/lakesoul-io/src/index/cache.rs`：内存索引缓存增加 `LAKESOUL_INDEX_MEMORY_BYTES`
   首选 env（兼容旧名）、hit/miss/eviction 指标、容量访问器。
3. `rust/lakesoul-io/src/vector/search.rs` 的 `load_shard`：
   `IndexStore::new(ssd_cache::wrap(store), prefix)`，仅索引加载经过 L2；数据文件读取不受影响。

**MinIO 端到端验证**（RELEASE.2025-09-07，本地 9000，bucket `lakesoul-test`；表 200,000 行 ×
128 维、4 桶、nlist=256、bits=1、top_k=10、nprobe=16、200 条真实 query；新进程 L1 为空）：

| 场景 | 首查延迟 | QPS | RSS | HWM |
|---|---:|---:|---:|---:|
| 基线：SSD 关闭（索引从 MinIO 读） | 103.8 ms | 562.9 | 278.0 MB | 387.9 MB |
| SSD 首次填充（1024 文件 / 16 MiB） | 504.5 ms | 557.8 | 280.9 MB | 387.7 MB |
| SSD 命中，且 S3 `_vector_index/` 已删除 | 174.6 ms | 533.4 | 278.6 MB | 387.6 MB |

第三行证明 L2 实际服务了 index-only：MinIO 数据文件仍可 HEAD，但 S3 上的索引对象已不存在，
查询仍成功且 top-1 一致；若 L2 miss 会出现 S3 404。本机 MinIO 延迟低，首查收益不如真实远程 S3；
SSD 首查 174.6 ms 主要是 1024 个小文件打开/解析开销，后续可合并 shard 文件或加预热。

**测试**：`cargo test -p lakesoul-io --lib index::ssd_cache` 3 项通过；Python 扩展 e2e 验证通过。

**清理**：drop `idx_cache_e2e`（PG table_info=0）、删除 MinIO `_vector_index/` 与表对象、
删除 `/tmp/lakesoul-index-ssd`、停止 MinIO 并删除测试数据目录。

### R79 — exact 三级缓存（S3 原始数据 → SSD payload → Memory 描述符/热点行），GloVe-200 MinIO 验证

**目标**：exact 的 payload 不再上传 S3；S3 只保留原始数据；本地 SSD 存 row-addressable
payload，内存缓存描述符/source 与可选热点行；减少随机候选读放大。

**改动**：

1. `rust/lakesoul-io/src/pk_locator/payload.rs`：
   - L2 payload 目录预算从“超预算直接放弃”改为 **mtime LRU 淘汰**：新 payload 放不下时
     删除最旧本地 payload 文件；只有单个 payload 大于总预算时才回退 reader；
   - 新增 **L1 可选热点行缓存** `LAKESOUL_PAYLOAD_ROW_CACHE_BYTES`（默认 0）：
     moka sync 加权 LRU，key=`(source_hash, kind_hash, column_pos, row_id)`，value=原始行字节；
     按候选行粒度，不做大块读，避免随机候选被放大成整块读取；
   - 新增 payload hit/build/eviction/row-cache 指标；
   - header 校验/不可变文件、tmp+rename 构建和 PK key index 依赖保持不变。
2. `rust/lakesoul-datafusion/src/datasource/file_format/vector_search_exec.rs`：
   仅做临时诊断后回退，无功能改动；exact fast path 逻辑保持原样。
3. N.B. exact direct 依赖现有 `LAKESOUL_CACHE` 提供的 PK key index；只开
   `LAKESOUL_VECTOR_RERANK_CACHE` 而不开 `LAKESOUL_CACHE` 时 exact direct 会回退 reader。

**GloVe-200 MinIO 端到端**（base 1,183,514 × 200d，4 桶，nlist=1024，bits=1，
top_k=100，nprobe=16，exact_overfetch=1，200 条真实 query，独立进程）：

| 场景 | 首查 | QPS | RSS | HWM |
|---|---:|---:|---:|---:|
| 无 payload（reader 解码整列） | 892.0 ms | 1.65 | 486.7 MB | 664.1 MB |
| payload 首次构建（903 MB 本地） | 1460 ms | — | — | — |
| payload 命中 + row cache | 543.2 ms | 279.9 | 442.3 MB | 442.3 MB |
| payload 命中，row cache 关（推荐） | 546.4 ms | **313.4** | **349.6 MB** | 349.6 MB |

**结论**：

- payload 命中约 **190×** 无 payload 基线，RSS 从 486.7 MB 降到 349.6 MB；
- **row cache 在随机 GloVe 查询下是负收益**（QPS 313.4→279.9，RSS +92.7 MB），
  因此默认 0，仅对重复/热点候选负载按需开启；
- MinIO 上只有 4 个数据文件 + `_vector_index/`，没有任何 payload 对象；
- 首查 546 ms 是 exact probe/coverage + 打开持久 payload/PK key index 的成本；
  真正冷构建一次约 1.46 s（903 MB 写本地），随后跨进程复用。

**测试**：`lakesoul-io --lib` payload 2 项（round-trip、预算淘汰）通过；
索引 SSD cache 3 项回归通过；GloVe 200 条 exact e2e top-1 与基线一致。

**清理**：drop `vec_glove_exact_e2e`（PG table_info=0），删除 MinIO 表前缀与
`/tmp/lakesoul-glove-payload`、`/tmp/lakesoul-glove-pk-cache`，停止 MinIO 并删除测试数据。

### R80 — batch 查询端到端 QPS/RSS：DataFusion / pgvector / Python（MinIO + GloVe-200）

**环境**：MinIO 本地，GloVe 1,183,514 × 200d，4 bucket，Vortex，nlist=1024、bits=1，
top_k=100、nprobe=16、exact_overfetch=1，200 条真实 query；exact 使用本地 payload
（903 MB，首次构建约 2 s，不计入 QPS）。

**结果（预热后 QPS / RSS）**：

| 入口 | index-only | exact |
|---|---:|---:|
| DataFusion SQL loop | 412.0 QPS / 303.5 MB | 315.2 QPS / 350.3 MB |
| DataFusion native batch (`Session.batch_search`) | 5,934.7 QPS / 293.9 MB | 6,492.2 QPS / 338.1 MB |
| Python `LakeSoulTable.search_batch` | 6,522.4 QPS / 286.9 MB | 9,801–11,075 QPS / 331.7–332.5 MB |

**结论**：

### R90 — Cluster-Lazy Index + 统一缓存预算（实现）

**实现**：

- `LazyIvfIndex`（`lakesoul-vector`）：新增 cluster-lazy 读取路径。
  - 每个 shard 先只读取 cluster 的 centroid（`read_segment_centroid` range read），
    建立 centroid selector；
  - 查询只选择 `nprobe` 个 cluster，按需读取这些 cluster 的 base/delta segment，
    合并后组装一个 selected-only `IvfRabitqIndex` 执行搜索；
  - cluster payload 进入全局 `ClusterCache`，按 `(index_prefix, commit_id, cluster_id)`
    区分，按字节预算 LRU；默认 1 GiB，可用
    `LAKESOUL_VECTOR_CLUSTER_CACHE_BYTES` 覆盖；
  - mutation、版本、`birth_version` 仍走原有 `assemble` 逻辑，不改变可见性语义。
- `LoadedShard`（`lakesoul-io`）改为 eager/lazy 二选一：
  - cluster 数 ≥64 自动 lazy，`LAKESOUL_VECTOR_LAZY_INDEX=0/1` 可强制；
  - lazy shard 句柄单独缓存，snapshot cache 只持有 MB 级 selector，不再把
    GB 级 index 放进 `CachedSnapshot`；
  - 任何 lazy 构建失败自动回退 eager，正确性不依赖 lazy。
- 统一预算配置：
  - `LAKESOUL_VECTOR_MEMORY_BYTES` 作为总预算提示；
  - cluster cache 默认取 60%，block cache 默认取 30%，snapshot 默认取 10%；
  - `LAKESOUL_VECTOR_SNAPSHOT_CACHE_BYTES` 替代硬编码 512 MiB；
  - block 行数改为按目标块大小自适应（`LAKESOUL_VECTOR_BLOCK_BYTES`，默认
    256 KiB），`LAKESOUL_VECTOR_BLOCK_ROWS` 仍可显式覆盖。
- pgvector 服务无需单独 cache：同一套 lazy index/cluster cache/预算通过
  `postgres-lakesoul` 生效；DataFusion 内存池继续用 `LAKESOUL_MEMORY_LIMIT`。

**正确性验证**：

- 新增 `lazy_search_matches_eager_search`：同一 512 向量 × 64 cluster 索引，
  lazy selected-cluster 搜索与 eager 全量搜索的 top-k ID 完全一致；
- Python 端 2 万行 × 8 维、nlist=128 表：lazy/eager 的 index/exact 单查询、
  batch 查询 ID 完全一致；
- `cargo test -p lakesoul-io --lib` → 195 passed, 1 ignored；
- `cargo test -p lakesoul-datafusion --lib` → 204 passed；
- Python `tests/vector/test_native_session.py` → **15 passed**；
- `lazy_search_matches_eager_search` → passed。

**Deep-Image 10M 实测（同一张表，nlist=1024, bits=1, nprobe=16, NQ=100）**：

| 指标 | eager | cluster-lazy | 变化 |
|---|---:|---:|---:|
| index 单查询 | 2.50 QPS / 首查 1933 ms / RSS 1412 MB | **65.57 QPS / 274 ms / 903 MB** | **26× / -36%** |
| index batch | 120.4 QPS / 430 ms / RSS 1419 MB | **699.2 QPS / 142 ms / 918 MB** | **5.8× / -35%** |

pgvector（同一张 Deep 表，nprobe=16，NQ=100）：

| 模式 | eager | cluster-lazy |
|---|---:|---:|
| index | 2.55 QPS | **64.39 QPS** |

**当前限制**：

- cluster directory 尚未持久化，首次 lazy open 仍要对每个 cluster 做一次 centroid

### R91 — 缓存配置收敛为 5 个公共变量

**问题**：三级缓存 + exact block + cluster lazy 之后，公开环境变量膨胀到
20 多个；用户需要理解每个子缓存的 budget/enable/path，且多 crate 各自读 env，
无法保证总预算。

**实现**：新增 `lakesoul_vector::cache_config::VectorCacheConfig`，启动时解析一次：

LAKESOUL_VECTOR_CACHE             总开关
LAKESOUL_VECTOR_MEMORY_BYTES      L1 总预算
LAKESOUL_CACHE_PATH               L2 根目录
LAKESOUL_CACHE_SIZE               L2 总容量（0 关闭）

- L1：snapshot 小预算、cluster ~60%、block ~30%、query 剩余；index-only 不占用

- `LAKESOUL_CACHE_SIZE`/`PATH` 现在同时启用 index SSD 与 exact block，不再要求
  单独的 `LAKESOUL_INDEX_SSD_*` 或 `LAKESOUL_CACHE=1`；
- 旧变量全部保留为 deprecated expert override，由 config 统一解析并打 debug 提示。

**代码接入**：

- `lazy.rs` cluster cache 预算；
- `pk_locator.rs` block cache/block 行数/block source；

- `object_store.rs` L2 启用；
- `index/ssd_cache.rs` index segment SSD；
- `vector_search_exec.rs` snapshot 预算；
- `postgres-lakesoul` 启动 warning 改为读 config。

**限制**：`LAKESOUL_CACHE_SIZE` 的 index/exact 50/50 是内部固定比例，后续可按负载

### R92 — 四数据集逐数据集缓存/参数基准（严格释放）

**目的**：在 cache 配置收敛和 cluster-lazy 后重新测 SIFT/GloVe/GIST/Deep，
记录 build time/RSS、recall、search QPS/延迟/RSS，覆盖 nlist/nprobe/nbits、
index-only/exact、cache on/off、单查询/batch。

**协议**：每个数据集单独：

```text
setup 写表 → 4 个 build 配置（nlist × bits）→ 8 个 search 配置
→ drop table + 删除 S3 前缀 + 删除本地 cache → 下一个数据集
```

这样避免上一轮 4 个数据集同时保留在 MinIO/本地 cache 导致磁盘/内存耗尽。

**结果摘要**：

- 建表写入：SIFT 3.1 s / GloVe 13.3 s / GIST 44.2 s / Deep 56.7 s；
- build：Deep nlist=4096 约 219–228 s、RSS 3.6–3.8 GB；nlist=1024 约
  66–74 s、RSS 3.6–3.8 GB；GIST build RSS 约 3.0–3.3 GB；
- cache on（L1 8 GiB + L2 16 GiB）：
  - SIFT：index 单查 160–265 QPS，exact 108–136，index batch 1.2k–7.0k，
    exact batch 1.1k–3.7k；
  - GloVe：index 132–258，exact 49–61，index batch 452–4.6k，exact 432–2.95k；
  - GIST：index 61–157，exact 12–14，index batch 195–2.2k，exact 159–617；
  - Deep：index 36–131，exact 6.2–9.5，index batch 148–1.66k，exact 134–627；
- cache off（NQ=20）：index 单查约 38–60 QPS，exact 单查 0.4–2 QPS，
  exact batch fallback 约 0.4–2 QPS；
- recall：nbits=7 显著高于 bits=1（SIFT nprobe16 0.61→0.89；GIST 0.69→0.80–0.93）；
- first latency：Deep nlist=4096 lazy 首次 index 查询约 20–30 s（16k cluster
  centroid range read），warm QPS 才回升；directory 持久化仍是后续优化项。

**注意**：

- cache on 的 RSS 包含 8 GiB L1 + 16 GiB L2 预算，GIST/Deep exact 峰值可达
  7–9 GB；cache off 的 RSS 低但 QPS 数量级下降；
- GIST-960 的 exact 单查仍受 block 读放大限制，约 12–14 QPS；
- adaptive block（目标 256 KiB）对 960 维使 block 更小，exact 单查相对早期
  256 行/块版本有退化风险，后续需按 exact QPS 重新评估目标块大小；
- 所有表/S3/cache 在每个数据集后已清理，PG 元数据归零。

### R94 — 流式索引构建输入 + Python 流式读

**构建读取流式（Phase 1）**：

- 新增 `lakesoul_io::index::reader::stream_shard_batches`，直接返回
  `Stream<Item = Result<RecordBatch>>`，不再先收集 `Vec<RecordBatch>`；
- fresh build / rebuild 走两遍 bounded streaming：
  1. pass 1：stream → reservoir sample；
  2. pass 2：再次 stream 同一个 shard → quantize；
- `LAKESOUL_VECTOR_STREAMING_BUILD=0` 可回退旧的 materialize 路径；
- 构建输出仍暂存在 `IvfRabitqBuilder` 的 cluster 中，phase 2（cluster chunk
  flush）尚未实现；因此当前收益是去掉 raw data 的完整 materialize，不是完全
  bounded memory。

**Python 流式读**：

- `LakeSoulSession.sql_stream(sql)`：PyO3 `NativeBatchStream`，按批拉取
  DataFusion 结果，不先 `DataFrame.collect()`；
- `LakeSoulTable.search_stream(query, ...)`：构造同一条向量搜索 SQL，
  返回可迭代的 Arrow batches；
- 测试：`tests/vector/test_native_session.py` 新增
  `test_streaming_build_and_streaming_reads`，共 16 passed。

**DataFusion**：Rust `DataFrame::execute_stream()` 本来就是流式；本轮把
`stream_shard_batches` 接入了索引构建读取路径。**pgvector**：pgwire 查询仍由
server 收集结果后发送，尚未接入 `NativeBatchStream`，是后续工作。

### R96 — Phase 2：cluster chunk flush

- `IvfRabitqBuilder` 新增 `build_with_chunk_flush`：
  - pass 2 每处理完一个输入 batch，检查 cluster 的 `memory_bytes()`；
  - 超过 `LAKESOUL_VECTOR_BUILD_CHUNK_BYTES`（默认 64 MiB）的 cluster
    立即 `flush_pending` → 写 segment（version 递增）→ 清空缓冲；
  - 构建结束再 flush 所有剩余 cluster；
  - 返回的 index 只保留 centroid/header，不再持有全量 cluster 数据；
  - 同一个 cluster 可产生多个 segment（version 0/1/...），查询侧
    现有的 segment merge 逻辑直接支持。
- IO builder 的 fresh streaming 路径改用 `build_with_chunk_flush`，
  不再调用 `write_base_segments`，因此构建输出内存由 chunk 阈值控制。
- 验证：
  - `LAKESOUL_VECTOR_BUILD_CHUNK_BYTES=1024` 强制大量 chunk 的
    Python 15 项测试通过；
  - `cargo test -p lakesoul-io --lib` → 195 passed, 1 ignored；
  - `cargo test -p lakesoul-datafusion --lib` → 204 passed。

### pgvector 搜索本来就是流式的

`datafusion-postgres` 的 `arrow-pg` `encode_dataframe` 使用：

```text
DataFrame::execute_stream()
  → RecordBatch stream
  → per-batch DataRow stream
  → QueryResponse { data_rows: SendableRowStream }
```

`pgwire::send_query_response` 再逐行 `feed(DataRow)`，所以 pgvector 的
结果路径没有 `collect()` 全量结果；现有 SQL 接口不需要改动。

Python 侧保持原有 `search` / `sql` 接口不变，内部改用 native
`NativeBatchStream` 按 batch 拉取后再组装 Arrow Table；DataFusion 侧
`DataFrame::execute_stream()` 也是相同的流式执行，只是不新增对外接口。

### R98 — 缓存兼容性审查

发现并修复了统一配置对旧 LakeSoul cache 设计的影响：

- 旧部署默认 loaded-index 512 MiB、snapshot 512 MiB、block 256 MiB、
  block rows=256；统一配置最初会把它压成 cluster 307 MiB / snapshot 64 MiB /
  block 153 MiB / adaptive block；
- 旧 `LAKESOUL_CACHE_SIZE` 原本全量给通用 `DiskCache`；统一配置最初默认取一半；
- 旧 `LAKESOUL_INDEX_SSD_DIR` 原本直接作为根目录，统一配置最初会追加
  `/index-cache`；
- `LAKESOUL_VECTOR_CACHE=0` 时确实要关闭所有 L1/L2 子缓存。

修复：

- 引入 `unified` 判定：只有显式使用 `LAKESOUL_VECTOR_CACHE` 或
  `LAKESOUL_VECTOR_MEMORY_BYTES` 才启用 60/10/30 新预算；
- 旧变量/旧默认值保持原语义，包括 512/512/256 MiB、legacy block rows、
  全量 DiskCache、旧 index-SSD 目录；
- `LAKESOUL_VECTOR_CACHE=0` 强制 cluster/snapshot/block/index-SSD 全为 0；
- 新增 `cache_config::tests` 覆盖 legacy 默认、legacy override、unified split。

验证：

```text
cargo test -p lakesoul-vector cache_config::tests -- --test-threads=1
3 passed
```

审查 streaming：

- pass1/pass2 读取流式、chunk flush 已生效；
- `stream_shard_batches` 的 stream 当前不是 `Send`；若未来把 build future
  丢进 `tokio::spawn`，需要先解决 reader stream 的 Send 约束；
- chunk flush 会让同一 cluster 产生多个 version segment，默认 64 MiB；
  A/B 显示 SIFT 查询 QPS 基本不变，但仍需按 generation 统计 segment 数。

**补充**：旧部署的 `LAKESOUL_CACHE_SIZE` / `LAKESOUL_CACHE_PATH` 单独设置
仍然不启用 L2，必须同时设置 `LAKESOUL_CACHE=1`；只有显式使用
`LAKESOUL_VECTOR_CACHE` 或 `LAKESOUL_VECTOR_MEMORY_BYTES` 的统一模式，
才允许由 `LAKESOUL_CACHE_SIZE/PATH` 直接启用并 50/50 拆分。
