# 向量检索方案对比：最初 vs 现在

> 本文对比 LakeSoul 向量检索"最初实现"与当前 HEAD 的**最终方案**，按能力层次组织，而不是按提交轮次。
> 逐轮改动、A/B 和回滚记录在 `向量查询优化日志.md`，本文只保留最终形态、设计原因和验收数据。
>
> **覆盖入口**：
> - 单查询 SQL：index-only（默认，`rerank='index'`）与 exact 重排（显式 `rerank='exact'`）；pgvector `<->` 也默认 index-only；
> - 快照批量入口：`provider.vector_batch_search(state, {queries, top_k, nprobe, metric, exact, ...})`；
> - 通用性入口：任意投影、`WHERE` 过滤、多文件桶/多版本、CDC 表、范围分区表（都走同一候选执行栈）；
> - pgvector 兼容服务（`postgres-lakesoul`）：复用同一执行栈。
>
> **基准**：GloVe-200，1,183,514 条 base / 200 条真实 query / 200 维 / nlist 1024 / **nbits=1** /
> 4 个 hash bucket / top_k 100 / KVM 虚拟机（8 物理核 16 逻辑核，AVX-512）/ 构建与搜索分进程；
> 大批量另用 10,000 条 query + GT。
>
> **数字口径**：文中"默认"指 `LAKESOUL_METADATA_TTL_MS=0`（默认关，语义与最初完全一致）；
> "TTL=200"指显式开启 200 ms 元数据复用后的推荐工作点。两者功能正确性完全相同，只是
> "新提交/DDL 何时可见"的口径不同。机器状态（page cache、表重建、是否预热）会带来 ±5–10% 波动。

---

## 0. 结论

最初的向量检索是 **"通用 DataFusion 规划 + reader 读数据文件做精确重排"**：
每条语句从建 provider/reader、加载索引起步，exact 还要回读整列向量；没有 index-only、没有批量入口、
没有 IP 索引排序，过滤/CDC/分区/多文件桶/任意投影都会回退到 reader。

现在是一套 **"句柄化查询 + 索引直达扫描 + 只读候选行"** 的统一执行栈：
- 查询向量在 analyzer 里折成句柄，索引序直接作为结果序；
- 需要精确重排时，从按需 decoded-block cache 只读候选块，不再解码整列；
- 同一 snapshot 的批量查询共享一次装载/解析，候选读取和排序全核并行；
- 多文件桶/多版本、任意投影、过滤、CDC、分区都在候选路径内解析，不再"特殊表就慢"；
- IP 与 L2 在单查询、批量、index-only、exact、多列融合五种组合下同速。

> **整文件 payload 已移除**：`LAKESOUL_VECTOR_RERANK_CACHE*` 不再存在。下面部分
> exact 数字是历史 payload 模式（用于展示优化过程），**不代表当前版本**；当前 exact
> 只走按需 decoded-block cache，实测见 [exact三级缓存.md](exact三级缓存.md)。

> `15.8 QPS` 是 exact 无缓存 reader 基线；`70.0 QPS` 是当前按需 decoded-block 模式

### 0.2 一句话概括改了什么

| 层次 | 最初 | 最终 |
|---|---|---|
| 查询表示 | 200 维向量、200 个表达式节点进入 plan，每轮 optimizer 都要遍历 | 8 字节句柄（进程内 registry），plan 保持最小 |
| 规划 | 默认 analyzer/optimizer/physical planner 全流程 | 折叠 + 下推 + 已知形状的快速物理计划，通用流程只作为回退 |
| index-only | 不支持；排序/回退 reader | 索引序即结果序，直接输出 PK，不读数据文件 |
| exact | reader 逐桶建计划，回读整列向量做 exact re-rank | 按需 decoded-block cache + 直读候选块 + 精确排序融合，无 SortExec |
| 批量 | 无入口，逐条 SQL | 同 snapshot 批量入口，一次装载/解析，全核探测与合并 |
| 通用性 | 特殊表形态（多文件/多版本/任意投影/过滤/CDC/分区）回退 | 统一候选路径；正确性由逐候选可见版本和 merge-on-read 保证 |
| 距离度量 | L2 快路径；IP 只有 exact 可用 | L2/IP 在单查询、批量、index-only、exact、多列融合均可用 |
| 元数据/并发 | 每语句重新查 PG；进程级 `Mutex` 串行化 | 可选的 TTL 复用（默认关）；读并发 `RwLock` |
| 缓存 | 无跨语句缓存；每次都从 S3 重新读索引，exact 回读整列 | 多层缓存：可选元数据 TTL、provider/文件列表/分片/索引解析缓存、**index-only 的 S3→SSD→Memory 索引缓存**、**exact 的按需 decoded-block 缓存（不写 S3）**；见 §2.8 |

## 1. 最初的方案（baseline）

### 1.1 单查询执行流程

```
SQL 文本（含 200 个浮点字面量）
  │
  ├─[parse] sqlparser：AST（ARRAY[200 个字面量]）                      ~0.21 ms
  │
  ├─[analyze] name resolution
  │    └─ catalog.table()：PG 查表信息 + 每次新建 LakeSoulTable / Provider
  │         （解析 Arrow IPC schema、properties、partitions、建 IOConfig、初始化 format）
  │    └─ SqlToRel：ARRAY[...] → Expr::make_array(200 个 Expr)           ~1.17 ms
  │
  ├─[logical optimizer] 默认 25 条规则 × 多轮                           ~0.35–0.82 ms
  │
  ├─[physical planner] DataFusion 默认 planner
  │    └─ 逐节点转换 + 一整轮物理优化器                                  ~1.15 ms
  │
  └─[exec] LakeSoulVectorSearchExec —— reader 路径                       ~13–15 ms
       ├─ 解析索引 commit（PG 往返）
       ├─ 装载各 bucket 分片索引（每次查询）
       ├─ 为每个 bucket 建 reader 配置：打开数据文件、读 schema、
       │    merge-on-read 的 mutation 链检查
       ├─ ANN probe 4 个 bucket（串行）
       ├─ 回读数据文件里的向量列做精确重排（exact re-rank）
       ├─ 按精确距离排序
       └─ 再读 id payload 输出
```

### 1.2 为什么最初慢

1. **每语句重复搭建**：provider、reader、索引分片、文件列表都没有跨语句复用；数据文件不可变，
   同一快照的重复查询仍从头来过。
2. **读放大**：为了返回 `id`，先读整列向量做精确重排、再读 payload；exact 的 1000 个候选
   几乎覆盖整列向量（4 桶 ≈ 944 MB/query），45–66 ms 花在 `take_rows`。
3. **排序在 DataFusion 里做**：`Sort` 先把候选行物化再排序，代价随候选数增长；exec 内部已经算过
   的距离又被上层 Sort 重算一遍。
4. **plan 带着 200 维向量**：analyzer/optimizer 每轮遍历、签名、不变量检查都要走 200 个表达式节点
   （或 2.6 KB 的 CSV 字符串）。
5. **通用 planner 对该形状是纯开销**：最终形状是确定的（Limit + 向量扫描），逐节点转换和物理优化器
   不产生收益。
6. **进程级互斥**：元数据客户端一把 `Mutex` 把所有元数据查询（含纯读）串行化，并发语句排队。
7. **能力缺失**：没有 index-only、没有批量入口、没有 batch exact、IP 只有 exact、没有过滤/任意投影/
   多文件桶/多版本/CDC/分区表的候选路径——这些场景只能回退 reader（13–25 ms/query，40–75 QPS）。

## 2. 现在的方案（最终形态）

### 2.1 总览：一套统一执行栈

```
SQL / batch API / pgvector(PostgreSQL wire)
        │
        ▼
查询改写与规划
  ├─ analyzer：把 distance(col, 常量向量) 折叠成 __lakesoul_vector_distance(col, @handle, metric)
  ├─ pushdown rule：Limit/Sort(distance)/[Projection/Filter]*/TableScan
  │       → TableScan(projection, marker, filter, fetch)，Sort 消失（index 序 = 结果序）
  └─ planner 快路径：形状匹配 → provider.scan + GlobalLimitExec（否则回退通用 planner）
        │
        ▼
VectorSearchExec（单查询）/ VectorBatchSearch（批量）——共用：
  ├─ 快照身份（store + 文件列表 + 检索列）→ 分片/解析缓存
  ├─ 分片 ANN probe（按桶并行；IP/L2 按 metric 选方向）
  ├─ 候选去重/部分排序 → 只解码 top_k 个 key
  ├─ index-only：直接输出 PK batch，不读数据文件
  └─ exact：decoded-block 缓存 + mmapped key index 定位候选块，
             精确 L2/IP 打分 → 融合排序（上层 Sort 已消除）→ 只保留 keep_rows
        │
        ▼
通用性扩展（同一候选路径）：
  多文件桶（每文件 key→rowid 映射）· 多版本（按文件年龄取最新）·
  任意投影（keep 行二次读取 payload 列）· WHERE 过滤（谓词下推 + 迭代扩探）·
  CDC 墓碑（op != delete）· 范围分区（按分区×桶读取）
```

所有缓存都绑定**不可变身份**：provider 指纹（表信息 + catalog options）、快照分片（store + 文件列表 +
检索列）、文件列表（table/partition/version）、**index-only 的索引文件（对象路径 + commit）**、
block key（data file 位置 + 列类型 + block id）、block source（文件位置 + 列类型）。数据文件/快照不变，
缓存就复用；compaction 换文件名自然失效。缓存分两类生命周期：**Memory 里的解析结果**（provider/分片/
block source，进程级、可淘汰）和**本地 DiskCache 里的 decoded block**（进程内按需重建、容量淘汰）；
S3 始终是索引文件和原始数据的唯一真相来源，**exact 不上传任何 payload**。

### 2.2 单查询 index-only

**最终流程**

```
SQL
  → parse（~0.21 ms，未变）
  → analyze：provider 复用 + 字面量折叠为句柄（~0.60 ms）
  → 逻辑优化：pushdown 规则消掉 Sort（~0.20 ms）
  → 物理规划快路径：provider.scan + GlobalLimitExec（~0.19 ms）
  → exec（~0.36–0.44 ms）：
       快照缓存命中（resolve 0 / load 0.005 ms）
       → 4 桶并行 ANN（~0.30 ms）
       → 去重 + select_nth 取 top_k + 只解码 100 个 key（~0.06 ms）
       → 输出 PK batch
```

**关键设计**

- **索引序即结果序**：index-only 不需要精确重排，Sort 和候选向量读取全部消掉；PK 就是答案。
- **句柄化**：plan 里只剩 8 字节句柄；optimizer 的遍历/签名/不变量检查与 plan 大小线性相关，
  这直接省掉 ~0.15 ms/语句。UDF 求值仍委托内置距离函数，语义等价。
- **provider/文件列表/分片缓存**：不可变数据只解析一次；"最新快照"每语句只保留两次 PG 查询（表信息 + 分区版本），
  其余命中缓存。
- **快速物理计划**：形状匹配（Limit→排序→扫描）时跳过逐节点转换和物理优化器，用计划树/schema
  双重校验保证不误伤；不匹配自动回退。
- **只解码 top_k**：上层 LIMIT 只要 100 行，候选 800 行里其余 700 行的解码/构列是白做。

**最终指标**：默认 525–553 QPS / p50 1.69–1.78 ms / RSS 231–234 MB；TTL=200 时 680–706 QPS /
p50 1.29–1.36 ms。与纯 Rust 同一流程相比，exec 已贴近 4 个 shard 的 ANN 下限（~0.30 ms）。

### 2.3 单查询 exact 重排

**最终流程**

```
SQL（rerank='exact'）
  → 同样的句柄化 + 快速物理计划（exact 形状）
  → exec：
       快照分片缓存 + 覆盖性证明
       → 每桶一个阻塞任务：ANN probe → 候选 key 排序/去重
       → decoded-block cache 读候选块 + mmapped key index 找行号（4 桶并行）
       → 精确 L2/IP 打分 → 跨桶合并
       → 按精确距离排序，只保留 keep_rows = max(fetch, top_k)
       → 输出 PK（若投影还有额外列：用 pk IN (...) 对 keep 行二次读取输出列）
```

**关键设计**

1. **按需 decoded block**：按（数据文件, 向量列, block id）只解码候选块，默认 256 行/块；
   不存在整文件 payload。数据文件不可变，block 只是派生缓存，删掉可重建，结果逐位一致。
2. **exact 直读**：跳过每桶 reader/session/plan/merge 的搭建，直接在 block cache + key index
   上定位候选行；多桶的读取在 blocking 池并行；候选 key 排序后用单调 galloping 替代逐 key 二分。
3. **融合与去 Sort**：exec 内部已经按精确距离选 keep 行，输出即有序；快速物理计划因此去掉
   `SortExec`；narrow 下 keep_rows 只保留目标行数。
4. **block source 缓存**：同一数据文件的 block cache/key index 在进程内复用，避免每查询每桶重开。
5. **可选元数据 TTL**：默认关闭；开启后省掉每语句两次 PG 往返。

**最终指标**（GloVe-200、block 256、L2=1GiB、MinIO）：

- 单查询首查 792 ms、warm **70.0 QPS**、RSS 873 MB；
- 重复热查询 83.7 / 107.3 / 107.9 QPS；
- batch exact（200 query）首 batch 2131 ms、warm **386.6 QPS**、RSS 859 MB；
- 历史无缓存 reader 基线 1.65 QPS；历史整文件 payload 的 300+ QPS 已随 payload 移除。

**参数选择**：提高 `nprobe`、适当调 `exact_overfetch`；必须保证 L2 预算覆盖工作集，
否则 block 频繁淘汰会严重降速。

### 2.4 快照批量入口

**最终流程**

```
provider.vector_batch_search(state, {queries, top_k, nprobe, parallelism, batch_size, metric, exact})
  → 当前 snapshot 文件列表（版本键缓存）
  → 每批一次 resolve_cached_many（Arc view，零克隆）
  → 每桶一个 OS 线程 ANN（桶内 rayon 用满全池）
  → index-only：排序/去重/解码/跨桶 top-k 融合成按 query 的并行区
  → exact：候选 × overfetch，payload + key index 读向量，就地打分跨桶合并，只解码胜出的 top_k
  → 分块 1024 query/块、最多 2 块在飞（RSS 有界），结果按块序还原
  → 输出每 query 的 top-k 主键
```

**关键设计**

- **同 snapshot 一次装载**：每桶整批只 load 一次索引、整批一次 resolve、一次覆盖性校验读；
  能证明"索引提交覆盖桶内全部 active 文件"时跳过 liveness 校验读（不能证明时保留校验路径）。
- **按桶并行 + 排序合并融合**：4 个桶各自 OS 线程并行 probe（原来"并行"实际串行，只用 ~5.3/16 核）；
  rank/去重/解码按 query 铺满全核；排序与跨桶合并融合成一个并行区，避免两次 spawn。
- **typed shard + 零拷贝**：不再每批 JSON 序列化/解析 1024 条 segment；排序时直接解码 key 引用，
  不逐候选 clone。
- **批量 exact**：候选 × overfetch，block source 共享，取向量按核调度、就地打分（不构造 Arrow ListArray），
  跨桶合并按 query 并行；条件不满足时返回明确错误，不静默退回近似结果。
- **有界内存**：10k query 分块，peak RSS 从 547 MB 降到 ~350 MB，QPS 不降。

**最终指标**

| 场景 | QPS | p50 | RSS | Recall |
|---|---:|---:|---:|---:|
| 批量 index-only，200 query | **11,410–12,113** | 0.079–0.084 ms | 237 MB | 0.42035 |
| 批量 index-only，10,000 query | **11,915–14,250** | 0.067–0.072 ms | 346–348 MB | 0.43784 |
| 批量 exact，200 query（block） | **386.6** | 2.59 ms | 859 MB | 0.6419 |

- index-only 端到端 ≈ 纯 Rust 手写流程检索段的 **83–85%**（合并流水线的 105%+）；
  CPU/query ≈ 1.0–1.15 ms，就是 4 个 shard 的 ANN 本身；
- exact block ≈ index-only 的 **3.4%**；瓶颈是候选块解码/读取与 block 缓存布局；
- 相对单查询 exact（70 QPS）batch 入口约 **5.5×**；
- 整文件 payload 快速路径已删除，不再有 5–7k 的 batch exact 数字。

### 2.5 通用性：不再要求表的特殊形态

最初只有"1 文件/桶 + 无 filter + 投影 = PK+向量列 + 无 CDC/分区"才可能走快路径；真实业务表往往
不满足，于是回退 reader（13–25 ms/query，40–75 QPS）。最终方案把这些要求逐个去掉，并保证正确性：

| 场景 | 最初 | 最终做法 | 正确性依据 |
|---|---|---|---|
| **多文件桶** | 必须 1 文件/桶，否则回退 | 桶内每个文件建 key→rowid 映射 + payload；候选 key 恰好命中 1 个文件才直读，多/零命中回退 | 命中唯一文件 = 该 key 的可见行；compaction 不再是前提 |
| **多版本（upsert）** | 直接回退 reader | 同一 key 命中多个文件时取"文件年龄"最大者；年龄由覆盖该文件的 segment `birth_version` 给出，年龄并列则回退 | 年龄取最新 = LSM 的"新覆盖旧"；覆盖性证明仍要求索引覆盖快照全部文件、无 pending 文件 |
| **任意投影** | 投影必须 = PK + 向量列 | 额外列在 keep 行上用 `pk IN (...)` 二次读取、按排名重排、投影到计划 schema | 额外列来自同一批数据文件、由同一批主键定位；行/列对应与 reader 一致 |
| **`WHERE` 过滤** | 候选后过滤；低选择性时返回 0 行，且快路径失效 | 谓词随 marker 下推到 scan；候选行读回后进程内求值；不足 keep 行时候选集 ×4 扩探（上限 64） | 候选行先过滤再排序，上层 Limit 拿到"过滤后 top-k"；另读路径用 payload-only 避免被 native reader 自身候选集二次截断 |
| **CDC 删除** | 有 CDC 列就回退 | 候选行读回后按 `cdc != 'delete'` 求值；覆盖性证明放宽为"索引覆盖快照全部数据文件" | 墓碑由 merge-on-read + 本进程谓词双重丢弃；mutation 链掩蔽被删 key，候选不会包含它们 |
| **范围分区表** | 有分区列就回退；旧 reader 兜底还缺分区列 | 按"分区×桶"独立 probe/读取（只读自己的文件，不会跨分区取到同 key 重复行）；谓词用 candidate_schema；兜底路径投影回计划 schema | 每个 work unit 只读自己的分区文件；分区裁剪在前，主键过滤不会跨分区 |

每个场景都有端到端测试断言"确实走了候选路径"（test-only 计数器）+ recall/暴力 top-k 对照；
任一条件不满足（谓词编译失败、覆盖性证明不成立、年龄并列等）都会显式回退 reader，结果不变，只是慢。

**仍未做**：额外列的二次读取目前复用 reader（约 +2–4 ms/query）；过滤扩探的起始倍率固定 ×4，
未用统计信息；多文件桶/upsert/分区大表的 QPS 还缺大规模实测。

### 2.6 IP（内积）与多列加权融合

最初：RaBitQ 的 IP 实现完整，但上层把 index-only 排序锁死在 L2，pgvector `<#>` 不被下推、
批量 IP 直接报错、多列融合只支持 L2（IP 融合方向错误）。
最终：

- **单查询**：下推规则识别 `Expr::Negative`，把 pgvector `-inner_product(vec,q)` 归一化为"正权重 + 规范方向"；
  允许 L2 ASC / IP DESC / 负内积 ASC；单列 index-only 支持 L2 或 IP；exec 去重/排序按 metric 取方向。
- **批量**：`VectorBatchRequest.metric` 贯穿去重、跨桶合并、精确打分；请求 metric 必须与表索引一致，
  不一致明确报错。
- **多列加权融合**：reader 融合前把每列 score 统一成"越小越好"（L2 → sqrt(sq)、IP → 负内积），
  加权和升序 = 加权相似度降序；支持 `Σ w·IP DESC` 与 pgvector `Σ w·(-IP) ASC`（包括 `0.7 * -(vec <#> q)`）；
  provider 不再因"多列 + 非 L2"回退，只要求各列 metric 一致。
- **实测结果**：IP 与 L2 在单查询/批量/index-only/exact 四组合下都是 96–104%；pgvector `<#>` 与
  DataFusion `inner_product(...) DESC` 两种写法结果逐条一致（200/200 id 列表相同）。
  单查询 IP exact 511.7 / index-only 675.1 QPS；批量 10k IP exact 7,060–7,146 / index-only 11,833–11,915 QPS。

仍未覆盖：混合 metric（L2+IP）多列融合（量纲不可比，属预期限制）；IP 多列融合的 QPS 未单独实测。

### 2.7 pgvector 兼容服务：同一执行栈

`postgres-lakesoul` 的 pgvector 兼容层（`<->`/`<#>`/`<=>`、`SET ivfflat.probes`、向量参数/结果类型）
复用同一个 `VectorSearchExec`，因此上面的优化对服务端全部生效；服务端特有的固定开销也压掉了：

- pgvector 形态的 list 字面量同样折叠成句柄；
- 每语句的 SQL 兼容解析器改为进程级复用，文本没有 `;` 时直接早退（`SELECT 1` 0.79 → 0.31 ms）；
- 向量参数/结果按 vector OID 编解码，`register_vector()`/numpy 参数可用；
- exact 业务必须配 `LAKESOUL_CACHE` 的 decoded-block 缓存（否则回退 reader，明显更慢）；
- 服务端进程同样启用 index-only SSD 缓存与 decoded-block 缓存，缓存只影响加载路径，
  不改变 SQL 结果；S3 上不存在 payload。

**实测**（GloVe-1.18M×200d、200 条真实 query、单 psql 连接）：服务端 exact 591/598 QPS、
index-only 791/782 QPS，与进程内 DataFusion（exact 528 / index-only 697）差距约 5–10%
（早期是 15–19%）。

### 2.8 缓存机制（S3 → SSD → Memory）

缓存不是单一组件，而是按“数据是否不可变、读什么、能否重建”分成多层；每层只解决一种放大：

```
S3（唯一真相：原始数据文件 + 索引文件）
  │
  ├─ index-only 索引文件 ──→ IndexSsdCache（本地 SSD，持久，整文件）
  │                              │
  │                              └─→ index memory cache（解析后的 IvfRabitqIndex，512 MiB）
  │
  ├─ exact 原始向量列 ──→ 按需 decoded blocks（DiskCache，S3→SSD）
  │                              │
  │                              ├─→ L1 moka block cache（默认 256 MiB）
  │                              └─→ VectorBlockSource（block + mmapped key index）
  │
  └─ metadata（table_info / partition list）─→ 可选短 TTL（默认关）
```

> 缓存配置已收敛为 5 个公共变量：`LAKESOUL_VECTOR_CACHE`、
> `LAKESOUL_VECTOR_MEMORY_BYTES`、`LAKESOUL_CACHE_PATH`、`LAKESOUL_CACHE_SIZE`、
> `LAKESOUL_VECTOR_LAZY_INDEX`。下表旧变量名仅作历史说明。

| 缓存层 | 缓存内容 | 介质/生命周期 | 关键配置 | 作用 |
|---|---|---|---|---|
| 元数据 TTL | `table_info`、分区列表 | 进程内，TTL（默认 0=关） | `LAKESOUL_METADATA_TTL_MS` | 省每语句两次 PG 往返；代价是最多 N ms 可见性延迟 |
| provider/文件列表 | provider 指纹、文件列表 | 进程内，不可变键 | 无 | 避免每语句重建 provider/重列文件 |
| 快照/索引解析（L1） | `IvfRabitqIndex`、cluster directory、commit view | 进程内 moka/锁缓存 | `LAKESOUL_VECTOR_MEMORY_BYTES`（默认 512 MiB，内部自动分配） | 索引只解析/加载一次；commit 变化失效 |
| **index SSD（L2）** | 索引对象整文件（segment/manifest/...） | 本地 SSD，**持久**，字节预算 LRU | `LAKESOUL_CACHE_PATH`、`LAKESOUL_CACHE_SIZE`（内部约 50% 分给 index） | S3→SSD，重启/新节点不必重读全部索引文件 |
| **decoded block（L2，默认）** | 候选行按自适应 block 解码后的 f32 block | 复用统一 DiskCache；按需增长 | `LAKESOUL_CACHE_PATH`、`LAKESOUL_CACHE_SIZE` | 只解码候选块，不一次物化整列；S3-SSD 复用 |
| **block source（L1）** | `VectorBlockSource`、mmapped key index | 进程内，文件+列身份 | 固定容量（16 sources） | 避免每 query 每桶重新 open key index；默认开 |
| PK key index cache | 候选 key→rowid 的 mmap 索引 | 本地磁盘（统一 DiskCache） | `LAKESOUL_CACHE_PATH`、`LAKESOUL_CACHE_SIZE` | exact direct 定位候选行所需；未开启时 exact 回退 reader |

#### index-only：S3 → SSD → Memory

- 索引文件不可变：`IndexSsdCache` 按对象路径哈希缓存**完整文件**，下载走
  `tmp → fsync → rename`，重启不清空目录；
- `IndexCachedStore` 实现 `ObjectStore`，只包装 shard 加载用的 `IndexStore`；
  `get`/`get_range` 从本地 SSD 服务，HEAD/写/列举仍委托 S3；
- 内存层仍是原有的 moka 加权 LRU：key=`(kind, prefix, commit_id)`，commit 变化即失效；
- 因此缓存层级是 **S3（源）→ SSD（持久文件）→ Memory（解析后的索引）**，
  删掉 SSD 目录只会导致下次重建，不影响正确性。

**MinIO 200k×128 A/B（索引对象删除验证）**：

| 场景 | 首查 | QPS | RSS |
|---|---:|---:|---:|
| 基线（SSD 关闭，索引读 MinIO） | 103.8 ms | 562.9 | 278.0 MB |
| SSD 首次填充（1024 文件 / 16 MiB） | 504.5 ms | 557.8 | 280.9 MB |
| SSD 命中，且 S3 `_vector_index/` 对象已删除 | 174.6 ms | 533.4 | 278.6 MB |

第三行证明 L2 确实在服务 index-only：S3 索引对象不存在时查询仍成功；本机 MinIO 延迟低，
SSD 首查收益不如真实远程 S3，稳态 QPS 主要受 ANN/CPU 限制。

#### exact：按需 decoded-block，不写 S3

- **整文件 payload 已移除**；候选行按 `(data_file, column, block_id)` 分组，默认 256 行一块；
- 只解码命中的 block，写入 `LAKESOUL_CACHE` 的 DiskCache（S3→SSD）和 L1 moka；
- 不再有 payload 描述符/payload 文件/row cache 开关；
- exact direct 依赖 `LAKESOUL_CACHE` 提供 block cache 与 PK key index；未开启时回退 reader；
- GloVe-200 / MinIO 当前实测：单查询首查 792 ms、warm 70 QPS、RSS 873 MB；
  batch exact（200 query）首 batch 2131 ms、warm 386.6 QPS；
- 历史无缓存 reader 基线 1.65 QPS 仅用于说明读放大，不再与 payload 模式对比。

#### 读放大与缓存边界

- index-only 不读数据文件；exact 只读候选行（100 候选 × 800 B = 80 KB/query）；
- 不用 256 KiB 大块缓存随机候选（会把 80 KB 放大到数十 MB）；
- 缓存只改变“从哪里读”，不改变快照、merge-on-read、CDC、分区语义；
- 缓存未命中/损坏/超预算时都回退原路径，结果不变。

详细实现与单测见 `index-only三级缓存.md`、`exact三级缓存.md`、`batch查询性能.md`。

## 3. 为什么现在快：完整原因

### 3.1 六类根本原因

| # | 原因 | 最初的做法 | 最终的做法 | 典型收益 |
|---|---|---|---|---|
| 1 | **不可变数据被重复处理** | 每语句重建 provider/reader；每次查询重新 resolve 分片、列文件、打开 payload；索引文件每次从 S3 读 | provider 指纹复用；快照分片/文件列表缓存；**index-only 索引文件走 S3→SSD→Memory 缓存**；decoded block 按文件身份复用；block source 进程缓存；批量一次装载 | index-only 从 61 到 300+；exact 3×；批量 70×；source 缓存 +22% |
| 2 | **读放大** | exact 回读候选覆盖的整列向量（944 MB/query）；批量重复装载 | payload 按行序物化，候选只 `pread` 800 B/行；index-only 不读数据文件；只解码 top_k；keep_rows 裁剪 | 15.8 → 310.9 QPS；RSS 1093 → 277 MB |
| 3 | **重复计算** | plan 里保留 200 个表达式/2.6 KB 字面量，optimizer 每轮遍历；批量每批 JSON 往返；排序/合并两遍；上层 Sort 重算距离 | 句柄化；typed shard；排序-合并融合；零拷贝解码；exec 内精确排序并去掉 SortExec；narrow 下只保留目标行 | optimizer 0.82→0.31 ms；exact +8.2%；批量 +96.5% |
| 4 | **固定开销与等待** | 每桶建 reader/session/plan/merge；每语句两次 PG 元数据往返；每语句构造 SQL 兼容解析器；线程池往返 | exact 直读跳过 reader；物理规划快路径；单 query probe 直连；parser 进程级复用；可选元数据 TTL；任务按核调度 | planner 1.15→0.19 ms；服务端 exact +31%、index +39%；TTL +20–31% |
| 5 | **通用性/正确性要求** | 特殊表形态（多文件/多版本/任意投影/WHERE/CDC/分区）直接回退；IP 被锁在 L2 | 候选路径内解析可见版本/过滤/CDC/分区；多文件桶、多版本按年龄取新；任意投影二次读取；IP/多列融合全链路支持 | 从 13–25 ms/40–75 QPS 回退恢复到候选路径；语义不变 |
| 6 | **测量方法错误** | benchmark 探针 SQL 硬编码 L2，IP 表上回退全表扫描；冷启动/单次噪声污染结论 | SQL 按 metric 生成；批路径预热；冷/热分开测 | IP 从"76–80%"修正为 96–104% 对齐 |

### 3.2 最终方案的设计原则（也是"为什么这么做"）

1. **索引是排序的真相来源**：index 返回的顺序就是结果顺序；能在索引层完成的排序，绝不进 DataFusion Sort。
2. **不可变数据只处理一次，缓存键必须是不可变身份**（表指纹/文件列表/commit/文件位置+列布局）；
   新鲜度语义靠"每语句读最新表信息/快照"保持。
3. **只读输出真正需要的行/列**：index-only 只读 key；exact 只读候选行的 800 B 向量；
   额外投影列只读 keep 行。读放大是最初最大的单点成本。
4. **大查询向量折成句柄**：plan/优化器成本与表达式规模成正比，200 维字面量留在 plan 里是纯税。
5. **已知形状跳过通用流程**：Limit + 向量扫描的物理计划是确定的；形状校验不通过就回退，收益确定、风险可控。
6. **正确性优先于快路径**：每个快路径都有覆盖性证明/条件检查和 reader 回退；优化只改变"怎么读"，
   不改变"读到什么"（快照、merge-on-read、索引 metric 语义不变）。
7. **先确认测量的是同一条路径**：IP/冷启动的教训说明，性能问题有一类是"基准在测另一条路径"。

## 5. 语义与正确性（最终方案未改变的部分）

- **快照语义**：每条语句仍从 PG 读最新表信息与分区版本；没有默认 TTL/记忆化（`LAKESOUL_METADATA_TTL_MS`
  默认 0，开启是显式部署选择）；批量入口固定在同 snapshot 上。
- **数据层**：表数据不可变、merge-on-read、hash bucket/range partition、时间旅行、索引结构
  （IVF + RaBitQ、nbits=1）全部未动；普通 `list_files_for_scan` 与文本/ES 索引路径未动。
- **缓存语义**：所有缓存都是派生数据/解析结果，绑定不可变身份（表指纹、文件列表、commit、
  文件位置+列布局）；索引 SSD 缓存按对象路径复用、commit 校验仍在内存层；payload 只落本地，
  **不上传 S3**；删掉任一缓存目录只会触发重建/回退，不改变结果。元数据 TTL 只影响可见性窗口，
  默认 0（逐语句最新元数据）；exact direct 需要 `LAKESOUL_CACHE` 提供 PK key index。
- **结果**：
  - index-only Recall@100 全程 0.42035；exact（np32/of1）0.6419（最初 0.64015，略升）；
  - 批量 index-only 200q 0.42035 / 10k 0.43784；批量 exact 200q 0.6419 / 10k 0.6686；
  - IP 单查询 exact 0.7006 / index-only 0.4395；批量 IP exact 0.7152 / index-only 0.4679；
  - 多列融合、P1–P4 场景都有 recall/暴力 top-k 对照与"确实走候选路径"的计数器断言。
- **回退保证**：exact 直读、多文件桶、多版本、过滤、CDC、分区等所有快路径都检查前置条件
  （覆盖性证明、decoded-block 缓存、metric 一致、年龄可判定、谓词可编译）；不满足就回退 reader，
  结果不变，只是慢。block 只是派生缓存，删掉后与回退路径结果逐位一致。
- **测试**：`lakesoul-datafusion --lib` **204 项全绿**（含 IP、批量 IP、多文件桶/多版本、任意投影、
  过滤扩探、CDC、分区、多列融合等）；`lakesoul-io --lib` 全绿（含 payload 往返、reader 融合改动）。

| 元数据 TTL 默认化（当前默认关） | 单查询 +20–31%，c=8 +33% | 新提交/DDL 可见性延迟变为 TTL（100–200 ms） | 需用户决策；已实现为可选开关 |

| exact row cache 默认关闭 | 重复热点候选可省一次 pread | 随机 GloVe 实测 QPS −10.7%、RSS +92.7 MB | 按负载评估后再开 |
| 按需 decoded block（默认） | 无整列物化、磁盘按访问增长 | 随机查询命中率低时块缓存收益有限 | 需要统一 L2 配置；已实现 |
| exact direct 依赖 `LAKESOUL_CACHE` | 提供 PK key index，单点候选定位必需 | 未开启时 exact 回退 reader（QPS 差 30–370×） | 已文档化；后续可解耦成 exact 专用缓存 |
| index probe 内核（rabitq） | 单查询 exec ~40%、批量 CPU ~50% | 属于 `rust/lakesoul-vector` 用户 WIP 区域 | 待用户推进 |
| 批量 exact block 吞吐 | 中 | 需优化 block 布局/预取/增加 L2 | 待决策 |
| 单查询 exact 的 SQL 前端（~1.0 ms） | +10–15% | 需动 DataFusion SqlToRel/AST，风险高 | 未尝试 |
| "固定快照 + 多次查询"入口 | 2× 以上 | 新增 API | 需用户决策 |
| P2 额外列二次读取 | +2–4 ms/query 可省 | 把 payload 扩展到任意标量列，工程量大 | 未做 |
| P3 用统计信息选扩探倍率 | 小 | 需要列统计/代价模型 | 未做 |
| P4 多文件/upsert/分区大表 QPS 实测 | 验证类 | 需要构造大表；正确性已有测试 | 未做 |
| 混合 metric（L2+IP）多列融合 | 小 | 量纲不可比，属预期限制 | 不支持 |
| pgvector 服务默认 `rerank` | 行为决策 | 已改为 index-only（`rerank='index'`） | 已完成 |
| IP 多列融合 QPS 实测 | 验证类 | 与 L2 融合同路径，预期同量级 | 未单独测 |

> 已验证不可行的方向（不再重试）：payload mmap（RSS 不可控）、io_uring（批量内存带宽受限、端到端 0–1%）、
> 稀疏 key 索引/软件预取（瓶颈是内存延迟不是搜索结构）、单查询拆 fetch 线程（新建线程开销抵消）、
> 自适应分组/线程数/连接池调整（都不减少 CPU 总量）。详见 `向量查询优化日志.md` 的证伪记录。
